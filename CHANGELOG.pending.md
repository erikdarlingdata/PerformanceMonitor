### Added

- **A per-collector database scope, so an expensive per-database collector can be limited to a representative sample instead of turned off for the whole server** ([#3477]) - the reporter's measured case is the whole argument: a 72-database instance paying a 43-minute `index_object_stats` pass whose `fanout` block put the SLOWEST database at 4.97% of it - pure width, 71 databases at roughly 36 seconds each - with `index_object_stats` at 17.6% of the store after 6x compression, and only two levers on offer: pay for all 72, or `enabled = false` and lose the index growth trend and duplicate-index analysis, the parts actually wanted. The third option now exists: an optional `databases` allow-list on the `config.config_collector_schedules` row (V125), beside `enabled` and the cadence columns, taking that pass to about one representative database's worth - and because it is an ALLOW-list, the pass cost stays independent of database-count growth: a database created tomorrow is not in the list and stays out until an operator names it, where a deny-list on that instance would mean maintaining 71 names and every new database silently rejoining collection (the reporter's dev estate creates databases daily). Empty or NULL is today's behavior - every database the server enumerates, no change for anyone who does not set it - and the scope layers exactly like the rest of the row: a fleet-wide row (`server_id IS NULL`) sets the default, a server row overrides it, a NULL column falls through per the table's standing per-column rule, and an explicit EMPTY array is "no scope at this level" - the documented opt-back-out that lets one server escape a fleet-wide scope without naming every database it has. `excludedDatabases` stays the coarse instrument and still WINS: the scope is one composed predicate on the enumerations the exclusion already rides - scoped-in AND NOT excluded - spliced engine-side as parameters of the exclusion filter's own shape, so both instruments agree on what a name IS under the engine's collation reality (SQL Server folds case on its default collations, PostgreSQL compares `datname` byte for byte) and no client-side comparer gets an opinion. It is the GENERAL form, one seam per fan-out family rather than a special case: the five enumeration-driven collectors (`index_object_stats`, `query_store`, `query_store_health`, `database_scoped_config`, `plan_correction` - a catalog-walking census pins that a sixth enumerator cannot ship without the seam) and the per-database connection loop (Azure SQL DB's eight, the per-database PostgreSQL collectors) through both providers' database-list plans. The scope is edited in the Viewer's Collector Schedules window as a comma-separated Databases column - the excluded-databases entry format, WYSIWYG on a custom server - and honors the same reload beacon as every other schedule column, so a change reaches the running service on its next sweep. Deliberate boundaries, stated rather than implied: a registration that NAMES a database is that database (the scope does not filter the single-database path, exactly as the exclusion never has - disable the collector for that server instead), and the Azure XE session inventory stays server-shaped, because those sessions serve three collectors whose scopes may differ.
