# PerformanceMonitor 3.12.0

The full changelog entries for 3.12.0. [CHANGELOG.md](../../CHANGELOG.md) carries the
compacted index for every version, this one included, and is where `[Unreleased]` is written.

## [3.12.0] - 2026-10-30

### Important

- **Upgrading from 3.11 runs the Darling store migrations V215 through V229 on the service's first start** - the store schema goes from 214 to 229. Every step adds something, and none rewrites a large table or needs an offline window. The new tables hold the Query Store hints (V217), the keys of the monitor's own Query Store statements (V219), the narrow hourly and daily Query Store data for the query tag roll-up (V221), and the SQL Server Agent alerts, the database protection ages and the identity capacity (V222, V223, V224). The new indexes are six on the investigation tables (V215) and one for the Job History statistics (V220). The new columns are two Amazon RDS flags on the server registry (V225, V226), a server tag scope on threshold overrides (V227), four blocking band columns on the alert settings row (V228), and the severity filter on notification routes with two supporting columns (V229). V218 widens a check to allow the recompile and plan guide server actions, V219 also adds two triggers on the Query Store text table, and V216 changes the Client Timeouts default (next item). The V220 index built in under a second on a copy of a production store, because a compressed chunk holds no rows in it. Two steps leave work for after the first start. The V219 key backfill runs in the background and took 157 seconds on a copy of a large store. The hourly builder fills the V221 tables, newest hours first, so until it catches up a fleet query tag read says how many hours it left out. An older build ignores all of these, and the rollback notes in `docs/darling/admin.md` list what each leaves behind.

- **The Client Timeouts alert is on after the upgrade, in Darling and Lite** ([#5736]) - The alert shipped off because its bars were not checked against real data. They now follow each server's own baseline, and a 7 day replay over 42 servers paged twice. Store migration V216 sets the Darling default to on. It also moves the stored off value to on, because that value was the old default and a store cannot tell it from a choice. Lite does the same once, with a marker in settings.json. If you had it off on purpose, switch it off again once after the upgrade.

- **Lite's DuckDB schema stays at version 78** - There is no Lite schema migration in this release. Lite starts as it did on 3.11, and nothing needs to be done.

- **Self-managed stores: re-run `provision-roles.sql` after upgrading** ([#6542], [#6395], [#6386], [#6389], [#6392], [#6393], [#6394], [#6396], [#6397], [#6398], [#6400], [#6401], [#6454], [#6455], [#6569], [#6928], [#6743]) - Run `Darling/tools/provision-roles.sql` again after the upgrade. The script gained the store functions and grants behind the new MCP write tools and web buttons. They cover a route's agent settings, the default notification channels, webhook signing keys, the service flags, agent actions on and off, database state expectations, a collector's database scope, known patterns, agent notes and closing an investigation request. They also cover the Analyze now and live Active Queries requests, the host change refusal text, and the severity filter column on notification routes. Until the script is re-run, the tools that need a missing function or grant fail. The route, signing key and default channel tools say in one sentence to re-run it. Collection and reads keep working. The compose store and managed provisioning do all of this on their own.

- **New msdb grants for existing monitoring logins** ([#6874], [#6873]) - This release adds two Darling collectors that read three msdb tables. A monitoring login set up for an earlier release does not have these grants. Until you add them, those collectors show as "no permission" in Collection Health. Run these on each SQL Server target, in the msdb database, with your monitoring login in place of `[YourLogin]`. `GRANT SELECT ON dbo.sysalerts TO [YourLogin]` covers the SQL Agent alert definitions and counters. `GRANT SELECT ON dbo.sysnotifications TO [YourLogin]` covers the operators each Agent alert notifies. `GRANT SELECT ON dbo.backupset TO [YourLogin]` covers the last full and log backup per database. The grants are optional, and the rest of collection continues as normal without them. Lite does not use these collectors. The Agent alerts collector does not run on Amazon RDS, Azure SQL Database or Azure SQL Managed Instance. Those servers do not need the first two grants. See `docs/permissions.md` for the full list.

- **The Darling web dashboard and MCP server, and Lite's MCP server, need a token once turned on** ([#6507], [#6557]) - Before, a loopback-only start with no token served every request with no credential. Now the web dashboard and MCP server do not start without a token, and they log one Critical line that names the settings to add. To keep the old tokenless loopback behaviour, with reads only, set `web.allowTokenlessLoopback` or `mcp.allowTokenlessLoopback` in darling.json. Lite's MCP server now answers 401 to any request without a valid bearer token. Lite makes its own token the first time the server starts. The Settings tab has a Copy MCP config button, so an MCP client that sent no token needs the new config.

- **Web dashboard Admin writes stay off after an upgrade until `web.allowAdminWrites` is true** ([#6600], [#6745]) - A missing key means false. Without the key the web Admin pages still list. These writes are refused: arming server-action switches, changing notification routes, webhook URLs and threshold overrides, and undoing agent changes. That is how 3.11 behaved. New installs from the MSI and the install scripts write `"allowAdminWrites": true`. To turn it on for an upgraded install, set it to true in darling.json and restart the service.

- **Adding servers is stricter** ([#6583], [#6752]) - A SQL Server entry's port field was stored but never used to connect. `add_servers`, the web add route and `--add-server` now refuse a non-zero port on a SQL Server target. They say to write it in the host as `host,port`. `--validate-config` warns about each existing entry that has a port. The web add and edit routes also refuse Windows sign-in over an unverified certificate unless `web.allowWindowsAuthOverUnverifiedTls` is true, as the MCP tools already did.


### Added

- **Notification routes can match on alert severity** ([#6928]) - A route now has a severities setting of both (the default), critical or warning (store migration V229). Existing routes keep their effect. A warning route also takes every alert that is not Critical. A resolution goes to the channels the fire went to, and a Warning that climbs to Critical is sent again as Critical. The agent-action gate also resolves each alert's route at that alert's severity.

- **Blocking colours follow settable blocking bands** ([#6927]) - The blocking colour on the Fleet Overview, the Overview tab and the Daily Health Calendar came from fixed limits. Warning started at 5 reports an hour or a 10 second block, and Critical at 20 reports or 60 seconds. A tuned blocking alert still showed red. Four settings now hold the bands (store migration V228), with those limits as defaults. Set them in the Darling viewer Settings window or with update_alert_settings. The fleet totals tiles use the worst band among the servers, and Lite keeps the fixed limits.

- **Alert threshold overrides can be set for a server tag** ([#6926]) - Store migration V227 adds the tag scope. The order is database, server, tag, then global. A tag covers its servers and the tags below it, and the deepest tag wins. The set_alert_threshold_override tool takes a tag in place of server_name. The web Admin tab and the Darling viewer's Threshold Overrides window list and edit tag rows.

- **The Darling grant script has an Amazon RDS form** ([#6889]) - Amazon RDS for SQL Server has no sysadmin and refuses CONNECT ANY DATABASE, ALTER SETTINGS and eight msdb grants to its master user. The command --grant-script --rds prints a script that runs as the master user and leaves those grants out. It creates the login's user in each current user database. Job History in Lite and Darling no longer fails every cycle on RDS when the login cannot read syscategories. A collector run that skips a database because the login has no user in it now says so in its collection log note. The connection test warns with the count.

- **Darling warns before an identity column runs out of values** ([#6875]) - A new collector reads sys.identity_columns every six hours in each user database (store migration V224). It stores the top 20 columns above 10 percent used plus a marker row for each scanned database. The get_identity_capacity tool, web panels, a Darling viewer tab and a fleet card chip show percent used and days to exhaustion. A new Identity Capacity alert is off by default and goes Warning at 70 percent used and Critical at 90. The collector needs VIEW ANY DEFINITION, which the grant script already holds. A pass that runs past 5 minutes stops, and the next pass resumes where it left off.

- **Darling checks the SQL Server Agent alert setup** ([#6874], [#6894], [#6908]) - A new agent_alerts collector reads msdb.dbo.sysalerts and the operators each alert notifies every 15 minutes on SQL Server. Grant SELECT on msdb.dbo.sysalerts and msdb.dbo.sysnotifications to the monitoring login. The get_agent_alerts tool, the web Configuration tab and a new Agent Alerts tab in the Darling viewer report the gaps. A gap is a missing alert for severities 19 to 25 or errors 823 to 825, or an alert that has no operator. A new Agent Alert Gaps alert is off by default. Azure SQL Database, Managed Instance and Amazon RDS do not run the collector, and get_agent_alerts and get_running_jobs answer not collected there (store migrations V222 and V225).

- **Darling watches backups and CHECKDB per database** ([#6873], [#6902], [#6946]) - A new hourly collector stores the last good CHECKDB and the last full and log backup of every database. Grant SELECT on msdb.dbo.backupset to the monitoring login, or the collector records a permissions skip. The RDS form of the grant script leaves it out. The get_database_protection tool, two web Health Checks panels and a Database Protection tab in the Darling viewer show each age. They flag full backups older than 7 days, log backups older than 60 minutes and CHECKDB older than 14 days. Three new alerts are off by default: Backup Overdue, Log Backup Overdue and CHECKDB Overdue (store migration V223).

- **Darling reads PostgreSQL server logs written in a named local log_timezone** ([#6866]) - Darling used to refuse the whole log read when the target's log_timezone was a named local zone such as CET, Europe/Berlin or America/Los_Angeles. It now converts a line only when the target itself proves the instant. A line it cannot prove is skipped and counted in foreign_zone_lines_skipped.

- **A Darling docs page lists every MCP tool and the store tables it reads** ([#6853]) - The page docs/darling/mcp-tool-tables.md lists 273 tools in three groups: tools that read collected data, tools about Darling itself, and tools that change something. A view or continuous aggregate is shown with its base table. Use it to find which tables hold the data for a tool.

- **Darling can front several stores with one web address and one MCP endpoint** ([#6840], [#6917]) - A store is a Darling service with its own monitoring database. Add a frontDoor block with enabled set to true and one entry per store to darling.json, then restart. Each MCP call and web page goes to the store that holds the server, and a fleet-wide read returns one answer per store. The web dashboard gets a store picker, and the Fleet page and sidebar show the picked store first, marked "current". See docs/darling/front-door.md.

- **The Darling viewer's Collector Schedules window has a Find box and a Disabled only filter.** ([#6768]) - The window lists about 70 collectors. The Find box filters by collector name as you type. The Disabled only check box shows only collectors that are turned off. Both can be used together. When nothing matches, the window says so.

- **`get_job_history` takes a `min_duration_seconds` filter, and I/O anomaly briefs name it.** ([#6614]) - The filter keeps only job runs that lasted at least that many seconds. It applies before the row limit. A negative value is refused. The web read route and Custom Views accept it too.

- **A signed-in web dashboard admin can make Admin writes on the managed store, once `web.allowAdminWrites` is on** ([#6600], [#6745]) - On the managed store, the web dashboard signed in to the store with a read-only login, so the Admin pages could only list. Now it keeps a second small connection pool that signs in as the managed admin role. That pool is used only for Admin writes by a person signed in as an admin, with the shared token or through OIDC. Reads stay on the read-only login. The writes are arming server-action switches, changing notification routes and webhook URLs, changing threshold overrides and undoing agent changes. The `web.allowAdminWrites` key in darling.json is read when the service starts, and a missing key means false, so an upgrade from 3.11 keeps those writes refused, as they were. New installs from the MSI and the install scripts write `"allowAdminWrites": true`. To get the same on an upgraded install, set it to true in darling.json. A store that the operator brings is unchanged.

- **Darling now collects Query Store hints, lists them with `get_query_store_hints`, and Change Watch sees one set or cleared.** ([#6581]) - A Query Store hint changes plans like a forced plan, but nothing showed one being set or cleared. A new Darling-only collector reads the hints every 5 minutes and keeps them for 30 days (store migration V217). The new MCP read `get_query_store_hints` lists them. A new Change Watch kind, `query_store_hint`, reports a hint that was set or cleared.

- **Agents can recompile a module and create or drop a plan guide through Level 3 server actions, with Undo.** ([#6569]) - Before, an agent that found a stale plan on a procedure, function or trigger had to run `sp_recompile` outside Darling, and nothing was journaled. The new `recompile_module` action does it with a journal row. The plan guide tools create and drop a guide, and Undo re-creates a dropped guide from the journaled definition. Each action needs its own per-server switch and defaults to a dry run.

- **A request's brief names the earlier report with the same root cause** ([#6565]) - One root cause on one server could open a new request for each analysis story, and the agent had to find the earlier report by hand. Now the brief puts up to 3 reports from the last 24 hours with the same root fact first in earlier_reports, even when 10 newer reports exist. A request still opens as before.

- **Client Timeouts alerts name the client host and carry a client_timeouts evidence section** ([#6553]) - Before, the alert detail named the client application and database but not the client host, and the investigation brief had no timeouts evidence. Now the alert card has a Top client hosts block, get_client_timeouts answers a top_hosts list, and a Client Timeouts request gets a client_timeouts evidence section. This applies to Lite and Darling.

- **Darling MCP supports named tokens with roles, and an operator token can set a notification route's agent settings** ([#6542], [#6395]) - Before, Darling's MCP server took one bearer token and could not tell an operator from an investigation agent, so you had to serve write tools or investigation tools, never both. Now mcp.tokens takes a list of named tokens, each with the role operator or agent. Each caller sees only the tools of its token's role, and an agent's token name is its identity: a different agent_id on a claim, a Level 2 action or a plan action (force, unforce, evict, kill) is refused as agent_id_not_token. The server instructions are written for each role. --validate-config prints the named token findings and warns when no agent token is set while an enabled route has an agent level. An operator token can also set a route's agent fields: create_notification_route and update_notification_route take agent_level (0 to 3), agent_max_per_hour, agent_max_per_day, agent_lease_minutes and agent_expiry_minutes, and no other token can use them. The change is validated like a change in the viewer and it writes a route_agent_changed journal row. update_notification_route also takes clear_agent_level, which puts the level back to Inherit, and the undo call of a route write puts the agent fields back too. Before, these fields could be set only in the viewer or on the web dashboard.

- **The Darling install scripts work with the MSI package and refuse a machine that the MSI owns** ([#6480]) - The install script takes -MsiPhase PreStart or PostStart so the MSI can run its non-service work, such as permissions, the operator group, the store folder and the firewall, without prompts. The uninstall script takes -MsiUninstall. The MSI records InstalledBy=msi in the registry. A plain install, upgrade or uninstall script run now refuses a machine that the MSI installed.

- **The Darling installer offers to add you to the operator group** ([#6478]) - Before, you had to open Computer Management, add yourself to PerformanceMonitor Darling Operators, and sign out and in before the viewer or command line worked without elevation. Now the installer asks once at the end whether to add the signed-in person to that group. The answer defaults to No. The prompt appears only when the group exists.

- **Darling prints the monitoring login and grant script, and the connection test names missing grants** ([#6472]) - The new --grant-script verb prints the login and the GRANT statements for a registered server or a host, with optional FinOps and Azure SQL Database sets. The Add/Edit Server dialog in the Darling viewer has a Copy grant script button and a FinOps checkbox. The connection test now checks the required grants and names each one that is missing. Before, you wrote about 15 GRANT statements by hand, and a missing grant only showed up later as a precondition status on a read.

- **The Darling zip ships Install-Darling.cmd, and the installer offers to restart elevated** ([#6469]) - Before, install-darling.ps1 stopped with a message to use an elevated PowerShell, and on a default client Windows its execution policy blocked it. Now you can double-click Install-Darling.cmd. It asks Windows for administrator rights and runs the installer with the execution policy bypassed for that one process only. If you run install-darling.ps1 without elevation, it now offers to restart itself elevated. Arguments such as -Network pass through.

- **A Darling page on how to back up, restore and move the store** ([#6411]) - There was no documented way to back up, restore or move the Darling store, and no disk-growth guidance. The new page, docs/darling-store-backup.md, has a pg_dump and pg_restore recipe tested against a compressed hypertable and a continuous aggregate, a move to a new host, the files outside the database (darling.json, keys and certificates), the managed, bring-your-own and Linux compose cases, and a section on how much disk the store uses, with size queries and the retention table.

- **Darling MCP write tools return the previous value and an undo call** ([#6403]) - The mute rule tools, the notification route tools and the server admin tools (add_servers, edit_server and remove_server) now answer with the previous value and an undo call. The undo call is the exact tool call that puts the state back. Where no single call can restore the state, undo is null and an undo note says why. The edit_server undo carries the expected modified time, so a change made after the edit gives a conflict instead of an overwrite. Stored passwords are never put in the previous value or the undo call.

- **Darling MCP get_server_settings reads what edit_server changes** ([#6402]) - The new get_server_settings tool returns a server's display name, engine, host, port, database, authentication, encryption settings, Query Store replica, monthly cost and modified_at. No password is returned. The monthly cost also shows in list_servers and get_collection_state as monthly_cost_usd.

- **Darling MCP can switch agent actions off and undo a non-plan agent change.** ([#6401]) - Before, only the viewer and the web dashboard could turn the service-wide agent actions switch off. Only they could undo a mute rule, custom alert rule, threshold override or deadlock signature merge. The new MCP tools `set_agent_actions_enabled` and `undo_agent_change` do the same. Turning the switch on is refused over MCP because that is a person's decision. Both tools need MCP writes on and a token.

- **Darling MCP can write, approve and reject agent notes, close an investigation request, and handle practice requests and report feedback.** ([#6400]) - Before, only the web dashboard and the viewer could do these. The new MCP tools include `write_investigation_note`, `approve_investigation_note`, `reject_investigation_note`, `close_investigation_request`, `start_practice_request`, `save_environment_profile` and `record_investigation_feedback`. They call the same store methods as the web routes, so the checks and journal rows are the same. They need MCP writes on and a token.

- **Darling MCP has a purge_expired_mute_rules write tool** ([#6399]) - Before, only the viewer's Mute Rules window could purge expired mute rules. The new tool takes no arguments and deletes every expired rule. It lists the deleted rules in its reply. It is served only when mcp.allowWrites is on, and it is never offered to an investigation agent.

- **Darling MCP can add, edit and delete known patterns.** ([#6398]) - Before, MCP could read known patterns but only the web editor and the viewer could change them. The new tools `create_known_pattern`, `update_known_pattern` and `delete_known_pattern` use the same store functions as the web routes. Each answer includes the before and after values and the call that undoes it. An update replaces the whole entry, as the web editor does.

- **Darling MCP can read and set database state expectations** ([#6397]) - Before, only the viewer's database state window could set the state the Database State alert expects. The new get_database_state_expectations read lists each database with its current and expected state, whether the expectation is yours, and its status. The new set_database_state_expected write tool sets a state, sets IGNORE, or CLEAR to delete the row. It answers set, cleared or unchanged and gives the previous value and an undo call. The write tool needs mcp.allowWrites.

- **Darling MCP can set a collector's database scope and reset a scope's schedules** ([#6396]) - The new set_collector_databases tool sets or clears the database scope that the schedule editor shows in its Databases column. The new reset_collector_schedules tool does what Reset to Defaults does in the editor. Both tools need mcp.allowWrites with a token, and an investigation agent is never offered them. Before, MCP could set enabled, frequency, run time and retention, but not the database scope.

- **Darling MCP can make and remove webhook signing keys, for the default webhook and for each route.** ([#6394]) - Before, only the viewer could do this, and `update_notification_route` pointed at a step that MCP could not take. The new tools `generate_webhook_signing_key` and `remove_webhook_signing_key` take an optional `route_id`. No `route_id` means the default destination. They need MCP writes on and a token.

- **Darling MCP can set the service flags** ([#6393]) - The new update_service_flags tool sets plan capture, Query Store backfill, the Query Store text budget in MB, the number of concurrent sweeps and the Query Store fetch top N. It needs mcp.allowWrites with a token. An investigation agent is never offered it. The range checks are shared with the viewer Settings window. Before, you had to use the viewer for these five.

- **Darling MCP can set the default notification channels** ([#6392]) - The new update_notification_channels tool sets the channels that every route falls back to. These are the same settings as Settings, Notifications in the viewer. It covers SMTP, Teams, Slack, a generic webhook and PagerDuty. Only the arguments you give change, and a dash clears a text field. Before, MCP could change only the email cooldown and the send-resolution flags.

- **The Darling viewer shows Fleet Sweeps, alert rules and Custom Views** ([#6390]) - The viewer has a Fleet Sweeps tab. It has an Alert Rules window with an editor and a Custom Views manager, and it runs Custom Views as dashboards and notebooks. The alert Triage link opens the server tab of the alert metric at the alert time. Pages that only the web dashboard has are listed in docs/tabs.md with the reason. Before, these existed only on the web dashboard.

- **The web dashboard Recommendations tab has Generate now and Ask AI** ([#6389]) - The Recommendations tab on the web dashboard now has a Generate now button and a per-card Ask AI button, like the Darling viewer. Before, only the viewer had them, and analyze_now was reachable over MCP only. Generate now needs edit rights.

- **The Darling viewer shows Resource Semaphore, Plan Cache by Type, Sessions by Application and more panels that the web dashboard already had** ([#6388]) - The viewer now has the Resource Semaphore Pressure, Resource Semaphore, Plan Cache by Type and Sessions by Application panels. It also shows table and index sizes under FinOps, Database Sizes. The PostgreSQL Overview tab shows the Extension Install Census under the Extensions grid. Before, these panels existed only on the web dashboard.

- **The Darling viewer shows PostgreSQL configuration changes, the logging audit and deadlock graphs** ([#6387]) - The PostgreSQL server tab now shows a Configuration Changes grid with the old and new value, the scope and the kind of change. It shows the Logging Settings Audit, with a verdict for each logging setting and the recommended value. It also shows PostgreSQL deadlock graphs. Before, only the web dashboard and MCP had these.

- **The web dashboard Active Queries panel can read the running requests live** ([#6386]) - A person signed in with edit rights can now ask the service to read the running requests from the monitored server right now, the same way the Darling viewer does. Before, the panel showed only stored snapshots.

- **The Darling viewer charts the four PostgreSQL trends** ([#6385]) - Before, the viewer's PostgreSQL tabs held grids only, while the web dashboard had four trend panels. The viewer now charts the database trend, the query duration trend, the wait trend and the I/O trend. The database and query duration charts are in a new Trends sub-tab on Activity. The charts read through the same code as the MCP tools and the web dashboard.

- **The Darling viewer shows Sweep Pressure and Heaviest Collectors panels** ([#6384]) - The web dashboard's Collection Health tab had these two panels and the viewer did not. The viewer's Collection Health tab for SQL Server now has a Sweep Pressure sub-tab. It shows the sweep verdict, busy percent, peak cycle and peak risk, and the three heaviest collectors. Both panels cover the last 7 days whatever the toolbar window is.
### Changed

- **Recommendations say "times its usual variation" instead of "robust σ"** ([#6925]) - The anomaly advice now says "at least 25 times its usual variation above its normal level" where it said "at least 25 robust σ above its baseline median". It is text only. No number or threshold changed. This applies to Lite and Darling.

- **Updated to .NET SDK 10.0.403, DuckDB.NET 1.5.6.1 and newer AWSSDK and ProtectedData packages** ([#6915]) - The self-contained Lite and viewer builds now carry .NET runtime 10.0.14 instead of 10.0.13.

- **Client Timeouts leaves out the VS Code mssql extension's metadata cancels** ([#6856], [#6858]) - The alert counted the extension cancelling its own metadata queries, as it did for SSMS IntelliSense before. It now leaves out five known vscode-mssql connection names, matched exactly and ignoring case. Any other name stays counted. The alert summary and get_client_timeouts name the tools whose samples were left out. This applies to Lite and Darling.

- **get_forced_plans and get_query_store_hints read each first-seen time in one pass** ([#6833], [#6876]) - Each call found first seen with one scan per output row. With 500 forced plans, 4.6 of 5.3 seconds went to that scan, and 345 hints took about 2 seconds. Both are now one grouped read with the same values. This applies to Darling MCP and the web dashboard.

- **The 31-day daily summary keeps closed days until the next UTC day plus 2 hours** ([#6809]) - The web Overview, the web calendar and the Darling viewer calendar used to reread about 30 closed days from cold. This happened at the first load after every hour. That read took about 8 seconds on a store with 42 servers. Closed days now stay cached and today stays live. Days before the retention horizon are reread once an hour so a purge still shows.

- **get_query_store_clutter and the Darling viewer's Query Store clutter view are faster on large servers** ([#6808]) - The plan churn read no longer sorts every raw row twice. Over 7 days on a server with about 2.4 million rows, warm time fell from about 7 seconds to about 1.3 seconds with identical results.

- **Darling viewer Top Queries by Duration looks up modules only for the ranked statements.** ([#6804]) - The module lookup ranked every retained `procedure_stats` row of the server. On a store with 42 servers that was 10 to 12 seconds of a 13.4 second first call. It now keeps only the ranked handles, as Lite already did.

- **FinOps High Impact and Optimization are faster, with no temp spill.** ([#6803]) - High Impact ran four lookups for every query hash, about 330 on a busy server, and kept only a few dozen. It now ranks first and looks up only the kept hashes. Optimization grouped the whole window's text and plans, which wrote about 345 MB of temp data per call. It now groups on narrow keys and looks up the text per group. The web dashboard, MCP and the viewer all get the change.

- **The Darling fleet `get_resource_use_by_tag` read is much faster: it reads narrow hourly and daily tables and is served from the read cache** ([#6800], [#6794], [#6865], [#6945]) - With no server named, the read used the raw tier for plan cache and procedures, about 10 to 13 GB per statement on a store with 42 servers, and its Query Store part read the whole window from the wide interval table. A cold visit took 61 to 118 seconds. Plan cache and procedures now use the hourly rollup when it covers at least 75 percent of the window, Query Store is read in one statement and not one per server, and a window of 24 hours or more is cached for 5 minutes. Store migration V221 adds narrow hourly and daily Query Store tables for the roll-up. After the upgrade the service builds up to 30 backlog hours per collection tick instead of about 3. A fleet read answers from the newest span that needs no backlog and says how many hours it left out and why. The MCP and viewer roles cannot see another role's transaction start time, and a read by those roles no longer falls back to the slow wide table because of that.

- **Darling's Job History page reads its per-job statistics from a new index** ([#6798]) - The average run time and last success for each job now come from a partial index of successful job runs (store migration V220). The page reads that index one job at a time. Before, a cold page read about 3,700 scattered history rows per server and threw most of them away. A cold call took 8.6 seconds on a store with 42 servers.

- **`--backfill-rollups` and `--recompress` can take the store's free space, and the data volume is measured on Linux.** ([#6791]) - When the store is on another host or a managed service, the verbs could not check free space from the machine that runs them. The new `--free-space <size>` option takes the number you checked on the store host and runs the same room check on it. A login without superuser rights still gets a refusal that says which grant is needed.

- **Query Store regressions list a query for cost only when it added at least 1 second of CPU** ([#6781]) - Before, a query was listed when its CPU per run rose more than 25 percent, even for a few runs of a cheap query. On one store with 42 servers, 80 to 96 percent of the cost rows added under 1 second of CPU over the whole window. - **The Overview tooltip's baseline arrow now shows only for the first series of a chart row.** ([#6787]) - A chart row has one baseline, and it belongs to the first series. Before, the tooltip judged every series against it. Total CPU got a red triangle when it sat above SQL CPU's band, with no matching dot on the chart. This applies to Lite and the Darling viewer.

- **The Wait Drill-Down banner is now readable on the Light and Cool Breeze themes.** ([#6773]) - The banner text was light blue or amber, picked for the Dark theme, and was pale on a pale page. It now uses theme brushes. This applies to Lite and the Darling viewer.

- **A server's own Capture execution plans setting now takes effect.** ([#6771]) - Before, the per-server `capture_plans` value was stored but never read. The service-wide setting decided for every server, though the Settings text pointed at a per-server control. Now NULL follows the service setting. True keeps plan XML for that server even with the service setting off. False collects statistics without plan XML even with the service setting on. An edit takes effect on the next cycle with no restart.

- **The Darling viewer logs a failed schedule read once, not once per waiting caller.** ([#6766]) - Before, one failed read logged up to four warnings, one for each caller that was waiting. It logged them again on every refresh while the store could not be read.

- **Investigation blocking evidence no longer counts parallel self-waits, keeps the head blocker's facts, and honors the high-memory signal.** ([#6761]) - Before, a parallel query's self-wait used up the 500 row cap. It also made a blocked session its own head blocker, so `head_blocker` named the wrong session. Some head blocker facts were empty when a blocked-process report covered the same pair in the same minute. These were login time, last request end, open transaction count and log bytes. The memory flag also ignored the high-memory signal. Now it counts it.

- **Darling web: an empty Add route or Write note says what is missing without a request, and Running Jobs and Recommendations text reads plainly.** ([#6760]) - The Admin page now checks the field first and shows the message without sending a request that returns a 400. The Running Jobs panel showed a 1222 character answer written for MCP clients. It now says which data is missing and keeps the causes the server names. A Recommendations card that read "HIGH 0.80 waits" now reads "HIGH (score 0.80) · waits".

- **Four Darling web pages no longer say two things at once.** ([#6759]) - The Queries tab showed two near-duplicate banners. It now shows one. The Overview CPU tile said "CPU 20%" next to a header chip that says "Total CPU 25%", so the tile now says SQL CPU. Running Jobs called an empty list normal even when the server's collection was stale. It now says the data is stale. The sign-in page now says "SQL Server and PostgreSQL monitor".

- **Darling viewer fixes to the grant script account, PostgreSQL notes and sidebar buttons.** ([#6758]) - The Copy grant script (Windows authentication) command named the wrong account. It now reads the service's real account, and says so when the service is not on this machine. The PostgreSQL Database Trend note no longer says "the biggest temp-file spiller" when nothing spilled. PostgreSQL notes show the real collection cadence, not a fixed one, so a schedule override is reflected. The sidebar buttons Open Plan Viewer, View Log, Open Log Folder and About, and two close buttons, now have accessible names.

- **Three web layout fixes in the Darling dashboard.** ([#6756]) - The server tab strip now wraps, so the last tab is no longer cut off. Recommendations text keeps a readable minimum width on phones. The Overview Waits strip now starts at 0, so a small swing no longer looks like a spike.

- **Lite keeps its first-run server step until the servers are bound to their settings.** ([#6755]) - On the first start of a 3.12 build over an existing 3.11 data folder, Lite wrote its "used before" marker before it bound servers. If the store failed to open or the window closed first, the next start skipped the step. Every server stayed unconfirmed, and SQL login servers needed their passwords typed again. The marker is now written after the binding.

- **Query Store reads now give the right status word on a Secondary role, with Query Store off, and for an empty forced-plan window.** ([#6749]) - Four reads gave the wrong status word: `get_query_store_top`, `get_query_store_duration_trend`, `get_forced_plans` and `get_query_store_hints`. They answered `not_collected` on an instance whose role read Secondary. That instance can still host databases outside any availability group that the collectors read. They now check the health capture first. With Query Store OFF or in ERROR, `get_query_store_hints` answered `unavailable`. It now answers `precondition` with the statement to run. An empty forced-plan window now answers `empty`. This applies to Lite and Darling.

- **Stopping the Darling service during a pass no longer logs a false alert-pass warning.** ([#6748]) - Before, a stop at the wrong moment could log "External alert pass failed" with a "disposed object" error. The collection loop now handles the stop and runs its normal shutdown.

- **The viewer now shows fleet-wide times in a fleet-wide zone, and each server tab's times in that server's own zone.** ([#6747]) - Fleet Sweeps, its time picker and the Custom View run window chart used the clock of whichever server tab refreshed last, with no zone label. The Custom Views "Saved" column ignored the Server, Local and UTC mode. A server tab's "collected" time could show another server's offset. All of these now use the right zone and say which. Two quick selection changes in the Custom Views list no longer leave the grid and editor on different views.

- **The generated grant script and the permissions doc now loop databases with a cursor, not `sp_MSforeachdb`.** ([#6741]) - `sp_MSforeachdb` is undocumented and can skip databases. It also replaced every `?` in the batch. A login name with `?` or a database name with unusual characters gave a wrong or failing grant. The FinOps part of `--grant-script --finops`, and the viewer's copy of it, now loops over writable user databases and quotes names safely.

- **Journal rows for refused agent actions, plan undo and operator route changes now record the right caller.** ([#6740], [#6751]) - Before, a refused bad `agent_action` was journaled with no caller. Every such row read `agent:<invalid>`, and all agents shared one refusal row per tool and hour. `undo_plan_change` recorded only `person:mcp` with no token name. A legacy token that passed a named agent's name and one bad argument wrote a refusal row into that named agent's journal. Each row now names the token that made the call, and `agent:invalid` is used only when the legacy token passes a named agent's name.

- **An investigation claim's later calls are now tied to the named token that made the claim.** ([#6738]) - Before, `submit_investigation_report`, claim renewal and `get_investigation_evidence` checked only the `claim_id`. Any named token that presented another token's claim id could act on it. The legacy token could do the same under a named token's claim. These calls now require the token that made the claim.

- **Plan guide drop answers now follow `mcp.dataDetail`, and forcing or unforcing a Query Store plan honors the excluded database list.** ([#6737]) - Before, `drop_plan_guide` returned the guide's batch text and hints as written, even with `mcp.dataDetail` set to `maskLiterals` or `metadataOnly`. The same text reached the journal. Now `module_or_batch` and `hints` are masked or withheld like other statement text. Also, `force_query_store_plan` and `unforce_query_store_plan`, and the force Undo, never checked a server's excluded databases. They now refuse there like the other plan tools.

- **Choosing the web dashboard option in the Darling MSI now makes a web token, so the dashboard starts.** ([#6736]) - Before, the installer wrote `web.enabled: true` with no token. The web host refuses to start without a token, so the dashboard never started and the installer's last step gave up without saying so. The installer now makes a random token and protects it. The dialog no longer says anyone signed in can open the dashboard without a password.

- **A server action switch no longer turns on for an Azure SQL target whose tool always refuses the action.** ([#6727]) - Before, the switch screens showed "on" and "valid" for an action that failed at every call on Azure SQL Database or Managed Instance. The switch now checks the stored engine edition and refuses to turn on an action the target cannot run.

- **A generic webhook can now close an alert, and a PagerDuty resolve now closes the incident the trigger opened.** ([#6718], [#6723]) - The generic webhook has a new `{{status}}` token. It is `firing` on an alert and `resolved` on a resolution. A resolution now carries the same dedup key as the fire, so a receiver can pair the two posts. For PagerDuty, the resolve used a key from a different set of incidents than the trigger. On some alerts the wrong incident closed and the right one kept paging. The resolve now sends the key the trigger sent.

- **Darling now copies the generic webhook, PagerDuty and send-resolutions settings from darling.json on its first start.** ([#6715]) - Before, the first start copied only the email, Teams and Slack settings into the store. The store won, so the file's generic webhook, PagerDuty and send-resolutions keys never took effect and nothing said so.

- **Darling on plain PostgreSQL: the blocking and deadlock baselines stop at the purge horizon** ([#6706]) - On a store without TimescaleDB, the raw tables are purged at the retention time, but the days that count as covered reach back 30 days. With a retention under 30 days, days with no stored events counted as quiet. At 7 days retention about 23 of 30 days read as quiet. The mean fell about 77 percent, and normal blocking or deadlocks flagged as anomalies. The baselines now stop at the purge horizon.

- **Alert texts use the right word for a count of one** ([#6700], [#6703]) - Alert texts printed counts like 1 source(s), 1 checkpoint(s) and 1 mute rule(s) have been. They now read 1 source and 1 checkpoint, and 1 mute rule has been, with the plural form for other counts. This covers the e-mail, Slack and other routes, the alert history and the MCP alert tools. Alerts that are already stored keep their old text.

- **ANOMALY_WRITE_LATENCY is scored against a write latency baseline** ([#6696]) - The write latency gate used the read latency baseline. Take a server whose reads sit near 1 ms with a narrow spread. Any ordinary write window of 10 ms or more scored far above that baseline. One store saw 129 alerts and 16 investigation requests in 14 days, and every one was normal nightly writes. The gate now uses a baseline built from write latency. This applies to Lite and Darling.

- **Chart text keeps its size at high Windows display scaling** ([#6678]) - In Lite and the Darling viewer, chart labels were drawn at 40 percent of their size at 250 percent display scaling. Charts now take the display scale of their window, and they follow when the window moves to a screen with another scale.

- **Darling's Query Store reads no longer list the monitor's own statement or statements from dropped databases** ([#6654], [#6659]) - The get_query_store_regressions tool and the viewer listed the monitor's own statement and queries from databases that the server had dropped. Dropped databases also used up the row limit. These are now left out of the regressions read and of the other ranked Query Store reads, and the read names the databases it left out.

- **Index Analysis no longer shows two banners that contradict each other, and two Settings and plan card labels are corrected** ([#6653]) - In the Darling viewer, Index Analysis showed the uptime under 14 days banner next to the dedupe-only banner. The first says unused index findings may be premature and the second says unused indexes were not flagged. With dedupe-only in effect, only the dedupe-only banner shows now. The get_finops index analysis notes follow the same rule. The help text for Capture execution plans and Query Store history backfill now sits with the matching settings. The estimated plan card is titled for what it holds instead of Predicted Runtime.

- **The Darling viewer charts and grids stay readable on a 1366x768 screen** ([#6652]) - Before, stacked charts got a plot a few pixels tall, long left axis titles were cut at both ends and two wide grids, Query Store Regressions and Collection Health, squeezed their columns to slivers. Charts now keep a minimum height and the page scrolls. The grids keep their column widths.

- **Web dashboard pages say MCP field names and raw collector counts in plain words** ([#6649]) - Notes written for MCP callers reached the web pages with field names that a person cannot act on, such as (see databases_left_out), baseline_start and latest_memory_mb, and raw key=value collector counts. The web pages now say these in words. MCP clients see the same text as before.

- **The right-sized verdict sentence says what decided the verdict** ([#6646]) - A right-sized verdict also comes from a CPU average under 15 percent with one sample at 40 percent or more. It also comes from a memory grant use of 50 percent or more. The old fixed sentence said CPU was moderately loaded and memory was well used, which contradicted the numbers. The sentence now names the test that decided the verdict.

- **A parallel query that waits on itself is no longer counted as blocking** ([#6645], [#6690]) - The threads of a parallel query can write blocked process reports where the blocked and blocking session are the same. Before, these counted in the wait counts, the head blocker count, the blocking chain and the blocking anomaly count. Now they are left out. The Darling blocking baseline leaves them out too, so it is compared with the same kind of window. Before, a server with many of these waits had a baseline that read too high. A real rise in blocking could stay under the anomaly line. Lite already did this for its baseline.

- **A store that the operator brings now works for every MCP tool and web page that takes a server name** ([#6630]) - The MCP and web hosts opened the store with the connection string exactly as darling.json gives it, without the collect and config search path. On a database whose search path could not be set, every MCP tool that takes a server name failed with error 42P01. Web reads failed the same way. The hosts now add the search path, as the worker already did. The CLI and the viewer connections do too.

- **Darling logs a usable web dashboard and MCP address when it listens on a specific IPv6 address** ([#6609]) - Before, a specific IPv6 listen address was logged without brackets, for example http://fd00::5:5150/, and a browser cannot open that. Now the address is logged in brackets. The installer ready message uses the same address, so it is correct too.

- **Darling Query Store query history now reports a plan whose force was removed as REMOVED.** ([#6598]) - Before, a plan that was forced when sampled showed `is_forced_plan: true` with no forced state and an empty `forced_plans` list. An agent needed a second call to `get_forced_plans` to learn the force was gone. Now the plan shows `forced_state: "REMOVED"` and the removed force appears in `forced_plans`. A standing force never drops out of the list because of a removed one.

- **The Darling install script registers the service path in quotes** ([#6597]) - Before, install-darling.ps1 registered the service path without quotes, so sc qc showed a bare path with spaces. The MSI registers it in quotes. The script now registers the quoted path, for both a new service and an in-place change.

- **An agent that holds the live lease gets its claim_id back when it claims again** ([#6576]) - Before, an agent that lost its claim_id could not get it back. A second claim_investigation_request answered already_claimed, and the request stayed locked until the 15 minute lease ended. Now, with a named agent token in Darling, the claim answers renewed with the existing claim_id and renews the lease. A different agent still gets already_claimed. Lite and the legacy token keep the old answer.

- **Change Watch no longer counts log_reuse_wait_desc as a database configuration change** ([#6566]) - The log_reuse_wait_desc value changes by itself when a long transaction ends or a log backup runs. Before, that opened watches and investigation requests, for example a tempdb change from ACTIVE_TRANSACTION to NOTHING. Change Watch now skips it, as the analysis already does. get_database_config_changes still lists it.

- **get_change_watches accepts state=all, sends each fact once, and can read one watch by watch_id** ([#6561], [#6591]) - Before, the tool answered state all when you left state out, but refused state=all as invalid. Now state=all means no filter. A closed watch also carried measures, not_measured and changes twice, so a request for 3 watches could return about 60 KB. Now each fact appears once. The new optional watch_id argument returns one watch in any state. An unknown id, text that is not a GUID, or an id from another server answers not_found. This is Darling only.

- **A Darling Change Watch no longer calls a plan mix shift a regression** ([#6555]) - A query that runs a fast plan and a slow plan at the same time has an average duration that follows the mix of plans. Before, a shift in that mix showed as a slower query even when no plan got slower. Now the watch compares the after window at the plan mix of the before window. A plan that got slower on its own, or a new slow plan, still counts as a regression. The result notes say when the average moved only with the plan mix. This covers Query Store and plan cache measures.

- **Query Store reads on a readable secondary say it is not collected, and why** ([#6554]) - The collectors skip every database on a readable secondary, so it has no Query Store rows. Before, get_forced_plans answered empty and get_query_store_top said Query Store is READ_ONLY. Now both answer not_collected and say that the server is a readable secondary. The message stays silent when query_store_replica is set for the server.

- **The Client Timeouts alert leaves out SSMS IntelliSense's own cancels** ([#6552]) - Before, the alert counted every time SSMS IntelliSense cancelled its own metadata queries. Those events are now left out of the count that the alert judges. When only IntelliSense pushed a server over a threshold, the fire is recorded as muted and nothing is sent. get_client_timeouts still shows these events and marks them as excluded.

- **Change Watch requests get their own family, skip replicated plan changes, and name the database** ([#6551]) - Before, a Change Watch request fell into the other family with custom and external alerts, and it spent the hourly limit of the performance route. A forced plan on a readable secondary was recorded again there, because its Query Store holds the primary's forced plans. The request detail also named query hashes without the database. Now the requests have a family of their own, a secondary skips replicated plan changes, and the detail names the database and where the hashes came from.

- **Change Watch says whether a plan was forced by automatic plan correction** ([#6550]) - Before, a recorded plan force did not say who forced the plan. A watch with only automatic plan correction forcing and reverting plans opened an investigation request like a person's change. Now each plan force carries MANUAL, AUTO, NONE or unknown, and get_change_watches shows it. A watch with only AUTO changes opens no request. A change recorded before this reads as unknown.

- **SQL Server's own cleanup statements are left out of regression targets, findings and Query Store reads** ([#6548]) - A regression of the change tracking cleanup statement could rank first in the regression_targets evidence and in the PLAN_REGRESSION finding. Those now skip change tracking cleanup, sp_flush_commit_table and sp_cdc_cleanup_change_table. A read such as select * from sys.change_tracking_tables is not skipped. The Darling Query Store reads that rank statements, get_query_store_regressions among them, leave these statements out too. Their filter also matches the change tracking cleanup text that SQL Server writes with brackets, which it did not match before.

- **The brief keeps the request's only alert when its text is long** ([#6547]) - Before, if the first alert alone was longer than the 8,000 character budget of the alerts section, the section came out empty and the agent got no alert text and no metric. Now the brief keeps that alert and cuts its long text further. The metric, time, value and threshold are never cut. The truncated entry says shortened: true. This applies to Lite and Darling.

- **Darling table tuning waits at most 5 seconds for a lock** ([#6539]) - Before, each ALTER TABLE SET statement could wait up to 300 seconds behind another operation that held a heavy lock, such as drop_chunks or decompress_chunk. That could stall a service start. Now each statement waits at most 5 seconds. On a timeout Darling logs one Information line naming the table and retries on the next pass.

- **Darling investigation requests from analysis findings get the resources and jobs families, not other** ([#6536]) - Before, most analysis categories that a SQL Server run emits had no investigation family. Their requests got the family meant for custom and external alerts, so you could not tell them apart by family. Findings in the anomaly, cpu, memory, io and disk categories now map to the resources family, and jobs findings to the jobs family. The family sets which open request a new one joins, which tools the brief offers, and the family filter in list_investigation_requests. A request opened before the upgrade keeps its other family, so an incident in flight at the upgrade can briefly hold an other request and a resources request for the same server. The config, database_config, coverage, bad_actor, tempdb and waits categories and the PostgreSQL ones stay other. This applies to Lite as well, because both editions share the map.

- **Lite asks again before it uses a saved password for a changed server** ([#6504], [#6559]) - Lite keeps one server list for every Windows user of the computer, but each user has their own saved password. Before, if a server's host changed, Lite went on sending that user's saved password to the new host. Now Lite remembers, for each Windows user, the settings each server was saved with, and it asks you to confirm before it uses a saved credential with changed settings. In the Edit Server dialog, Test now asks one question and names the Query Store replica when you typed one. It no longer asks a second time after you answered Yes, and it asks nothing when the replica box is empty.

- **Lite clears the Blocking and Deadlocks strips when the window has no events** ([#6482]) - Before, the strips kept the bars from the previous window while the grid below said there were no events. Now each strip clears and shows "No blocked process reports in the selected time window." or "No deadlocks in the selected time window."

- **The Darling installer tells the truth when it stops, catches an unedited sample, and puts shortcuts where every user sees them** ([#6475]) - Before, it printed "Nothing was installed or changed" after it had already locked the folder's permissions. A darling.json that was an unedited copy of the sample passed on a rerun and installed. The Viewer shortcuts went to the Desktop of the elevated account, which is not always the person's. Now the sample check runs before the lock, the stop text says what is true, and the shortcuts are made for all users.

- **The investigation brief lists the arguments that submit_investigation_report really takes** ([#6462], [#6546]) - Before, the brief's report contract listed root_cause_found as required, but the tool has no such argument, and it left out summary, which is required. The list now reads request_id, claim_id, report_format, verdict, root_cause, evidence and summary. The brief says the service sets root_cause_found from the verdict. For an anomaly request, the brief's next_calls now start with calls that fit the anomaly, such as get_file_io_trend for write latency and get_cpu_utilization for a CPU spike. This applies to Lite and Darling.

- **Darling builds all three large start-path indexes during the first start of an empty store** ([#6460]) - Before, a new store built one of the three indexes on its first start and deferred the other two. About 30 seconds later the hourly pass logged two warnings that read like a fault, and a new store needed several restarts to be fully tuned. Now an empty table does not use the one-build budget, so the first start builds all three indexes and logs no warning.

- **Lite no longer logs a notification_routes warning on its first start** ([#6458]) - On a first start, Lite read the notification_routes table before it had created the table and logged a WARN that read like a fault. Lite now creates its store first and then loads the routes. A table that goes missing later is still logged.

- **Fleet-wide windows in the Darling viewer show times one way, and Azure SQL Database notes lead with what the engine lacks** ([#6457]) - The Notification Routes, Threshold Overrides and Known Patterns windows showed times in three different ways with no label, and Notification Routes applied a server's UTC offset to rows that belong to no server. Now all three show the same instant the same way, with the zone name after the time, for example 2026-07-01 10:07 UTC. Local mode uses this machine's zone and every other mode uses UTC. The "not collected" sentence on Azure SQL Database tabs such as Running Jobs, CPU Scheduler and Trace Flags now starts with what the engine lacks, not with the collector's name.

- **Darling investigation event webhook posts now send the default User-Agent** ([#6456]) - Before, an investigation event post carried only the content-type and webhook signature headers, with no User-Agent. Now it sends the same default User-Agent that an alert post to a generic webhook URL already sends. Operator headers still belong to the alert channel only.

- **Darling MCP write tools give honest statuses and clearer errors** ([#6455]) - The edit_server refusal for a host or connection change now says that the new settings must come with the password. The dismiss_alert_history and restore_alert_history tools answer dismissed or restored only when a row changed. They answer not_found for keys that name no row and unchanged for rows already in the asked state. update_alert_settings names the cooldown delivery.cooldown_minutes in updated_fields, whether the caller sent that or the email_cooldown_minutes alias. assign_query_tag refuses a query_hash that is not 0x plus 1 to 16 hex digits, or a decimal that does not fit an unsigned 64-bit number, as invalid. A call that leaves out a required argument now answers invalid and names the argument, in Darling and in Lite, including a call with no arguments at all. When a plan tool refuses a dry run that has no agent_action, the message says why a dry run needs the claim and whether the server action switch is on. The tool text and docs for custom alert rules now state the rule scope, which is all servers, a list of servers or a fleet tag. With no scope, the rule applies to every monitored server.

- **Darling server admin tools are current at once and clean up after remove_server** ([#6454]) - Before, list_servers could show an edit or a removal 40 to 60 seconds late. Now it reads the server definition and is current at once. remove_server now also clears that server's collector schedule overrides and run times, which would have come back when you added the server again. The monthly cost of a server can now be cleared.

- **Reads with nothing stored say empty when the collector ran clean** ([#6453]) - Before, the system_health reads and other reads with no stored rows answered unavailable and told you to check collection health, while collection health called the same collector healthy. Now a read with no stored rows answers empty, a true negative, when the collector's newest run succeeded with no note. This covers the nine get_health_parser reads after a clean event_file read. It also covers get_collector_stall_probes, which no longer answers not_collected for an empty 7 day window. An idle query_stats collector, such as on a serverless Azure SQL Database, is no longer banded WARNING as regressed.

- **The system_health collector keeps reading new events when the ring buffer is full** ([#6441], [#6544], [#6564]) - SQL Server cuts the ring buffer at about 4 MB and keeps the oldest events. Before, a busy server could store 0 rows and record success while new events sat unread. Lite and Darling now read the session's event_file target, and the ring buffer is the fallback. When the saved bookmark is in the current file, the read opens that file by its exact path, so it stays well inside Lite's 30 second command timeout.
