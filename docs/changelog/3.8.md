## [3.8.0] - 2026-09-17

### Added

- **The web dashboard's TLS certificate warns before it lapses, on the channel you already watch** ([#3514]) - a LAN-exposed dashboard configured with `web.network.tls` loads its certificate ONCE at service start and serves it for the process's life, and its expiry was surfaced only two ways - a startup-log line within 30 days of the date, and the `--status` summary - both of which need someone to look. On a headless service that can run for months without a restart neither re-fires as the clock crosses the window, so the first anyone learned of a lapsed certificate was the dashboard failing closed to loopback-only the day it expired (correct - it never downgrades to plain HTTP - but a silent surprise). The service now re-reads the SERVED certificate's fixed expiry against the clock on its own hourly cadence and raises a fleet self-alert through the same delivery, cooldown and mute plumbing as Retention Held and the stale-mute alert: Warning inside 30 days (the same `ExpiryWarningDays` the startup log uses, so the two agree to the day), Critical once lapsed, and a resolution when the dashboard stops serving the certificate - disabled at runtime, or TLS switched off (an in-place renewal is a service restart, which simply stops it firing). It fires WITHOUT a restart and names the certificate's subject, thumbprint and expiry so it ties to the host's own log line, and re-states daily rather than on the shared cooldown because the fact is a fixed date that changes only when the operator renews. The SERVED certificate is the one that matters, not the file on disk: exposure is restart-only, so a fresh certificate dropped in without a restart is not the one still serving and still lapsing - and an already-expired certificate the host refused at start still surfaces the Critical rather than being lost to a log line. Loopback-only installs, an unconfigured `tls` block and an unusable one raise nothing, because there is no served certificate to watch.
- **A per-collector database scope, so an expensive per-database collector can be limited to a representative sample instead of turned off for the whole server** ([#3477]) - the reporter's measured case is the whole argument: a 72-database instance paying a 43-minute `index_object_stats` pass whose `fanout` block put the SLOWEST database at 4.97% of it - pure width, 71 databases at roughly 36 seconds each - with `index_object_stats` at 17.6% of the store after 6x compression, and only two levers on offer: pay for all 72, or `enabled = false` and lose the index growth trend and duplicate-index analysis, the parts actually wanted. The third option now exists: an optional `databases` allow-list on the `config.config_collector_schedules` row (V125), beside `enabled` and the cadence columns, taking that pass to about one representative database's worth - and because it is an ALLOW-list, the pass cost stays independent of database-count growth: a database created tomorrow is not in the list and stays out until an operator names it, where a deny-list on that instance would mean maintaining 71 names and every new database silently rejoining collection (the reporter's dev estate creates databases daily). Empty or NULL is today's behavior - every database the server enumerates, no change for anyone who does not set it - and the scope layers exactly like the rest of the row: a fleet-wide row (`server_id IS NULL`) sets the default, a server row overrides it, a NULL column falls through per the table's standing per-column rule, and an explicit EMPTY array is "no scope at this level" - the documented opt-back-out that lets one server escape a fleet-wide scope without naming every database it has. `excludedDatabases` stays the coarse instrument and still WINS: the scope is one composed predicate on the enumerations the exclusion already rides - scoped-in AND NOT excluded - spliced engine-side as parameters of the exclusion filter's own shape, so both instruments agree on what a name IS under the engine's collation reality (SQL Server folds case on its default collations, PostgreSQL compares `datname` byte for byte) and no client-side comparer gets an opinion. It is the GENERAL form, one seam per fan-out family rather than a special case: the five enumeration-driven collectors (`index_object_stats`, `query_store`, `query_store_health`, `database_scoped_config`, `plan_correction` - a catalog-walking census pins that a sixth enumerator cannot ship without the seam) and the per-database connection loop (Azure SQL DB's eight, the per-database PostgreSQL collectors) through both providers' database-list plans. The scope is edited in the Viewer's Collector Schedules window as a comma-separated Databases column - the excluded-databases entry format, WYSIWYG on a custom server - and honors the same reload beacon as every other schedule column, so a change reaches the running service on its next sweep. Deliberate boundaries, stated rather than implied: a registration that NAMES a database is that database (the scope does not filter the single-database path, exactly as the exclusion never has - disable the collector for that server instead), and the Azure XE session inventory stays server-shaped, because those sessions serve three collectors whose scopes may differ.
- **The High CPU card names the active maintenance operation** ([#3495]) - first night of live dogfood alerting, a High CPU page delivered honestly - 100% total CPU sustained, correctly split SQL/other - and the cause still took two more instrument reads to establish: an RDS-managed `BACKUP DATABASE ... WITH COMPRESSION` seventeen minutes in, compression burning the SQL share and the backup agent the other, visible the whole time in the active-session snapshot the service had already collected on the same sweep. Everything the triage needed was knowable by the alert pass at fire time; the card just could not say the one sentence that closes it. Now, when the High CPU condition fires, the fire branch reads the same active-session surface the operator ended up reading by hand - the long-running-query alert's own store read, at threshold zero with every noise opt-out OFF and an empty database-exclusion list, all deliberate: the `excludeBackups` filter exists to keep maintenance off THAT alert, and this probe wants exactly the population it removes, while an excluded database's backup still burns this server's CPU - and appends one line per system-maintenance session to the card's detail: `Active maintenance: BACKUP DATABASE (RdsAdminService), 17m 14s elapsed, ASYNC_IO_COMPLETION` - statement kind, program, elapsed, wait, straight off the session row. `BACKUP DATABASE`/`BACKUP LOG`, `RESTORE DATABASE`/`RESTORE LOG` and `ALTER INDEX` are the recognized shapes, matched on the trimmed statement HEAD rather than contains-anywhere, so the annotation under-claims (a maintenance statement buried mid-batch costs only its line) rather than ever naming maintenance on a card where none runs - the wrong direction for an annotation whose whole value is being trustworthy. Concurrent maintenance sessions get one line each, longest-running first, capped at three with the omission STATED - the [#3493] discipline, never a silent cut - and the added lines ride the same prose path that fix taught to split across Slack section blocks, so a longer detail text costs blocks, not delivery. **This is an annotation, never a suppression: the tiers stay where they are, the page still fires, and the line states what IS - session kind, program, elapsed, wait - never a verdict.** A backup pinning CPU at 04:30 with the store idle is routine; the same pin at 14:30 under checkout load is a capacity finding with a named cause, and that judgment belongs to the reader, who can only make it in one glance if the card names the backup. Absent any maintenance session the card is byte-identical to before, pinned. The probe is cooldown-bounded - fire branch only, one bounded read per delivered page, never per sweep - and log-and-degrade: a failed annotation read is counted on [#3013]'s swallowed-read surface under its own read name (so an annotation gone blind is distinguishable from a condition gone blind) and costs the card its maintenance line, never the page. And the line is a rendering, not an identity: High CPU carries no incident fingerprint and its cooldown keys on (server, metric), so a page that re-fires with a different elapsed is the same incident it always was.
- **The Long-Running Query card names the Agent job** ([#3497]) - second night of live dogfood alerting: the nightly index-maintenance window opened and the Long-Running Query alert did its job, roughly a dozen honest cards over two cohorts, each showing an `ALTER INDEX ... REORGANIZE` past the threshold - and each leaving the reader to reconstruct "that is the maintenance job, running as scheduled, merely long" from the statement shape, the hour, and prior knowledge, twelve times, every night, because index maintenance recurs. The session data the collector already captures identified the program as a SQL Agent job step; the card never surfaced WHICH job. Now a card whose session's `program_name` carries the standard `SQLAgent - TSQL JobStep (Job 0x<job_id> : Step <n>)` form gains one field, directly under the raw Program it explains: `Running under Agent job: nightly index maintenance, step 3 (Reorganize fragmented indexes)`. The job id is recovered from the program name's hex - the `uniqueidentifier`'s binary(16) layout, Data1-Data3 little-endian, the same conversion the collector's CDC filter already does server-side via `TRY_CONVERT(uniqueidentifier, TRY_CONVERT(binary(16), ...))` - and the byte order is PINNED in tests rather than trusted, because a wrong conversion here does not error, it resolves nothing, silently, on every card. Names resolve in ONE msdb round trip per delivered card, at FIRE time deliberately: capture time would have meant a schema rung on both stores and a failed lookup baked into collected rows, where fire time costs nothing on quiet sweeps (the lookup sits inside the cooldown-gated fire branch, scoped to the sessions the card will actually show, deduped) and a failure retries on the next card. The lookup rides the recently-failed-job check's exact live-msdb seam and permission arm on both SKUs: a monitoring login without SELECT on `msdb.dbo.sysjobs` and `sysjobsteps` - expected for read-only accounts, and SQLAgentReaderRole is NOT the remedy, it gates the `sp_help_job*` interface and confers nothing on the base tables - degrades to the unresolved form, `Running under Agent job: (name unresolved) Job 0x<hex>, step <n>`, which still states the Agent-job fact the parse alone establishes and carries the raw marker an operator can match against the Program field by eye; logged at Info with the grant named, never an error, never a blocked card. **This is an annotation, never a suppression - the [#3495] contract, sibling card: the thresholds stay where they are, every card still fires, and the annotation states what IS, never a verdict.** A maintenance job running long during its own window is routine; the same job still running at noon, or an unfamiliar job name on a checkout-adjacent statement, is a finding - and that judgment belongs to the reader, who can only make it in one glance if the card names the job. Sessions not under Agent render byte-identically, pinned, and never trigger the lookup at all. The annotation is fingerprint-INERT by construction: the [#1140] dedup key hashes (server, incident type, `query_hash`) and the annotation is a rendered field, so a card that re-fires with a different elapsed - or with the job name freshly resolved, or freshly unresolvable - folds into the same incident it always did, which per-fingerprint delivery cooldowns and PagerDuty correlation both key on; pinned through the engine, not merely stated.
- **A store's self-alerts can name the store they came from** ([#3500]) - every fleet-level self-alert a Darling store emits - `Store Disk Pressure`, `Retention Held`, the `Collector Cost Digest`, the `Fleet Sweep Rollup`, all twelve families and their resolution edges - fired under the constant `Monitor Store`, which is unambiguous with exactly one store and the product does not assume there is only one: the `peers` block exists precisely to describe a multi-store estate. The reporter is standing one store up per data centre, both delivering into one Logic App, one Teams channel and one Azure DevOps board, and their analysis named both halves of the cost with precision: on the shared channel a `Store Disk Pressure` says `Monitor Store` and nothing else, so the operator checks both hosts to find the one filling up - and, the half that bites, the delivery fingerprint downstream automation dedups on is computed inside the product from the same constant identity on both stores, so the second store's disk pressure never opens its own work item, it lands on the first store's as a recurrence. One host's incident is silently lost, and no transport-level workaround (a query parameter per store, a Logic App per store) can reach a fingerprint computed inside the product. The new file-only `peers.storeName` - a short label beside `thisStoreCovers`, which stays the sentence it is - opts a store in: set, it becomes the server label on every self-alert family, flowing into the cards, the alert history, the mute-rule matching, the triage page's fleet-level recognition (both spellings keep answering there, because channels still hold links minted before the opt-in) and the delivery fingerprint, exactly as a monitored server's display name travels - so two stores with distinct labels produce distinct fingerprints for the same family, and the Teams card names the host. **Unset is byte-identical to today**, pinned by a test that compares the fired outcomes as whole records, because the label is part of the fingerprint and changing it orphans every open work item keyed on the old one: the operator who sets the field is accepting that re-key knowingly, which is also why the reporter's suggested machine-hostname fallback is deliberately not taken - it contradicts their own (correct, bolded) opt-in requirement by performing the re-key on every existing install at upgrade, silently. One coupling to plan for, documented at the field and here: **mute rules match the alert row's server spelling**, so on an opted-in store, re-scope self-alert mutes from `Monitor Store` to the label - a rule scoped to either spelling matches exactly the rows that spelling names, in both the shared mute seam and the stale-mute alert's own explicit-rule scan. A label that shadows a monitored server's display name is a stated non-goal to police - the registry is store-authoritative after seeding, so config validation cannot see it - and the docs say not to reuse one. Every fire site reads one accessor, held by a from-source census so a thirteenth family added later cannot quietly hardcode the constant back in, and the label gets the peers block's credential-shaped-text refusal, because it rides out on every delivery channel. Credit to the report for the estate shape, the fingerprint mechanics and the opt-in requirement arriving already worked out - the issue was the design document.

- **Fleet Sweep Reports: the sweep with memory, on the web dashboard** ([#3466]) - a scheduled, stateful whole-fleet summary at a user-configured cadence (15-1440 minutes, default hourly, the new `fleet_sweep` settings group beside the alert knobs) that the alert engine deliberately is not: alerts are edge-triggered per fingerprint, and this is level-and-difference reporting per fleet. Every sweep bands each server through the SAME daily-summary scoring the Performance Calendar and `get_daily_summary` use, diffs against the previous sweep's PERSISTED rows (band transitions with their reasons, servers arriving and departing - a first sweep says `no_previous_sweep` rather than implying a quiet history), advances watch items through a hysteresis state machine whose bars are stated in sweeps (two consecutive sightings to open, two quiet sweeps to close, so no single sample flips state in either direction), and persists one immutable document per run. Two contracts learned on a real fleet lead the design. The muted-mode contract: with the alert master switch OFF the sweep keeps running at full cadence, states the mute on every document, and carries a would-have-paged ledger - one evidenced row per (server, critical trigger), derived from the sweep's own scoring and labelled as such rather than replaying the alert engine - because on the evidence day an operator mute was the only thing standing between an 18-minute CPU pin and nobody ever knowing. And quiet-is-not-clean: every sweep proves its instruments were alive before believing a quiet hour (per-server read faults render as unreadable-not-quiet, fleet-wide silence outside the post-restart settle window fails the verdict, and a frozen alert-pass counter beside a delivering path - the reading that caught a real gating defect - is judged against the previous sweep's own persisted baseline), and a sweep that could not prove its instruments renders LOUDLY on the new **Fleet Sweeps** web page: a red banner on the document and a marked timeline row, never a green sweep with a footnote. The page shows the timeline at configurable viewing spans (default the last hour, per the delivery ruling), the per-server verdict transitions, the watch-item worklist with each item's hysteresis position, and the ledger whenever a sweep was taken under mute - including empty, because "muted, and nothing would have paged" is a statement the operator is owed. Channel delivery is deliberately bounded at a **daily rollup**, a ceiling and not a default, by the same ruling: at most one INFO post per day (the collector-cost digest's machinery reused whole - daily dedup, empty-sends-nothing, the declared INFO arm, the shared mute seam) summarizing the trailing day's band transitions, watch-item openings and closings, instrument-liveness incidents, and - whenever any covered sweep ran muted - the would-have-paged ledger those sweeps carried, counted and named per family and server, so the operator sees what the silence cost. A day with nothing to say posts NOTHING rather than a one-line all-clear (an honest all-clear would have to carry its instrument-liveness proof, and a daily post carrying proof-of-quiet is the report card the ruling bounds; the affirmative all-clear lives on the web feed at full cadence, where every sweep proves its own instruments), and the rollup's delivery is itself master-gated: under the mute the sweeps keep publishing, nothing reaches the channel, and the first post-re-enable rollup covers its trailing day only and states how many of its sweeps ran muted - older muted days stay in the web feed permanently rather than arriving as a re-enable flood. The `get_sweep_reports` MCP tool completes the non-goals split (the product publishes evidence, an operator's agent adds judgment): the sweep timeline, one sweep in full, and the watch worklist, through the SAME presentation builders the web feed serves, with the mute-header and quiet-is-not-clean field semantics documented in the tool description an agent plans against.
- **A 90-second plan-flip pileup can page, from the collectors that were already current while it ran** ([#3467]) - a parameterized statement joining a `#temp` table flipped to a plan doing ~35x the logical reads; every caller shares the parameterized plan, so ten tenants inherited the flip together, the copies convoyed on `PAGEIOLATCH_SH`, and sixteen executions died at the client's 30-second command timeout. The whole episode ran about ninety seconds and self-cleared. The store was AHEAD of it: the 20:10:31Z active-query snapshot had three concurrent copies of the one statement - 29.1 s / 28.3 s / 27.7 s elapsed, 287K logical reads on the leader, two suspended on page-IO - beside that same statement's 54 ms observation from 3.5 minutes earlier. Nothing could page on any of it. The timely findings were correct and capped below the notify threshold (`ANOMALY_QUERY_DURATION` 0.72, `ANOMALY_BATCH_REQUESTS` 1.0, `ANOMALY_CPU_SPIKE` 0.56, against 1.5), the finding that DID clear it keys off Query Store data that had not landed yet (~28 minutes), and no alert family covers the shape - `long_running_query` triggers at 30 minutes and the victims died at 30 seconds, `poison_wait` does not class PAGEIOLATCH, CPU stayed near 50%. So the tool watched an outage it could describe and could not report. **Same-statement pileup** is a new analysis finding evaluated on the COLLECTION cadence rather than the 30-minute analysis interval, which is the entire point: N concurrent sessions on one statement, every copy past ten seconds, at least one on an IO-class wait, where that statement's own snapshots over the prior 45 minutes were sub-second. Severity scales with concurrent sessions x elapsed (the magnitude principle, not presence), calibrated so the measured incident scores 2.08 before the band cap against the 1.5 gate while a three-session pileup at the ten-second floor scores 0.75 - a visible, drill-downable finding that does not page - and a two-session pileup produces no finding at any duration, because a coincidentally-slow pair is not a shared plan flipping. The thresholds are derived from fleet distributions (four production servers, 24 hours, ~4,160 snapshot instants: 484 same-statement groups at two or more concurrent sessions, 103 at three or more, and exactly FOUR at three-or-more with every session past ten seconds - three of which are routine batch shapes that fail the IO-wait and baseline gates, and the fourth is this incident). It is computed from the active-query snapshot collector ALONE, and that is a requirement rather than a convenience: on deployments where the Query Store readers are deliberately disabled ([#2296]) a Query-Store-keyed baseline or fingerprint would ship blind on exactly the servers that needed it, so a source census holds the detector and both editions' readers to that one table. Episodes of the same statement carry one incident fingerprint, so the recurrence that re-drew the same bad plan later the same evening folds onto the first episode's trail as an occurrence instead of arriving as a fresh surprise - the drill-down an operator wants when deciding whether the plan deserves forcing, and a stable trigger token for the force-plan bot ([#2138]). Both editions ship it: the finding rides the existing analysis-finding machinery end to end (the mute registry, occurrence folding, `notify_severity`, the incident-keyed cooldown and its worsening rule), so it adds no delivery semantics of its own and the master switch gates it exactly like every sibling ([#3464]'s census counts the two new paths). Detection latency for the measured incident: inside one collection cycle of the snapshot that proved it, against 21 minutes for the capped anomalies and ~28 for the Query-Store-fed confirmation.
- **A mute rule that has outlived its reason now reports itself** ([#3306]) - a mute is a deliberate blind spot in a monitoring tool, and nothing surfaced that one existed, how old it was, or whether it would ever expire; the only way to find one was to already suspect it and call `get_mute_rules`. So a rule created to stop a false-positive flood keeps suppressing the alert after the fix ships, and the symptom is silence rather than a number going the wrong way - the Retention Held pattern one surface over, and harder to notice for exactly that reason. A new fleet-level service self-alert reports a rule that is enabled, has no expiry, and was created longer ago than the longest expiry the mute dialog itself offers, judged on that conjunction rather than on permanence alone, which the dialog offers on purpose. Severity follows blast radius: a rule that constrains nothing suppresses EVERY alert on the store, so the fleet reads healthy for want of anything being reported, and that reads Critical. Nothing is un-muted automatically - a silent expiry floods the delivery channel the rule was usually created to protect - so the alert states the rules, their ages and their reasons and leaves the decision with the operator, while the triage link drills straight into the rule list and the week of alert history a muted alert is still recorded in. No blanket mute can suppress it: a rule that constrains nothing matches every alert including this one, so honouring such a mute would let the condition suppress the only report of its own subject. It re-states itself once a day rather than on the shared alert cooldown, which on the shipped defaults would have posted every fifteen minutes about a fact that changes on a scale of days.
- **Non-interactive Microsoft Entra auth for headless targets: Service Principal and Managed Identity** ([#3484]) - the headless collector connected with Windows or SQL authentication only, and every Microsoft Entra mode was refused with one message on the reasoning that interactive MFA is nonsensical unattended - which swept in the two modes that are NOT interactive and are exactly right for a 24/7 service. A monitored target can now authenticate as an Entra **service principal** (application/client id + client secret) or a **managed identity** (system- or user-assigned), across both onboarding paths: darling.json and the `add_servers` MCP tool. The service principal reuses the existing credential shape - the client id travels as the username and the client secret as the password, DPAPI-encrypted at rest exactly like a SQL password - so it needed no new config field, no new store column, and no migration; managed identity carries no secret at all. The connection-string mapping mirrors Lite's, which has shipped these modes on the desktop for releases. The interactive Entra modes (MFA, device-code, default-credential) stay refused, with a message that now names the two supported ones, because they genuinely cannot run without a broker or a signed-in user. The Viewer's add-server dialogs offer the two modes too ([#3485]): both the single Add and the bulk Add-multiple dialogs now write Service Principal (application/client id + client secret) and Managed Identity, with the client secret stored the same DPAPI way as a SQL password and the interactive Entra modes still blocked at the whitelist - so the feature ships end to end, headless paths and GUI together.
- **User-authored custom alert rules** ([#3285]) - a threshold alert on any compose-catalog measure, the companion to the custom notebooks: choose a source, measure, aggregate and window, a comparison with Warning/Critical thresholds or a range (within or outside a band, with an optional Critical tier), N-sample hysteresis and a scope of all servers, a chosen few, or a fleet tag (and its sub-tags), and the service evaluates it on its own sweep and delivers through the existing plumbing (cooldown, mute rules, Summary/per-event, email and webhooks) - for SQL Server and PostgreSQL metrics alike. Rules are authored over MCP (`create_custom_alert_rule` / `update` / `delete` / `get` / `list` / `validate_custom_alert_rule`, plus `test_custom_alert_rule` to see a rule's current value and would-fire verdict on each in-scope server without delivering, and `list_custom_alert_templates` for a starter set covering common PostgreSQL and SQL Server signals such as autovacuum backlog, replication lag, connection saturation and blocking); the compose catalog gained the PostgreSQL measures for all 20 PG collector tables, gated so a measure only offers on the server types that collect it, which makes PostgreSQL targets both alertable and chartable. Notifications show the rule's name rather than an internal id; a rule that no longer compiles or can never fire (scoped to no monitored server, or an always-NULL measure) is surfaced as one aggregated service self-health alert; and disabling or deleting a rule force-resolves any open incident. This release ships the evaluation engine, the MCP authoring surface, and a visual web editor in the viewer (the Scalar compose picker with inline validation, a live per-server would-fire preview, start-from-template, and a "create alert from this panel" action); the rule list shows when each rule last fired.

### Changed

- **The `fanout` block publishes the slowest item's share of the pass - the verdict `dominance` was being read as** ([#3502]) - `get_collection_health`'s per-collector `fanout` block published `dominance` - slowest_ms x items / run_ms, the slowest item against the MEAN item - and the tool description told readers to take the width-versus-concentration decision on it: near 1.0 the cost is width, "around 2.0 or above one database dominates". That reading is numerically wrong at width, because the ratio's ceiling is `items`: at 72 databases, even a dominance of 10 is one database holding 14% of a pass. A user's evidence on [#3477] proved it in the most instructive way possible - their two instances score dominance 3.58 (72 items) and 4.20 (15 items), near-neighbour scores the guidance calls the same shape, whose slowest items' shares of their passes are 4.97% and 27.98% - 5.6x apart, wanting opposite remedies. The block now publishes `slowest_share_pct` - slowest_ms / run_ms, which is dominance / items - the one-division-away number the remediation decision actually turns on: a low share means the cost is the fan-out's WIDTH and bounded parallelism is the lever, a high share means one database dominates the pass and a per-database schedule override or a stagger reaches exactly it. `dominance` stays for continuity - it is not wrong, it is just not a verdict; it still answers how EVEN the fan-out is - and both SKUs' tool descriptions now route the decision through the share, carrying the two-instance counter-example as the permanent warning label. The share is DERIVED from dominance (share = dominance / items) rather than recomputed from the columns, so the two figures can never drift apart or describe different runs, and it is null exactly when the `fanout` block is null - never a 0% that would read as "perfectly even" on a run that reported nothing. No schema change: the three stored columns already carry everything the share needs. The derivation, the counter-example, and the "publish the number the decision turns on" framing are the [#3477] reporter's, verbatim from their evidence comment.

- **The same-statement pileup is scoped to the database whose plan it is** ([#3474]) - the review on [#3469] asked the question the merge had defaulted: the pileup detector grouped concurrent sessions by `query_hash` alone, and `query_hash` is not database-scoped - on a fleet of identical tenant schemas, textually-identical SQL in different databases shares a hash by construction - while a SQL Server compiled-plan cache entry IS keyed per database, so the causal story the finding tells (one shared parameterized plan flipped, every caller of that one plan convoyed) is only strictly true within one. The store's own snapshots answered the question that decided the shape: the measured incident's three convoy sessions all ran in ONE tenant database - the "ten tenants" of the incident narrative are application-level tenants inside it, sharing exactly one parameterized plan - so per-database scoping preserves the motivating incident intact, and the conflation the review predicted turned out to be measured rather than hypothetical: within the same hour as the incident, the same statement text ran 9.7 s with 7.4M reads in a DIFFERENT tenant database on the same server, one snapshot's timing away from joining the incident's pack and repricing its severity with a session that never touched its plan. The group key is now `(database, statement identity)`, and the "normally sub-second" baseline reads only the same database's history, closing both pollution directions: another database's fast history cannot vouch for a statement that is new-and-slow where it actually runs, and another database's unrelated slow occurrence cannot suppress a real pileup - the direction that fails quiet. The evidence pull also surfaced a wrinkle neither option in the issue had named: the DMV sometimes attributes a copy's database context to `tempdb` - a 16.5 s copy of the incident statement was recorded there the day before, because the DMV's `database_id` is the session's execution context, that session's context WAS tempdb, and the statement reached the tenant tables by three-part names (joining a `#temp` table moves nothing). That strengthens the shipped rule rather than complicating it: compiled-plan cache entries are keyed by the context database's dbid, so tempdb-context copies genuinely share a tempdb-keyed plan among themselves, and their own `(tempdb, statement)` group with a baseline drawn only from tempdb-attributed history is correct plan-cache semantics, not merely honesty about what the DMV said. Reattribution to the "real" tenant database is deliberately not attempted - a reattributed row would blame a plan that is not the one convoying, and would plant multi-second rows in another database's history, poisoning exactly the per-database baseline this change exists to keep clean. The evidence pack's database attribution is now structural rather than picked: the finding's database is the group key's database, where the previous first-non-empty pick over the pack was nondeterministic for a multi-database pack - and `ComputeIncidentId` folds on that name, so the same recurring pileup could land on different incident ids across evaluations, undermining the occurrence folding the detector was built around and the stable trigger token the force-plan bot ([#2138]) wants. The calibration carries over without a re-pull, by argument rather than assertion: per-database scoping PARTITIONS the server-wide groups and can never grow one, so every gate becomes strictly harder to pass and the four-instants-in-four-server-days derivation stays conservative under the new predicate; the measured incident was single-database, so its group, its 2.08 severity, and its notify margin are unchanged.
- **A server's deadlock health band reads a RATE, not a raw count** ([#3368]) - `ServerHealthClassifier.DeadlockSeverity` was `count > 0 ? Critical : Healthy`, and `OverallMetricSeverity` short-circuits on the first Critical, so one resolved deadlock anywhere in the window banded a server Critical whatever else it looked like - making the band's most common cause the one condition that had already resolved itself. It bands deadlocks per HOUR now, normalised over the window the count covers, so one pair of thresholds means the same condition on a 1-hour read and a 24-hour one. Measured on a 43-server production OLTP fleet, the count band read 13.4% of one-hour windows Critical and 87.9% of 24-hour windows Critical - the same servers and the same code, a 6.5x swing from window length alone. Defaults are 5 per hour (Warning) and 20 per hour (Critical), derived from 14 days of collected deadlocks across those servers rather than chosen as round numbers: 99.1% of server-hours hold at most two, the routine mode tops out at 15 in an hour, and nothing at all was observed between 16 and 89 - so the Critical tier sits inside a measured empty interval. Both are store-backed knobs on `config_alert_settings` (V120), reported and accepted by `get_alert_settings` / `update_alert_settings` under a new `health_bands` group and editable in the Viewer's Settings window, clamped to 1-1000 per hour - the floor keeps the knob a rate, so no reachable setting restores the count band. The `health_bands` group is deliberately separate from `deadlocks`: that one governs whether an alert is DELIVERED, these decide what a card reads and how `get_fleet_overview` counts bands, and nesting a band tier under the alert would invite tuning one and expecting the other to move. A window too short to normalise is not banded on a rate at all - a non-zero count reads Warning and a zero count reads Unknown, so an absent denominator can never read as healthy. A target with no deadlock source reports Unknown for the severity AND null for the rate, both derived from the same reading, so a PostgreSQL card cannot publish a per-hour figure its own severity denies. Both cards publish the rate beside the count and name it in the "needs attention" reason.

- **The alerting layer's recent-runs read no longer sorts a server's whole retention history to return ten rows** ([#3496]) - the alert pass's own store reads on the biggest production store class began failing in slow-rising numbers as the 90-day retention horizon filled: swallowed read failures climbed 13 → 31 over twelve hours on the 43-server store while its two same-class controls sat at 3 and 0, each failure a read clocking ~12 seconds against the pass's 10-second command deadline - a deadline derived from a measured 1,744.9 ms worst case when the store was young. Degradation rather than outage (31 swallowed among ~1,600 clean passes, live pages delivering throughout), but the trend line only pointed one way. The root cause was measured live: `ReadCollectionSignalsAsync` asked `collection_log` - a time-partitioned hypertable, 16.4M rows, 32 chunks, compressed history - for a server's recent runs with `ORDER BY log_id DESC LIMIT $2`, and `log_id` is not the partition column and appears in no index, so the planner's only legal plan appended all 32 chunks - decompressing the columnar history - into a top-N heapsort of ~389,000 rows to return ten, twice per statement (the status twin repeats the shape), every alert pass, every 30 seconds, per server. It presented as a tail-only slow burn because the statement self-warms: the hot mean sat near 221 ms, and only the cold/contended excursions crossed the deadline - which is exactly a margin being eaten, not a margin already gone. The conviction and the fix rode the same `EXPLAIN`: the statement's own `MAX(collection_time)` arm - same table, same `server_id` predicate - resolved in **0.097 ms**, because its sort key is chunk-orderable, so ChunkAppend stopped at the newest chunk and 30 of 32 chunks reported "never executed"; three orders of magnitude on the same table and predicate, the fix's efficacy measured before the fix existed. The recent-N subqueries now order by `collection_time DESC, log_id DESC` - semantics-identical, because a server's id order and its time order agree (the id generator is a process-monotonic counter re-seeded forward from the clock across restarts) and the id stays in the ORDER BY as the deterministic tiebreak within one collection instant - and horizon-INDEPENDENT, which is what makes this a fix rather than a reprieve: ChunkAppend stops at the newest chunks however many chunks the retention horizon accumulates, so extending the horizon cannot regress the read back over the deadline. Verified against a real TimescaleDB with compressed chunks before shipping, because the plan had to show the early stop and not merely a faster wall clock: on a 37-chunk harness table (33 compressed, ~104K rows per server), the old shape executed every chunk and read the server's whole population into per-chunk top-N sorts while the new shape's ChunkAppend left 36 of 37 chunks never executed and read 1,252 rows - the newest chunk's worth, an 82x collapse whose bound is chunk width rather than history length - with both orderings returning identical rows in identical order across every server and window tested, ties included. The `MAX(collection_time)` arm is deliberately untouched - it is the measured control, and its one residual (a server whose newest qualifying row is ancient walks deeper before stopping) is the rare case and the right cost to pay exactly then. The ordering is pinned at the source so a future editor cannot quietly revert to id-first - the regression is silent on any store small enough to test against, which is how it shipped the first time - and the gated live suite gains the ordering arm: newest-instant-first fill with the highest ids winning inside a tied instant.

Teams, Slack, PagerDuty, the generic webhook and email now render only the incidents actually outside their own window, with a one-line footer stating how many others are still open. The alert history row continues to record every incident, so nothing the MCP reader, the triage page, the Viewer's detail pane or the mute pre-fill reads has changed. Per-event delivery already sent one incident per message and is unchanged. PagerDuty's `dedup_key` now anchors on the first DELIVERABLE incident, which corrects a correlation defect: a batch of one in-window and one fresh incident previously triggered under the in-window incident's key and folded into its existing alert, so the genuinely new incident never surfaced there at all.
- **A Collector Cost Regression self-alert now has to be worth reporting, not merely real** ([#3316]) - the predicate floored the average daily TOTAL cost and then compared cost PER RUN, and a total-cost floor is cleared by volume, so it never constrained the quantity the ratio tested: a collector averaging 3 ms per run cleared the 1,000 ms/day floor on run count alone and was then judged by a 2x ratio on that 3 ms. Those firings were truthful rather than noisy - both sides of the ratio are means over many runs, so rounding averages out - and still unactionable, the measured case doubling 3.0 to 6.1 ms per run across 50 runs to add 0.16 s of collection time a day. A third gate now asks what the regression COSTS, the per-run rise times the volume it is paid on, which is unit-consistent with the ratio and unlike a minimum per-run baseline still reports a 3 ms collector that runs often enough for the rise to matter. The floor is derived from a measured fleet sample where real regressions added 21.8-22.6 s a day and unactionable ones 0.16-3.6 s, and the alert now states the added cost that justified it.
- **Analysis-finding alerts no longer render their Diagnosis facts twice on every delivery channel** ([#3302]) - the finding's prose detail restates its own structured context under different labels, so the delivery gate's equality test could not see the duplication: a restatement is not a copy. The producer now DECLARES whether its prose restates its context, and the analysis path declares that it does, so the facts go out once - while a producer whose prose is genuinely its own, such as a remediation string the context does not carry, still delivers it. That declaration is a required member rather than a defaulted one, so a new producer cannot omit it silently, and where it is defaulted it defaults to DELIVERING: a redundant paragraph is cosmetic, while a withheld one discards an operator's only copy of the remedy. `config_alert_log.detail_text` is unchanged, so the MCP reader, the triage page, the Viewer's detail pane and the mute pre-fill all read what they always did.
- **A deadlock or blocked-process report whose statement sat inside a stored procedure now names the procedure** ([#3307]) - SQL Server emits an unresolved `Proc [Database Id = N Object Id = M]` placeholder in `inputbuf`, and neither collector attempted to resolve it, so the alert named the object the deadlock fought over but not the code that lost. Both collectors now resolve it to `database.schema.object` with one batched lookup per collection cycle - three-part, matching how `Involved Objects` already qualifies names - and keep the raw placeholder when the object has been dropped or the monitoring login cannot see its database, so a failed lookup degrades to today's output rather than to a half-built name. The parse and the lookup are C#-side: the XML shredding the resolution hangs off already happens locally, and the monitored server is asked only for an object name.
- **The installer and the portable launcher are signed, and a release-time guard refuses to publish an unsigned executable anywhere else** ([#3288]) - the portable launcher stub, `Update.exe` and `Setup.exe` shipped unsigned on both products while the app payload was signed, so the file a user double-clicks in the portable zip was a 399 kB unsigned launcher rather than the signed 182 kB app - which is exactly what an "unknown publisher" policy blocks, and what forces the elevation that breaks Entra MFA in #3196. Velopack creates those three during packing, so no pre-pack round reaches them, and SignPath's open-source policy requires origin verification through a trusted build system - a signing request is accepted only through the GitHub Action, which cannot be invoked from inside a running `vpk pack`. So the standalone assets are signed by an Action step AFTER packing: `Setup.exe`, and the root launcher and `Update.exe` inside `Portable.zip`. Neither carries a recorded hash - `releases.<channel>.json` records a SHA256 and a Size for the two `.nupkg` files and nothing else - so rewriting them invalidates nothing, and the portable zip is rebuilt member by member with every unchanged entry's local header, name and raw compressed bytes copied verbatim, verified against a snapshot of the original before it replaces it. **Two executables are still unsigned, and only inside the `.nupkg`**: `lib/app/<App>_ExecutionStub.exe` and `lib/app/Squirrel.exe`, because that package's bytes are what the updater verifies and what the delta patches against. Their deployed copies in `Portable.zip` ARE signed; the copies `Setup.exe` lays down are not, so an installed user's shortcut target and updater remain unsigned. The release guard walks every published `.exe` including those inside the zips and packages, exempts exactly those two by member path AND container so the same names anywhere else still fail, reports each exemption's reason, and treats an empty census as a failure rather than a pass.
- **PostgreSQL instance CPU bands on Aurora Serverless v2 capacity headroom, not on percent-of-allocated** ([#3281]) - `os.cpuUtilization.total.avg` is percent of the capacity CURRENTLY ALLOCATED, and a serverless instance class re-sizes that allocation continuously - so a 1-vCPU instance reads exactly 100% whenever one core is busy for a minute, which is the routine trigger for scaling up rather than a saturation incident. Measured on a production instance at such a minute: 4 of 12 configured ACUs in use, 33% of the ceiling, while CPU read 100% with idle at 0.0. `RdsCpuIngestor` now collects `os.general.acuUtilization.avg`, `os.general.serverlessDatabaseCapacity.avg` and `os.general.maxConfiguredAcu.avg` on the Performance Insights call it already made, with a single retry on the CPU metric alone if the service rejects the request shape - so an instance class with no ACU concept loses the capacity columns rather than its CPU reading. The fleet card ladder and the High CPU alert both band on percent of the CONFIGURED ceiling, and where no capacity reading exists the band is Unknown rather than Healthy and the alert does not fire. The raw CPU figure stays collected and displayed - it answers "was a core pinned" - labelled with what it is a fraction of, and `get_pg_cpu_utilization` no longer describes the reading as capacity-independent.
- **`get_pg_index_bloat` now carries its own coverage denominator, so a limited page cannot read as a coverage claim** ([#3278]) - the read sorts answerless rows first by design, so any limit below the answerless population returned 100% of them, and nothing distinguished "the collector estimated nothing" from "it covers plenty, sorted behind more numerous skips". It now returns a population-level census from a separate query no row limit can reach - candidate btree indexes, trusted against suppressed, and each suppression reason - with BYTES beside every count, because the row and byte rankings of those reasons disagree: one bucket measured second-largest by rows and last by footprint, at 0.0004% of it. The candidate total is derived from its parts, so the published total cannot disagree with the breakdown explaining it. Shipped on the MCP tool, the WPF storage panel and the web dashboard through one classifier.
