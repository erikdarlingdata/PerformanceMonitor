## [3.11.0] - 2026-10-22

### Important

- **Upgrading from 3.10 runs the Darling store migrations V174 through V210 on the service's first start** - the store schema goes from 173 to 210. Almost all of it is new tables that start empty or new nullable or constant-default columns, which PostgreSQL adds without rewriting the table: the service version table (V174), the Client Timeouts alert's attention events (V179), per-collection procedure totals (V176), Query Store watermarks (V178), an hourly collection log rollup (V186) and a failure record for the Query Store builder (V189), an estimated-size flag on the store metrics (V190), the alert settings for the Runnable Queue alert, the Volume Free Space excluded volumes list and the Query Store fetch limit (V177, V200, V209), the tables for alerts raised by other services (V180), a route's server or tag scope and its resolution flags (V181, V187), the read record's window band, in-flight and caller columns (V182, V183), the investigation, Level 2, Level 3, evidence, follow-up and signed webhook tables and columns (V184, V188, V191, V193, V196, V197), the query tag tables (V192, V194), forced plan collection (V195, V201), the head blocker's evidence columns on the blocking snapshots (V199), the Availability Group primary replica column (V202), the hypothetical index login (V203), folders and owners on custom views (V204), an expiry on custom alert rules (V205), a start time on mute rules (V208), the pseudonym key (V198, seeded once with a random value) and a trigger that stops MCP tag writes from changing which servers an agent route covers (V210). None of them rewrites a large table or needs an offline window. The ones that read or change existing rows are small: V175 adds the plan regression day column and marks every built day stale, one row per server and day, so a day reads from the interval table until the hourly builder refills it; V182 replaces the primary key of the hourly read record table; V206 makes the collector schedule's enabled column optional, merges rows whose collector names differ only by case, deletes rows whose name is not 1 to 64 lowercase letters, digits or underscores, and caps a frequency above 525,600 minutes and a retention above 3,650 days. V175 needs an exclusive lock on the plan regression day table for its new column and sets a lock timeout for it.

- **Upgrading Lite from 3.10 moves its DuckDB schema from version 67 to 77 on the first start** - every step adds: the Client Timeouts mute rule match column (v68), the notification routes table and the Level 1 investigation tables (v69), the query tag tables (v70), the investigation evidence table and the new investigation request and report columns (v72 to v75), the head blocker's evidence columns on the blocking snapshots (v76) and the Availability Group primary replica column (v77). The one step that discards rows is v71: it drops and recreates the query tag sightings table so the database joins its key, and the collectors refill it on their next rounds. If the v71 step fails, the schema version stays at 70 and the step retries on the next start. None of them rewrites a large table or needs an offline window.

- **Self-managed stores: re-run `provision-roles.sql` after upgrading** ([#6066]) - The pseudonym key table's revoke and the owner-only trigger sweep apply only after the script runs again. The migration already revokes the key table from `PUBLIC` and from the three roles that exist.

### Added

- **Investigations panel in the Darling viewer and Lite** ([#5907]) - the Darling web viewer gets an Investigations page, and Lite gets an Investigations window (sidebar button), both read-only: agent investigation requests by state and family (opened, server, metric, family, agent, lease, reported, route) and, for a picked request, its reports, stored brief and journal. In Lite the reports, brief and journal text are masked at the level the MCP investigation tools serve.

- **Agent notes can be approved or rejected in the Darling web dashboard and in Lite** ([#5908]) - A note an agent proposes with its investigation report waited as pending with no way to approve it, so no brief ever carried one. The Darling web dashboard's Admin page has a Pending Notes tab (server, metric, family, the proposed text, the agent and the request) with Approve and Reject, and Lite has an Agent Notes screen under Settings (Review Agent Notes) over its local database. An approved note goes into later briefs; a rejected note is kept with who decided and when, and never reaches a brief. Each decision is stamped with the person and the time and journaled. On Darling, managed and compose stores connect the web dashboard as the viewer role, which can list notes but cannot decide them, so there the page says to decide in the desktop Viewer or to set postgres.webConnectionString to an admin login. Lite stays advise-only for agents: a person decides notes, and the note text can't be edited.

- **A new Darling MCP tool, `backtest_custom_alert_rule`, shows where a custom alert rule would have fired and cleared over stored history** ([#5919]) - there was no way to see how often a rule would fire before saving or changing it: `test_custom_alert_rule` reads only the current value and skips the breach and clear samples. The new tool replays a saved rule or a draft definition over up to 7 days (default 24 hours) on up to 10 servers. At each step it reads the rule's own panel as of that step and applies the same breach and clear samples the live engine applies, so the fire and clear points match what the live engine would do on the same samples. It writes and sends nothing. One call runs at most 2,880 queries and 60 seconds, and a call a cap stops answers `partial` with `stopped_at` and what it covered. A server with no stored samples answers `unavailable`, never 0 fires. The MCP catalog grows from 187 to 188 tools.

- **Store schema for Level 2 agent investigations** ([#5920]) - the store gains the tables and columns Level 2 needs, in one migration (store schema version 191). A notification route may now be set to agent level 2 (0 to 2) and an investigation request may carry autonomy level 2; any level outside the range is still refused. `config_service` gets an `agent_actions_enabled` switch that reads as on on a new and an upgraded store. A new `config_threshold_overrides` table holds per-server, per-database threshold overrides, is deleted with its server and bumps the `config_version` reload beacon on every change. A new `investigation_feedback` table holds a person's verdict (right, partly or wrong), corrected verdict, missed step and comment on a report, one per request per author, and goes with its request. Investigation requests gain a nullable `practice_of` column with no foreign key. The admin role can write both new tables, the viewer role can only read them, and the mcp role can write the overrides table and read feedback, in both the managed roles and `provision-roles.sql` (a bring-your-own store needs the script re-run after upgrading). Retention needs no new pass: feedback ages with its request and overrides are never aged. Nothing reads or writes the new tables yet; later Phase B slices do.

- **The alert engine can take per-server and per-database threshold overrides** ([#5921]) - the engine read every alert threshold as one global value, so a threshold could not be tuned for one server. Each tunable integer threshold now has a registered key and a scope (server, or server and database), and the engine reads every one of them through an optional overrides object. The version store (PVS) percent and floor and the file growth rise and level bars can also take a per-database value, because those alerts grade each database on its own. Nothing supplies overrides yet: Lite passes none and Darling passes none until a later release adds the store-backed overrides, so every alert behaves exactly as before.

- **Investigation reports can record Jira, pull request and bug report links** ([#5922]) - An agent's report may carry up to 10 links, which must be https with no user name or password (http, file and UNC links are refused, and are checked again whenever a link is shown). Later briefs for the same server and alert family list the last 30 days of links, and the viewer and web dashboard show a report's links.

- **The Level 2 agent action gate and its journal** ([#5925]) - Darling now has the one gate every Level 2 agent change will go through: a live claim on the request, the request's server only, a reason and evidence, with each refusal journaled at most once an hour and each change journaled before and after with its evidence masked at `mcp.dataDetail`. Requests now record the lowest agent level among their routes, and an alert from a custom rule an agent last wrote stays at Level 1.

- **People can give feedback on investigation reports** ([#5926]) - A report can be marked right, partly right or wrong, with a corrected verdict, the step the agent missed and a comment, from the Viewer's Investigations window (Report Feedback tab, admin login) or the web Admin page's new Report Feedback tab (recorded only under an admin store login; list-only otherwise). `get_investigation_reports` now returns each report's feedback and, per alert family, how many investigations ended as false positives before and after people's corrections.

- **Lite: Level 1 agent investigations** ([#5820]) - when an alert fires on a notification route whose agent level is 1, Lite opens an investigation request for it, and when `mcp_allow_investigations` is on with MCP writes off it serves four tools (`list_investigation_requests`, `claim_investigation_request`, `submit_investigation_report`, `get_investigation_reports`) so a local agent can claim the request, read its brief, and file a report that Lite keeps beside the alert. Requests, reports, notes and the journal live in Lite's own DuckDB file; nothing writes to a monitored server; with both MCP settings on the investigation tools stay off and Lite logs one Critical line saying so.

- **Deadlock graph window: a visible Copy button for the SQL text** ([#5663]) - the only ways to copy a process's SQL text were the right-click "Copy SQL Text" menu item or selecting the text box and pressing Ctrl+C, and the menu was easy to miss. The Properties panel now has a Copy button on the same row as the "SQL Text" heading, in Lite and the Darling viewer. It copies the same full SQL text as the menu item, through the same code, and is only shown when the process has SQL text.

- **A Runnable Queue alert warns when runnable tasks per scheduler stay high** ([#5641]) - no alert read scheduler queue depth, so a CPU-bound server could time out clients minutes before High CPU fired. It reads the stored runnable-tasks-per-scheduler values one collection at a time (a collection the collector split across several rows is summed, not averaged row by row), averages the collections of the last 5 minutes when there are at least 3, and when the collector runs late falls back to the newest 3 collections if all are within 10 minutes (within 4 times the recent gap between collections when collection is slower, so the Low-Impact preset's 5-minute collection still evaluates). A standing Runnable Queue alert resolves, with that reason in the notice, when 30 minutes pass without an evaluated reading (the 30 minutes count from the last evaluated reading, and a read that is not an observation never restarts the count). It alerts Warning at 8 and Critical at 16 by default, with the usual cooldown, mute and cleared notice. The alert card also shows the CPU for the same minutes and the heaviest requests by CPU in the newest query snapshot ("at least N more" when the read hit its 50-row cap). Both bars and an on/off switch are settings (Lite and Darling Settings windows, `get_alert_settings` in both apps, Darling `update_alert_settings`), and the metric can be muted from either mute dialog.

- **Mute rules can match by client application** ([#5714])- a mute rule now has an optional "Client application (substring)" match, set in the Lite and viewer mute dialogs, on the web Mute Rules page and through `create_mute_rule` / `update_mute_rule`, so cancels from one tool (for example SSMS) can be muted without muting an application's own timeouts. A rule that names a client application never mutes an alert that has none.

- **Other services can raise alerts through Darling** ([#5726]) - A second service can now raise alerts that go through Darling's notification channels, routes and mute rules, each with its own database login. The store gets the source, queue and firing-state tables and the mute-rule `external_source` column (schema version 180), a submission function that each source login calls with only its EXECUTE grant, delivery of the queued alerts, and CLI verbs to add, rotate, list and remove sources; a mute rule can name an external source in the Darling MCP tools (`get_mute_rules`, `create_mute_rule`, `update_mute_rule`, `get_alert_history`) and on the web Mute Rules page.

- **Enter opens a server tab** ([#5764]) - In Lite and the Darling viewer, pressing Enter on a selected server in the server list opens its tab, and the selection stays put when the list refreshes.

- **Darling records the collection slots it stepped over** ([#5741]) - when a server's collection falls behind (a body that ran long, a wait for a fleet slot, the memory launch guard's hold, or a lost daily run), Darling now writes one `collection_cycle` row to the collection log per server, at most every 5 minutes, with the slot count, the cause and both ends of the gap (a row with no measured cause leaves its duration empty). Collection health, "last collected", Collection Stopped and the other log readers leave the row out, so it cannot hide an outage or inflate a count. A computer that slept or a paused service writes no row. Collection health now shows the late slots: a `skipped_cycles` block in `get_collection_health` (status "unavailable" with empty figures if its read fails, the rest of the answer unaffected), a Skipped Cycles panel on the web Collection Health tab, and a line on the Viewer's Collection Health tab. `get_collection_log` counts the collection_cycle rows in a new `skipped_cycle_rows` and leaves them out of `run_count`, in the per-server and fleet forms, as Lite's does. Lite's `skipped_cycles` block now carries the same `status` ("ok", or "unavailable" with empty figures if its read fails), so one failed read no longer fails `get_collection_health` in Lite either.

- **Darling warns at start when the store was migrated by a newer build** ([#5773]) - An older build started against a newer store now logs one warning at start that names the migrations it does not know and keeps running, and Darling/README.md's new "Rolling back to an older build" section explains that a rollback keeps the store and holds the list of migrations that change what an older build reads, empty so far.

- **A notification route can be limited to one server or to a tag, in Lite and Darling** ([#5769]) - A route used to match an alert by metric name or family only, so every server sent its alerts to the same webhook. A route can now be set for one server, or for a tag and every tag below it. One server or one group of servers can then post to its own channel. When more than one route fits an alert, a route for that server wins. Next comes a route for a tag the server is under (the deeper tag wins). A route for all servers comes last. Inside each of these, the order is the exact metric name, then its family, then the new "every metric (*)" match. The "every metric" match is allowed only on a route that has a server or a tag. As before, a route replaces only the channels it sets. Generic headers and the body template stay shared by all routes. Lite now has notification routes for the first time: use Settings > Manage Notification Routes. Lite keeps each route's webhook URLs and PagerDuty key in Windows Credential Manager, not in its database. A URL can be up to 1,280 characters long. The window refuses changes while a saved-settings restore is pending. The Darling viewer's routes window has the same "Applies to" choice and shows each route's scope and status. The Darling web dashboard's Routes list shows the same scope and status, read-only. A route whose server or tag is deleted is not removed. It is marked as orphaned and matches nothing, so a deleted scope never turns the route into an all-servers route. In both products, `get_notification_routes` now shows the scope, its name, how many servers it covers now, and whether it is orphaned. It never shows a URL or key. Lite also serves `set_notification_route_enabled` and `delete_notification_route`, but only when `mcp_allow_writes` is true. If you provisioned your Darling store yourself, run `tools/provision-roles.sql` again after the upgrade. Then the viewer and MCP roles can read the two new scope columns.

- **Read latency capacity fields** ([#5792]) - Darling now records, for every web, composed-panel and MCP read, the width of the window it asked for (1h, 24h, 7d, 7d+ or none), how many other reads were running when it started, and how long it waited for a store connection, and `get_read_latency` and `get_slow_reads` return them.

- **Read caller** ([#5795]) - Slow reads now record who made them (an MCP client's name and version, or a salted hash of the web session) and the hourly read-latency rows count distinct callers, with no personal data stored. The web dashboard shows the caller in the slow-reads grid and gives read latency a grid of its own.

- **A store sizing guide for Darling, and a load-test harness for the Query Store tables** ([#5800]) - The new guide gives the measured size per monitored server for SQL Server with and without Query Store and for PostgreSQL, the retention horizons behind those numbers, and host sizes (vCPUs, RAM, disk) by server count up to 150 servers. `Darling/loadtest/` adds scripts and a runbook that raise a restored store's Query Store interval data N times and measure the reads, the hourly work and the writes at each N. The service log line of each of the three hourly Query Store builders now ends with the time it took, in ms.

- **Darling limits how many long reads run at once** ([#5806]) - on 2026-10-02 one MCP client held the store's disk at its limit for about 5 minutes. The service now runs at most 2 long reads at a time (`reads.maxHeavyReads` in darling.json, 0 for no limit). A read is long when its route took 2 seconds or more at that window size. Up to 16 more wait for up to 45 seconds. After that, a read gets `busy` on MCP, or HTTP 429 on the web. Short reads never wait. An identical read in the next 15 to 120 seconds comes from memory. `get_read_latency` and its web grid show queued, refused and cancelled reads, and count each store read once, joined callers apart.

- **Darling can hand an alert to your own AI agent** ([#5632]) - a notification route can now be set to Investigate, so the alerts it matches, and the analysis findings that page, open investigation requests for an agent you run. Darling opens one request per server and alert family, and the alerts of that server and family within 30 minutes join it while the request is open or claimed, up to a limit per route per hour (20 by default) and per day (100 by default). Your agent works through four MCP tools: `list_investigation_requests`, `claim_investigation_request`, `submit_investigation_report` and `get_investigation_reports`. The claim and the report are served only when you set `mcp.allowInvestigations` with a bearer token, while `mcp.allowWrites` is off. A claim returns a brief: the alerts, the analysis findings, earlier reports, recent changes, approved notes about the server, your environment profile and the read tools to call next. The agent only reads and reports; it cannot change a monitored server. A new setting, `mcp.dataDetail`, masks statement literals (`maskLiterals`) or holds back query text, plan XML and input buffers (`metadataOnly`) in every MCP tool answer, `get_investigation_reports` included, and in the brief, and `get_mute_rules` now names each rule's match summary `match_summary`, in Darling and Lite and in the mute-rule write tools' answers. The viewer has a Manage Investigations window for requests, reports, notes and profiles, and the web alert page a read-only Investigations panel. Darling ships no agent.

- **Alert Details window: resizable, selectable values, Copy all details, and a link to the full chain** ([#5854]) - In Lite and the Darling Viewer, the Alert Details window now resizes and remembers its size. Its values can be selected and copied, and a Copy all details button copies the whole alert as plain text. Blocking and deadlock alerts get a link that opens the server's Blocked Process Reports or Deadlocks grid around the alert's time.

- **MCP long-poll: an agent waits for an investigation request to open for its routes** ([#5856]) - New MCP tool `wait_for_investigation_requests` waits up to 25 seconds for an investigation request to open on the agent routes it names, then answers each new request's id, route, server, family and open time with a cursor for the next call. The claim stays `claim_investigation_request`, and nothing is queued for an agent that is not waiting.

- **Alert resolutions go to the channels that got the fire, opt-in per channel** ([#5855]) - When an alert clears, Darling can now send that to Slack, Teams, the generic webhook and email. Each channel has a "Send resolutions" setting that is off by default, and a notification route can override it for its own destinations; the clear goes only to the destinations its delivered fire reached, a mute rule stops it, and its history row records the channels and the outcome. With PagerDuty auto-resolve on, any alert's clear now closes the incident its fire opened.

- **Generic webhook: {{investigation_json}} carries the alert's investigation request** ([#5853]) - A generic webhook body template can now include `{{investigation_json}}`, the investigation request the alert opened or joined (its id, state, lease and expiry times, the brief masked at `mcp.dataDetail`, and the MCP tool names to claim and report it), so a POST endpoint can start an agent from the alert. It is empty when the alert opened no request, and the request is now opened before the alert's channels post.

- **Lite: Level 1 agent investigations** ([#5902]) - Lite can open investigation requests from alerts, and your own agent can list, claim and report on them over MCP (four tools, served only with mcp_allow_investigations on and mcp_allow_writes off, no token), with routes, settings, data-detail masking, an instructions paragraph, a guide per tool, a docs section and a starter agent file, matching Darling.

- **Practice requests with a score per agent** ([#5937]) - Pick a case you already gave feedback on, in the Viewer's new Practice tab, and Darling replays it for an agent without the original report, verdict or comment. The agent's report is scored against your feedback (a corrected verdict, or right and partly right) and the score shows per agent in the Viewer and on the web Admin page. A practice request never joins a live alert, never counts against a route's limit, and is left out of the Report Feedback list and the per-family counts; its report is not shown to other briefs. While a practice is live, the replayed case's report is also left out of the other briefs' earlier reports and prior links, and out of get_investigation_reports for an agent on the investigations arm. The score is advisory.

- **Agents at Level 2 can change mute rules and custom alert rules, journaled** ([#5934]) - An alert route set to Act (Level 2) now lets an agent with a live claim mute one metric on the request's server and create, change, disable or delete a custom alert rule scoped to that server. Every change needs a reason and evidence, is stamped with the agent, and is journaled with the before and after rule; the service's own alerts cannot be muted and writes stop once the report is submitted. The Viewer route editor offers the Act level.

- **Per-server alert threshold overrides** ([#5933]) - Darling can hold a threshold for one server, or one database on it, that differs from the global value, so an alert that is noisy on one server can be tuned without changing every other server. It covers the integer alert thresholds and the PostgreSQL deadlock and blocking counts; set one with `set_alert_threshold_override`, and see the effective value and its source with `get_alert_settings` and `server_name`. The desktop Viewer (Settings, Alert rules) and the web Admin page (Threshold Overrides tab) show a grid of the overrides with the global value beside each; both refuse a bad key or bound, and the web accepts a change only under an admin store login (a managed or compose store connects the web dashboard read-only, so there it is a list). A Level 2 agent may change an override only for its own request's server and can never set a threshold to the value that turns its alert off (the top of the key's range, or zero for Low Disk; to silence an alert, mute it), and a bring-your-own store needs `provision-roles.sql` re-run once to grant the table.

- **Agent changes list with one-click undo and an off switch** ([#5936]) - The Viewer's Investigations window and the web Admin page have an Agent changes tab: every change an agent made, what it was refused, and calls with no known result shown as "result unknown". Undo puts a mute rule, custom alert rule or threshold override back the way it was before the agent's change, but only if nobody has changed it since (otherwise it says "changed since" and leaves it); a deleted rule comes back with its own Custom id. A switch turns every agent change off at once. The web decides only under the admin store login; on managed and compose stores it lists only.

- **CI lints the workflow files with actionlint** ([#5947]) - a pull request that changes a file under `.github/workflows/`, and every push to main or dev, now runs actionlint in the Guard tests job, so a broken expression, a `needs:` name that matches no job, or a bad action input fails at once and not when the workflow runs.

- **Test code can no longer call `Thread.Sleep`, and CI failures are counted with the skip marker apart** ([#5943]) - the test projects get `TestWait.WaitUntil` and an `AnchorClock` in place of fixed sleeps, `Thread.Sleep` is a build error in them, and a new script counts the deliberate "CI not run" marker apart from real failures.

- **CI can set aside a test that dev's own latest push broke, for up to 72 hours, on pull requests that do not reach it** ([#5942]) - a broken test on dev failed every unrelated pull request until a fix merged. A new `.github/ci-quarantine.txt` lists such a test with its dev run, time and issue; the Guard job and the shard runners leave it out only while the latest dev push run failed it and the pull request does not touch it. The file ships empty.

- **Run all collectors now, or one collector now, for a server** ([#5941]) - On a server's Collection Health tab, an editor seat now has "Run all collectors now" (every enabled collector, once) and a "Run now" button on each collector (that one, even if disabled, without changing its schedule); the MCP tool `run_collectors_now` does the same. A second request is refused while one is running, and a request within 60 seconds of the last one is refused with the time the next is allowed.

- **Client Timeouts measurement scripts** ([#5736]) - Two read-only scripts, `Darling/tools/attention-rate-measure.sql` for the PostgreSQL store and `Lite/tools/attention-rate-measure.sql` for the DuckDB store, report each server's per-minute client attention rate over the minutes the collector actually ran (minutes in span, minutes with a run, longest collection gap, attentions, p50, p99, p99.9, max and the three busiest minutes) and the fleet spread of the per-server p99.9, so the Client Timeouts alert's default bars can be set from measured data.

- **Query tags: shared rule matcher** ([#5979]) - A pure matcher in the shared library that both Darling and Lite will use to give each query key one tag, by hand assignment first and then by rules, with a record of why.

- **Query tags: store tables** ([#5977]) - Darling's store gains the tables query tags need: tags, hand assignments by query hash or object, rules, sightings, the tag map and a version row, with grants, server-removal cleanup and retention of aged sightings. Nothing reads or writes them yet.

- **Alert recurrence in investigation briefs** ([#6000]) - An investigation brief now says, for each metric linked to the request, how many times it fired and how many times it was muted within 30 minutes either side of the first alert's time of day over the previous 7 days (not counting the 30 minutes before the alert, which are the same incident), with the dates fired and the dates muted. A metric with no history says zero.

- **Query tag sightings from the collectors** ([#5980]) - The collectors that see a query hash, a procedure or a caller (active queries, long-query completions, query stats, Query Store, procedure stats, blocked process reports, DMV blocking snapshots, deadlocks, attention events and default trace events) can now describe the query keys and the application, login and host each row saw, so the tag map can be built from them in a later change. Every hash is keyed in one `0x` text, whichever collector saw it. Nothing is stored yet.

- **Query tag rule MCP tools** ([#5982]) - Darling serves `create_query_tag_rule`, `update_query_tag_rule` and `delete_query_tag_rule` (with `mcp.allowWrites` and a token) and `list_query_tag_rules` and `test_query_tag_rule`. A rule can be tested against the recent query sightings of one server or all, showing what it would tag and what a hand assignment or a higher rule already holds, before it is saved.

- **Investigation evidence, follow-ups and signed-webhook keys in the store** ([#5997]) - The Darling store gains the tables and columns that later investigation work uses: evidence per request section (cleared with the brief at 90 days), daily deadlock signature counts (kept 30 days), signature merges, report family and queries-run fields, follow-up fields, and signing keys on notification settings and routes that the read-only viewer and MCP roles cannot read.

- **Lite has a query-tag store** ([#5989]) - adds the DuckDB tables and a tag, assignment and rule store that match Darling's, kept across an archive reset and cleared when a server is removed. Nothing is shown in the UI yet.

- **Tags on the Darling query reads** ([#5984]) - Darling's top queries, top procedures, Query Store, active queries and long-query completions reads now show each row's query tag and take an optional `tag` filter that matches the tag and every tag beneath it. An unknown tag name answers empty and says so.

- **Query tag MCP tools** ([#5981]) - Six new Darling MCP tools create, edit, delete, assign, unassign and list query tags; the five writes are served only with `mcp.allowWrites`. A query can be tagged by `query_hash` or by object, for one server or every server, and a tag that has assignments, rules or child tags asks for confirmation before it is deleted.

- **Investigation reports carry a family, fix links, evidence basis and the queries run** ([#6004]) - A report can name the first report of its family (checked to exist), link a commit or a release as the fix, label each evidence item verified or inferred (served as two lists, with older evidence shown as unlabelled), and record up to 20 statements it ran, masked like any statement text. Darling reports no longer carry an `evidence` key: the evidence is served as `evidence_verified` and `evidence_inferred` (and `evidence_unlabelled` for items written before the basis was required), and a submit whose evidence items lack a `basis` is refused as `invalid`.

- **Query tag map built by the collector** ([#5985]) - Darling now records which query hashes, objects and callers each collection saw, and keeps a tag map up to date from your tag rules and hand assignments: a changed rule retags everything already seen on the next pass, and new queries are tagged as they appear. Sightings are buffered in memory and written once a minute by the map step, a query hash seen in two databases is recorded per database so a database rule matches each one, and a restarted service rebuilds its map in one pass instead of re-reading all history. Store schema version 194 (an index swap on the sightings table).

- **Investigation evidence is frozen at the open** ([#6001]) - A High CPU investigation now captures its top statements, active requests by host and program, Query Store state, jobs and waits from the data already collected, right after it opens, so an agent reads what the breach looked like and not what is left of it by the time it claims. The brief carries the evidence, masked at the configured data detail level.

### Changed

- **Plan analysis and exports are bounded, spreadsheet-safe and warn on unencrypted mail** ([#5699]) - The plan analyzer's regular expressions now time out after 250 ms and share a 2 second wall-clock limit per plan (a check that is cut short is named in a rule 40 note on its statement unless rule 40 is disabled, and is never reported as a finding), and plan XML passed to the analyzer is refused when one element has more than 1,000 attributes or holds a DOCTYPE declaration. CSV exports and copied rows write a text cell that starts with `=`, `+`, `-` or `@` as text (copied rows first turn tabs and line breaks inside a cell into a space, and the rule looks past leading white space; the web dashboard's Copy row and Copy table do the same; CSV fields holding a comma, semicolon, tab, quote or line break are quoted), while Copy Cell copies exactly one cell as it is (the deprecated Dashboard gets the same export and copy rules through the shared helpers). - **darling.json and the store's admin and viewer credential files are limited to a local operator group** ([#5700]) - These files were readable by every interactive account. They are now readable by SYSTEM, Administrators, the service account and the local group `PerformanceMonitor Darling Operators`. The install and upgrade scripts create the group (empty), and the group has to exist before the service starts, because the service grants the group read access to these files at its start and applies the new access to existing installs; the upgrade script does not apply it itself. A fresh install that cannot create the group stops, after the service has been granted its access to the install folder and before the service starts; the upgrade script warns and starts the service; add each person who runs the Viewer or the CLI without elevation to the group. - **A screen reader or UI test tool can open a server from the sidebar or an Overview card, and the alert badge and Settings inputs have names** ([#6138]) - Viewer and Lite sidebar rows and Overview cards now accept the Invoke action and open the server tab the way a double-click does; the alert badge reads "1 unread alert" or "N unread alerts"; every Settings input has an automation name. Overview Needs Attention rows also accept Invoke, open on Enter, and are named for the server and why it needs attention.

- **An offline PostgreSQL target no longer reads as healthy** ([#6169])- its empty panels and reads say it is offline, the fleet sweep keeps a target that was offline before a restart as offline, and Run all collectors now is off for it.

- **Five MCP reads no longer answer past the 32 KB response target without saying so** ([#6195]) - `get_perfmon_stats`, `get_blocked_process_xml` and `compare_analysis` were over the target at default arguments on a busy server (545 counters, 82 KB; 3 blocked-process reports, 54 KB), and `get_collection_health` with `full_detail` and `get_collection_log` with a large `limit` were over it when asked for more. Each read, on both Darling and Lite, now keeps the whole rows that fit and reports `truncated`, how many it returned of the total, and a `size_note` naming how to get the rest (a filter, a smaller `limit`, a shorter window, or one report by its `event_time`). Blocked-process report XML is never cut mid-document.

- **A collector the server keeps refusing is now tried less often** ([#6202]) - a permission-refused collector (for example `tempdb_stats` for a contained user on Azure SQL Database) wrote a PERMISSIONS row every interval in Darling and was skipped for the whole session in Lite. Both now back off while the same refusal repeats (up to hourly), return to the normal interval on the first success or a changed answer, and pick up a granted permission without a restart.

- **The PostgreSQL "Test an index" check now runs under its own login, with only the grants planning needs** ([#6191]) - the check ran EXPLAIN on stored statement text over the monitoring connection, and planning can run an IMMUTABLE function with constant arguments under the roles of the login that plans. It now signs in as a login set up like the remediation login (hypotheticalIndexUsername and hypotheticalIndexEncryptedPassword, an env: or file: reference) that needs CONNECT, USAGE and SELECT only. With no login set, the check is refused and the message says what to set up; it never falls back to the monitoring login. It tests SELECT statements only. Adds store migration V203 (two nullable columns on the server registry).

- **MCP reads name an Azure SQL Database server by its display name** ([#6188]) - an entry with a database set showed its `<host>:<database>` connection key in the `server` field and in message text of most MCP reads in Darling and Lite, in `get_pg_database_stats`/`get_pg_session_states` not_collected text, and on the Blocking, Query Store and FinOps Locking panels. They now show the display name; when two entries share a display name the key is shown so it can be passed back as `server_name`.

- **A row with an empty cell no longer costs every server its first delta after a restart** ([#6212]) - the delta seeding read some nullable store columns without a null check, so one such row abandoned that family's seeding for all servers. Empty cells now read as empty or 0, and a row lacking its key ids seeds nothing.

- **PostgreSQL collectors now work on older PostgreSQL targets** ([#6206]) - On PostgreSQL 10 to 13 targets, six collectors failed on every run and wrote an ERROR line to the target's log each time. Each collector now sends a query that fits the target's version: `pg_stat_statements` before 1.8 is stored from its old column names, newer-only columns are NULL, and `MATERIALIZED` is left out before PostgreSQL 12. `pg_write_stats` now also runs below PostgreSQL 14 with NULL WAL columns, and `get_pg_io_stats` says `not_collected` with the version on targets older than 16.

- **PostgreSQL target connections run no type-loading query of their own first** ([#6143]) - Npgsql read pg_type on the first connection of each PostgreSQL target, before the service checked search_path. Target connections now load no types, so the first statement on one is the service's own and a server's own search_path setting can't change how it reads.

- **kill_session on PostgreSQL refuses a connection that lacks the pinned search_path** ([#6143]) - The kill connection now loads no Npgsql types on open and, before it reads anything, checks that its search_path is `pg_catalog, pg_temp`. If a connection pooler dropped the startup option, the kill is refused with `search_path_not_pinned` and a message naming the setting it saw, and nothing is run.

- **A healthy Darling install no longer writes four event-log warnings an hour** ([#6219]) - the daily collector-cost digest, fleet-sweep rollup and analysis singles digest were logged as `ALERT TRIGGERED [Warning]`, and a notification channel that failed them (for example a Teams endpoint that timed out) logged the same warning again on every hourly retry. The three reports now log at Information as `SCHEDULED REPORT`; a failing delivery warns on the first failure and when the error changes, repeats at Information with a running count, reminds once a day, and logs one line on recovery. The collector-cost regression and digest also no longer treat the first hours of a new install as a baseline (a pair now needs 3 days between its first and last observation). Retries are unchanged.

- **The diagnostics bundle now finds a managed store that is starting or listening on another port, and says why when it cannot reach it** ([#6217]) - On a managed install the bundle tried the configured port once and reported `connect_failed` even with the service running. It now reads the store's own `postmaster.pid`: it connects to a live store on another port (with a warning), waits up to 20 seconds for one that is still starting, and otherwise reports `store_not_running`, `store_starting` or `data_directory_missing` instead of a bare `connect_failed`.

- **The web deadlock graph's process pane wraps its SQL handle note and property lines** ([#6228]) - The SQL handle note and the other lines in a process's detail pane ran in one line past the pane's right edge and were cut off, because the pane inherited the table cell's no-wrap setting. They now wrap inside the pane, and a long hex handle breaks anywhere, at desktop and phone widths. The desktop viewer already wrapped this text.

- **A quiet server's top-queries reads say "nothing ran" instead of "unavailable"** ([#6232]) - `get_top_queries_by_cpu`, `get_query_store_top` and `get_pg_top_queries` answered `unavailable` (check collection health) for a window in which the collector ran successfully and stored no rows because nothing executed. They now answer `empty` with `successful_runs_in_window`, and keep `unavailable` for a window with no successful run. Darling and Lite match; the Darling reads apply it only where the raw tier holds the whole window.

- **The PostgreSQL Activity grids show their values when a statement or log message has many lines, and the OS CPU grid shows rounded numbers** ([#6229]) - A statement stored with hundreds of line breaks made its Query Shapes row thousands of pixels tall, which pushed the row's numbers out of view and left the grid looking blank. Text cells in the Activity tab's grids are now capped at a few lines. The OS CPU grid showed raw doubles such as 130.67499999999 and bare disk byte counts; CPU, User and System are rounded to one place and Disk Read and Write show sizes. The captured-plans durations, the lock statistics Max Wait and the buffer usage percentages are rounded the same way.

- **The forced-plans collector no longer reads plan XML on the monitored server** ([#6221]) - the variant and plan-guide check added for #6160 read the XML of every later plan of every forced query every 5 minutes, which took 17 to 86 s per server on a store with about 300 forced plans and made collection passes overrun. The collector now reads only the forced plans, and the variant check runs in the store against plan XML the Query Store collector already stored. A later plan whose XML is not stored yet gives a new state, UNKNOWN_PLAN_NOT_COLLECTED, instead of IGNORED.

- **Custom Views: a created, edited or deleted view reaches the sidebar and the list at once** ([#6243]) - after Create or Delete the sidebar kept the old list until a reload (the shell only re-read it on its 60 s poll). Every view write now refreshes the sidebar list straight away, and the Custom Views list no longer waits on the fleet read before it draws.

- **Darling Viewer: the Fleet Overview heading is no longer covered by its filter controls, and Help > About names the build** ([#6249]) - In a narrow window the "Needs attention only" checkbox was drawn over the "Fleet Health" heading; the controls now wrap to the next line instead. Help > About showed only "Version 3.10.0"; it now shows the commit the Viewer was built from when the build has one, for example "Version 3.10.0 (commit 0993a1441)", and just the version when it does not.

- **A command nobody picks up within 15 minutes now expires instead of running later** ([#6251]) - a pause, purge, undo or other command queued while the service was stopped used to run whenever the service next started, however late. The service now fails a pending command older than 15 minutes (on the store's clock) with an "expired" message instead of running it, and the Viewer cancels its own command when it stops waiting, unless the service has already started it, in which case it says the command is running.

- **The hourly store-size row no longer walks every database file** ([#6250]) - the store self-metrics sweep sized the whole database with `pg_database_size` every hour, which averaged 7.2 s and reached 77 s on a store with many chunks. The hourly row is now estimated from catalog page counts and marked `size_estimated` (in `get_store_metrics`, `get_store_host`, the web Store size cell and the Viewer status bar); one sweep a day still writes the exact size. The Store Disk Pressure alert text marks the store size it quotes as "~X (estimate)" when it came from the hourly estimate.

- **The forced-plans collector no longer takes 15 to 60 s per server on a primary** ([#6221]) - it joined two Query Store views in one statement, which costs about 130 ms per forced plan on a primary with a large Query Store. It now reads the forced plans first, then their object ids from a temp table: 0.6 s for a database with 162 forced plans that took 20 s before.

- **Plan correction and Query Store health skip a readable secondary replica** ([#6252]) - the two collectors only skipped availability group secondaries, so a cloud read replica was read on every pass and wrote the primary's rows again (69,358 plan correction rows in a day on one store). They now skip a database whose Query Store reports `readonly_reason` bit 8, as the Query Store collector does.

- **MCP route edits keep what a route matches and covers when it has its own destinations; quiet windows are limited; write logs name the token** ([#6241])- `update_notification_route` no longer changes the match or scope of a route that has a destination of its own or an agent Off setting (change those in the Viewer); `set_quiet_window` starts at most 7 days ahead and allows one upcoming or active window per server or fleet; MCP write log lines carry a token fingerprint and the client-reported name. **Updated:** both route tools now set a route's own destinations (see "Route destinations over MCP" below); a match or scope change on a route with its own destinations is allowed, and only a route with an explicit agent setting keeps its match and scope. The function behind the MCP route tools no longer hands a stored webhook or key back to the `mcp` login (it says only whether one was saved) and refuses a webhook value that is not exactly a sealed value and a recipient list with control characters, angle brackets, quotes or more than 50 entries; MCP answers show the host for Teams and Slack only (saved or none for generic and PagerDuty) and the recipient list in full, with the earlier list in the undo arguments; an oversized key or URL over MCP answers `invalid` like the Viewer. A Viewer save of a route whose saved recipient list has display names (such as `Ops <ops@example.com>`) is refused until the list is rewritten as plain addresses.

- **A failed webhook's stored error now shows the HTTP status only** ([#6241]) - the alert log's send error and the channel health text for a failed webhook post read `HTTP <status> <reason>`; the endpoint's reply body is written to the service log (Darling) or the app log (Lite). The Test buttons still show the body. A webhook or heartbeat URL written with a trailing dot, or as a NAT64 or IPv4-compatible link-local address, is now refused at save, and a heartbeat URL on a blocked address reports a fixed reason.

- **MCP dismiss, restore and quiet window fixes** ([#6241]) - dismiss_alert_history and restore_alert_history failed on managed and compose stores because the mcp role could not update the alert history table; it now has update on the dismissed column only. set_quiet_window refuses a window over 7 days, clear_quiet_window only clears windows set by set_quiet_window, an investigating agent cannot set a mute start time, and the slow-call record keeps argument names only for write tools and redacts `*_url` arguments.

- **Diagnostics bundle no longer rewrites known names inside ordinary words** ([#6258]) - the final name check replaced a known name as a plain substring, so a name such as `data` also changed `database`. A name of 4 to 6 letters inside a plain run of ASCII letters is now left alone (`wholesales`, `administrator`). A name of 7 or more letters, a name with a digit or punctuation, and a name at an escape, case-change or digit-then-letter edge are still replaced, so `SALESDWFULL.BAK`, `SQLPROD_Full.bak`, `mainalpha-sql-01` and `SalesReport` are replaced.

- **A fleet Query Store panel reads the interval table for the servers that can use it, and raw only for the rest** ([#6115]) - one server that failed the interval-table gate (a newly enrolled server, or one with no Query Store collection) used to send every fleet panel to raw `query_store_stats`, which timed out on a large store; now only that server reads raw.

- **Agent dispatch docs, starter instructions and log lines match what ships, and a setup that cannot serve an agent is warned about** ([#6273]) - The README said an agent can only read and report, the remediation login log line said nothing would use it (SQL Server) or to remove it (PostgreSQL), and the docs had no page on agent dispatch. A new page, `docs/darling-agent-dispatch.md`, covers setup, levels, the action switch statement, the journal and undo. `AGENTS.example.md` and the log lines are corrected. The start-up log and `--validate-config` now warn about investigations on with MCP off, with no usable token, with writes also on (writes win), and note a setup with no agent route. The warnings do not change the exit code or stop the start. The Lite tool count in `docs/mcp-server.md` is 97 by default.

- **A fresh install no longer logs a console error on Alert History, FinOps and Job History** ([#6280]) - With no servers registered, `list_servers` answered with plain text, which the web API turned into a 400. It now answers the `empty` status like other reads, on Darling and Lite, so the pages show their empty text and MCP clients get a status they can read.

- **A change to a server's remediation login in darling.json now reaches a server that already exists** ([#6262]) - the two remediation keys were read only when a server was first registered, so editing them and restarting did nothing and said nothing. On every start they now set, replace or (when both are removed) clear the registered server's remediation login, with one log line per change that names the server and the secret's shape and never the login or secret. A server that is not in darling.json is not touched. `--validate-config` and the service log at start now also warn when the remediation secret is a DPAPI blob: operator remediation still opens it, but agent server actions (plan force, eviction, kill) accept only an `env:` or `file:` reference. The README and sample file now say so.

- **A plan undo that changed the server is always journaled, and an agent change checks the agent switch again before it writes** ([#6271])- If the store failed while recording a person's undo of a forced plan after the server accepted it, the undo vanished from the journal and the change could be offered for undo again. It is now recorded late and the answer says so. An agent change also re-reads the agent actions switch right before it writes, so turning agent changes off in that window stops the write.

- **An agent's force, unforce, evict or kill re-checks Level 3 and the server's own switch when it writes** ([#6271])- turning a server's switch off, or lowering its route to Level 2, while the dry run was still reading the server did not stop the write, and a kill cannot be undone. The write's own transaction now checks everything the gate checked, with the switch and route rows locked until the write ends.

- **Two agent mute or threshold changes at once no longer fail, and turning agent changes off waits for a change in progress** ([#6271])- two agent store writes at the same moment could deadlock and one failed; they now queue. An agent change to a monitored server now has one 30 second limit for the connect, the read and the write, and the Viewer's agent changes switch, the web switch and the collection pause wait up to 60 seconds for a change in progress instead of giving up after 5 to 15 seconds.

- **A person's plan undo and a plan force with a lost reply no longer drop their records** ([#6271]) - an undo whose late journal row failed once on an open connection waited on its own lock and reported the row missing; an undo with an unknown outcome left no journal row; a force whose reply was lost but took effect never got its post-force checks; and a person's undo ignored the server's switch lock. Each is fixed.

- **MCP can no longer turn off or delete an Off agent route, repoint a server a route is scoped to, or register a second database on a machine such a route is scoped to** ([#6282])- over MCP these are refused and point to the Viewer or the web dashboard; turning an Off route on is still allowed, and a route with no scope does not block editing or adding servers.

- **MCP tag tools no longer change which servers an agent route covers** ([#6281]) - assigning or unassigning a server, deleting a tag, or moving a tag over MCP is now refused, with a sentence naming the route, when the tag is the tag of a route with an agent setting (Off included) or is above or below it. This also holds when MCP connects as the store's owner, and for servers that are no longer registered; `remove_server` over MCP answers a refusal for a server mapped under such a tag. Tag edits in the Viewer and the web work as before. Needs store schema 209.

- **The Overview Blocking & Deadlocking lane now shows a lone deadlock or blocking event as a visible bar, and hovering it reads 1** ([#6287]) - over a long window (for example Yesterday) one event was drawn as a bar under a pixel wide and the hover read 0 unless the pointer was within a minute of it, so a deadlock the Blocking/Deadlocks page listed looked missing. The bar and the hover reach now scale with the window in the Darling Viewer and Lite. Short windows draw as before.

- **Changing a server's agent action switch from the web needs a signed-in admin** ([#6275])- the web and a plan undo from the web refuse a caller who is not signed in as an admin; PostgreSQL aliases (pg, aurora) are read as PostgreSQL; a switch can always be turned off; the MCP tool takes one server by its exact name.

- **"Sign in again" after a web dashboard session expiry now takes you to the sign-in** ([#6278]) - the link pointed at the page's own address, so a click did nothing until the page was reloaded by hand. It now always reloads the current page, which shows the sign-in form (or starts the SSO redirect) at the same address, so the page you were on opens again after you sign in. The address named in the server's answer is not used.

- **A triage link clicked in Teams, mail or another site now opens signed in** ([#6286]) - the session cookie is `SameSite=Strict`, so a link followed from another site arrived without it and showed the sign-in page even with a live session. A page request marked cross-site and started by a click, with no session cookie, is now answered with a small page that reloads the same address from the dashboard's own site, which carries the cookie; the path, query and `#/` route are kept. Script redirects and meta refreshes still get the sign-in page, and with no session the click still ends at the sign-in page. A Mute Rules link now fills in only the scope fields (never the reason, source, start or expiry) and shows a notice to check the form. HTML pages carry `Cross-Origin-Opener-Policy: same-origin`. The cookie setting is unchanged.
