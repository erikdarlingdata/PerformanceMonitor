## [3.11.0] - 2026-10-22

### Important

- **Upgrading from 3.10 runs the Darling store migrations V174 through V214 on the service's first start** - the store schema goes from 173 to 214. Almost all of it is new tables that start empty or new nullable or constant-default columns, which PostgreSQL adds without rewriting the table: the service version table (V174), the plan regression built-days columns and a trigger on the interval table (V185), the change watches table (V207), the Client Timeouts alert's attention events (V179), per-collection procedure totals (V176), Query Store watermarks (V178), an hourly collection log rollup (V186) and a failure record for the Query Store builder (V189), an estimated-size flag on the store metrics (V190), the alert settings for the Runnable Queue alert, the Volume Free Space excluded volumes list and the Query Store fetch limit (V177, V200, V209), the tables for alerts raised by other services (V180), a route's server or tag scope and its resolution flags (V181, V187), the read record's window band, in-flight and caller columns (V182, V183), the investigation, Level 2, Level 3, evidence, follow-up and signed webhook tables and columns (V184, V188, V191, V193, V196, V197), the query tag tables (V192) and a new unique key on the query tag sightings table (V194), forced plan collection (V195, V201), the head blocker's evidence columns on the blocking snapshots (V199), the Availability Group primary replica column (V202), the hypothetical index login (V203), folders and owners on custom views (V204), an expiry on custom alert rules (V205), a start time on mute rules (V208), the pseudonym key (V198, seeded once with a random value) a trigger that stops MCP tag writes from changing which servers an agent route covers (V210), the two multiples of the Client Timeouts relative bars on the alert settings row (V211), the name a monitored machine reports for itself on the server registry (V212), two Query Store replica columns with a rebuilt collection log view (V213) and the known pattern table (V214). None of them rewrites a large table or needs an offline window. The ones that read or change existing rows are small: V175 adds the plan regression day column and marks every built day stale, one row per server and day, so a day reads from the interval table until the hourly builder refills it; V182 replaces the primary key of the hourly read record table; V206 makes the collector schedule's enabled column optional, merges rows whose collector names differ only by case, deletes rows whose name is not 1 to 64 lowercase letters, digits or underscores, and caps a frequency above 525,600 minutes and a retention above 3,650 days. V175 needs an exclusive lock on the plan regression day table for its new column and sets a lock timeout for it.

- **Upgrading Lite from 3.10 moves its DuckDB schema from version 67 to 78 on the first start** - every step adds: the Client Timeouts mute rule match column (v68), the notification routes table and the Level 1 investigation tables (v69), the query tag tables (v70), the investigation evidence table and the new investigation request and report columns (v72 to v75), the head blocker's evidence columns on the blocking snapshots (v76) the Availability Group primary replica column (v77) and the collection log's Query Store read source column (v78). The v71 step recreates the query tag sightings table so the database joins its key; that table is new in this upgrade, so no rows are lost. If the v71 step fails, the schema version stays at 70 and the step retries on the next start. None of them rewrites a large table or needs an offline window.

- **Self-managed stores: re-run `provision-roles.sql` after upgrading** ([#6066], [#6254], [#6383], [#6334]) - Run `Darling/tools/provision-roles.sql` again after the upgrade, because four changes need it. The pseudonym key is locked to the store owner (#6066): the upgrade already hides it from `PUBLIC` and from the three roles, and the script finishes the lock-down. The Query Store replica setting needs the new 18-argument `config.edit_monitored_server` function and the `viewer` and `mcp` grant on `query_store_replica` (#6254): the service replaces the three `config.edit_monitored_server` functions at each start when its login owns them and warns once, naming the script, when it does not, but those two come only from the script, and until it is re-run, editing a server from the web dashboard or the MCP `edit_server` tool fails with `permission denied` (collection and reads keep working). `unmute_analysis_finding` needs the `mcp` role's DELETE on `config.analysis_muted` (#6383). Known patterns need their three write functions (#6334): until the script is re-run, adding, changing or deleting a known pattern fails. The compose store and managed provisioning do all of this on their own.

- **A remote SQL Server reachable only over a named pipe no longer connects from the Darling service or Lite** ([#6352]) - Turn on TCP/IP for that instance in SQL Server Configuration Manager and add the port to the host if it is not 1433 (`name,port`).


### Added

- **Investigations panel in the Darling viewer and Lite** ([#5907], [#6265]) - the Darling web viewer gets an Investigations page, and Lite gets a read-only Investigations window (sidebar button), each listing agent investigation requests by state and family (opened, server, metric, family, agent, lease, reported, route) and, for a picked request, its reports, stored brief and journal. In Lite the reports, brief and journal text are masked at the level the MCP investigation tools serve. On the web, an admin store login can also close a request, write an agent note and start a practice request from the Investigations, Pending Notes and Practice Scores tabs, using the same storage code, states, refusals and journal rows as the Viewer (a viewer-role web login gets a clear refusal, and a note written this way is approved as written).

- **Agent notes can be approved or rejected in the Darling web dashboard and in Lite** ([#5908]) - A note an agent proposes with its investigation report is pending until a person decides it. The Darling web dashboard's Admin page has a Pending Notes tab (server, metric, family, the proposed text, the agent and the request) with Approve and Reject, and Lite has an Agent Notes screen under Settings (Review Agent Notes) over its local database. An approved note goes into later briefs; a rejected note is kept with who decided and when, and never reaches a brief. Each decision is stamped with the person and the time and journaled. On Darling, managed and compose stores connect the web dashboard as the viewer role, which can list notes but cannot decide them, so there the page says to decide in the desktop Viewer or to set postgres.webConnectionString to an admin login. Lite stays advise-only for agents: a person decides notes, and the note text can't be edited.

- **A new Darling MCP tool, `backtest_custom_alert_rule`, shows where a custom alert rule would have fired and cleared over stored history** ([#5919]) - there was no way to see how often a rule would fire before saving or changing it: `test_custom_alert_rule` reads only the current value and skips the breach and clear samples. The new tool replays a saved rule or a draft definition over up to 7 days (default 24 hours) on up to 10 servers. At each step it reads the rule's own panel as of that step and applies the same breach and clear samples the live engine applies, so the fire and clear points match what the live engine would do on the same samples. It writes and sends nothing. One call runs at most 2,880 queries and 60 seconds, and a call a cap stops answers `partial` with `stopped_at` and what it covered. A server with no stored samples answers `unavailable`, never 0 fires. The MCP catalog grows from 187 to 188 tools.

- **Store schema for Level 2 agent investigations** ([#5920]) - the store gains the tables and columns Level 2 needs, in one migration (store schema version 191). A notification route may now be set to agent level 2 (0 to 2) and an investigation request may carry autonomy level 2; any level outside the range is still refused. `config_service` gets an `agent_actions_enabled` switch that reads as on on a new and an upgraded store. A new `config_threshold_overrides` table holds per-server, per-database threshold overrides, is deleted with its server and bumps the `config_version` reload beacon on every change. A new `investigation_feedback` table holds a person's verdict (right, partly or wrong), corrected verdict, missed step and comment on a report, one per request per author, and goes with its request. Investigation requests gain a nullable `practice_of` column with no foreign key. The admin role can write both new tables, the viewer role can only read them, and the mcp role can write the overrides table and read feedback, in both the managed roles and `provision-roles.sql` (a bring-your-own store needs the script re-run after upgrading). Retention needs no new pass: feedback ages with its request and overrides are never aged.

- **The alert engine can take per-server and per-database threshold overrides** ([#5921]) - the engine read every alert threshold as one global value, so a threshold could not be tuned for one server. Each tunable integer threshold now has a registered key and a scope (server, or server and database), and the engine reads every one of them through an optional overrides object. The version store (PVS) percent and floor and the file growth rise and level bars can also take a per-database value, because those alerts grade each database on its own. Lite passes none, and in Darling only the stored per-server overrides change a threshold, so every other alert behaves exactly as before.

- **Investigation reports can record Jira, pull request and bug report links** ([#5922]) - An agent's report may carry up to 10 links, which must be https with no user name or password (http, file and UNC links are refused, and are checked again whenever a link is shown). Later briefs for the same server and alert family list the last 30 days of links, and the viewer and web dashboard show a report's links.

- **The Level 2 agent action gate and its journal** ([#5925], [#5632]) - Darling now has the one gate every Level 2 agent change goes through: a live claim on the request, the request's server only, a reason and evidence, with each refusal journaled at most once an hour and each change journaled before and after with its evidence masked at `mcp.dataDetail`. Requests now record the lowest agent level among their routes, and an alert from a custom rule an agent last wrote stays at Level 1. If the store's commit fails after the server accepted the change, the journal records it as done (marked recorded late); if the store cannot be written at all, it shows as result unknown, never as failed.

- **People can give feedback on investigation reports** ([#5926]) - A report can be marked right, partly right or wrong, with a corrected verdict, the step the agent missed and a comment, from the Viewer's Investigations window (Report Feedback tab, admin login) or the web Admin page's new Report Feedback tab (recorded only under an admin store login; list-only otherwise). `get_investigation_reports` now returns each report's feedback and, per alert family, how many investigations ended as false positives before and after people's corrections.

- **Lite: Level 1 agent investigations** ([#5820]) - when an alert fires on a notification route whose agent level is 1, Lite opens an investigation request for it, and when `mcp_allow_investigations` is on with MCP writes off it serves four tools (`list_investigation_requests`, `claim_investigation_request`, `submit_investigation_report`, `get_investigation_reports`) so a local agent can claim the request, read its brief, and file a report that Lite keeps beside the alert. Requests, reports, notes and the journal live in Lite's own DuckDB file; nothing writes to a monitored server; with both MCP settings on the investigation tools stay off and Lite logs one Critical line saying so.

- **Deadlock graph window: a visible Copy button for the SQL text** ([#5663]) - the only ways to copy a process's SQL text were the right-click "Copy SQL Text" menu item or selecting the text box and pressing Ctrl+C, and the menu was easy to miss. The Properties panel now has a Copy button on the same row as the "SQL Text" heading, in Lite and the Darling viewer. It copies the same full SQL text as the menu item, through the same code, and is only shown when the process has SQL text.

- **A Runnable Queue alert warns when runnable tasks per scheduler stay high** ([#5641]) - no alert read scheduler queue depth, so a CPU-bound server could time out clients minutes before High CPU fired. It reads the stored runnable-tasks-per-scheduler values one collection at a time (a collection the collector split across several rows is summed, not averaged row by row), averages the collections of the last 5 minutes when there are at least 3, and when the collector runs late falls back to the newest 3 collections if all are within 10 minutes (within 4 times the recent gap between collections when collection is slower, so the Low-Impact preset's 5-minute collection still evaluates). A standing Runnable Queue alert resolves, with that reason in the notice, when 30 minutes pass without an evaluated reading (the 30 minutes count from the last evaluated reading, and a read that is not an observation never restarts the count). It alerts Warning at 8 and Critical at 16 by default, with the usual cooldown, mute and cleared notice. The alert card also shows the CPU for the same minutes and the heaviest requests by CPU in the newest query snapshot ("at least N more" when the read hit its 50-row cap). Both bars and an on/off switch are settings (Lite and Darling Settings windows, `get_alert_settings` in both apps, Darling `update_alert_settings`), and the metric can be muted from either mute dialog.

- **Mute rules can match by client application** ([#5714]) - a mute rule now has an optional "Client application (substring)" match, set in the Lite and viewer mute dialogs, on the web Mute Rules page and through `create_mute_rule` / `update_mute_rule`, so cancels from one tool (for example SSMS) can be muted without muting an application's own timeouts. A rule that names a client application never mutes an alert that has none.

- **Other services can raise alerts through Darling** ([#5726]) - A second service can now raise alerts that go through Darling's notification channels, routes and mute rules, each with its own database login. The store gets the source, queue and firing-state tables and the mute-rule `external_source` column (schema version 180), a submission function that each source login calls with only its EXECUTE grant, delivery of the queued alerts, and CLI verbs to add, rotate, list and remove sources; a mute rule can name an external source in the Darling MCP tools (`get_mute_rules`, `create_mute_rule`, `update_mute_rule`, `get_alert_history`) and on the web Mute Rules page.

- **Enter opens a server tab** ([#5764]) - In Lite and the Darling viewer, pressing Enter on a selected server in the server list opens its tab, and the selection stays put when the list refreshes.

- **Darling records the collection slots it stepped over** ([#5741]) - when a server's collection falls behind (a body that ran long, a wait for a fleet slot, the memory launch guard's hold, or a lost daily run), Darling now writes one `collection_cycle` row to the collection log per server, at most every 5 minutes, with the slot count, the cause and both ends of the gap (a row with no measured cause leaves its duration empty). Collection health, "last collected", Collection Stopped and the other log readers leave the row out, so it cannot hide an outage or inflate a count. A computer that slept or a paused service writes no row. Collection health now shows the late slots: a `skipped_cycles` block in `get_collection_health` (status "unavailable" with empty figures if its read fails, the rest of the answer unaffected), a Skipped Cycles panel on the web Collection Health tab, and a line on the Viewer's Collection Health tab. `get_collection_log` counts the collection_cycle rows in a new `skipped_cycle_rows` and leaves them out of `run_count`, in the per-server and fleet forms, as Lite's does. Lite's `skipped_cycles` block carries the same `status` ("ok", or "unavailable" with empty figures if its read fails), so one failed read does not fail `get_collection_health` in Lite either.

- **Darling warns at start when the store was migrated by a newer build** ([#5773]) - An older build started against a newer store now logs one warning at start that names the migrations it does not know and keeps running, and Darling/README.md's new "Rolling back to an older build" section explains that a rollback keeps the store and lists the migrations that change what an older build reads and what to do before rolling back past each.

- **A notification route can be limited to one server or to a tag, in Lite and Darling** ([#5769]) - A Darling route used to match an alert by metric name or family only, so every server sent its alerts to the same webhook. A route can now be set for one server, or for a tag and every tag below it. One server or one group of servers can then post to its own channel. When more than one route fits an alert, a route for that server wins. Next comes a route for a tag the server is under (the deeper tag wins). A route for all servers comes last. Inside each of these, the order is the exact metric name, then its family, then the new "every metric (*)" match. The "every metric" match is allowed only on a route that has a server or a tag. As before, a route replaces only the channels it sets. Generic headers and the body template stay shared by all routes. Lite now has notification routes for the first time: use Settings > Manage Notification Routes. Lite keeps each route's webhook URLs and PagerDuty key in Windows Credential Manager, not in its database. A URL can be up to 1,280 characters long. The window refuses changes while a saved-settings restore is pending. The Darling viewer's routes window has the same "Applies to" choice and shows each route's scope and status. The Darling web dashboard's Routes list shows the same scope and status, read-only. A route whose server or tag is deleted is not removed. It is marked as orphaned and matches nothing, so a deleted scope never turns the route into an all-servers route. In both products, `get_notification_routes` now shows the scope, its name, how many servers it covers now, and whether it is orphaned. It never shows a URL or key. Lite also serves `set_notification_route_enabled` and `delete_notification_route`, but only when `mcp_allow_writes` is true. If you provisioned your Darling store yourself, run `tools/provision-roles.sql` again after the upgrade. Then the viewer and MCP roles can read the two new scope columns.

- **Read latency capacity fields** ([#5792]) - Darling now records, for every web, composed-panel and MCP read, the width of the window it asked for (1h, 24h, 7d, 7d+ or none), how many other reads were running when it started, and how long it waited for a store connection, and `get_read_latency` and `get_slow_reads` return them.

- **Read caller** ([#5795]) - Slow reads now record who made them (an MCP client's name and version, or a salted hash of the web session) and the hourly read-latency rows count distinct callers, with no personal data stored. The web dashboard shows the caller in the slow-reads grid and gives read latency a grid of its own.

- **A store sizing guide for Darling, and a load-test harness for the Query Store tables** ([#5800]) - The new guide gives the measured size per monitored server for SQL Server with and without Query Store and for PostgreSQL, the retention horizons behind those numbers, and host sizes (vCPUs, RAM, disk) by server count up to 150 servers. `Darling/loadtest/` adds scripts and a runbook that raise a restored store's Query Store interval data N times and measure the reads, the hourly work and the writes at each N. The service log line of each of the three hourly Query Store builders now ends with the time it took, in ms.

- **Darling limits how many long reads run at once** ([#5806]) - one MCP client could hold the store's disk at its limit for minutes. The service now runs at most 2 long reads at a time (`reads.maxHeavyReads` in darling.json, 0 for no limit). A read is long when the 90th percentile of its route's time at that window size is over 2 seconds. The limit covers MCP and web reads; the Viewer's direct reads are not counted. Up to 16 more wait for up to 45 seconds. After that, a read gets `busy` on MCP, or HTTP 429 on the web. Short reads never wait. An identical read in the next 15 to 120 seconds comes from memory. `get_read_latency` and its web grid show queued, refused and cancelled reads, and count each store read once, joined callers apart.

- **Darling can hand an alert to your own AI agent** ([#5632], [#5850], [#6066], [#6237], [#6273]) - a notification route can now be set to Investigate, so the alerts it matches, and the analysis findings that page, open investigation requests for an agent you run. Darling opens one request per server and alert family, and an alert of that server and family joins it while the request is open or claimed, when it fires within 30 minutes of the request's latest alert and up to 4 hours after its first, up to a limit per route per hour (20 by default) and per day (100 by default). Your agent works through four MCP tools: `list_investigation_requests`, `claim_investigation_request`, `submit_investigation_report` and `get_investigation_reports`. The claim and the report are served only when you set `mcp.allowInvestigations` with a bearer token, while `mcp.allowWrites` is off. A claim returns a brief: the alerts, the analysis findings, earlier reports, recent changes, approved notes about the server, your environment profile and the read tools to call next. At Level 1 the agent only reads and reports; it cannot change a monitored server (Levels 2 and 3 have their own entries). A new setting, `mcp.dataDetail`, masks statement literals (`maskLiterals`) or holds back query text, plan XML and input buffers (`metadataOnly`) in every MCP tool answer, `get_investigation_reports` included, and in the brief, and `get_mute_rules` now names each rule's match summary `match_summary`, in Darling and Lite and in the mute-rule write tools' answers. The viewer has a Manage Investigations window for requests, reports, notes and profiles, and the web alert page a read-only Investigations panel. Darling ships no agent. The investigation reads say when a page was cut (`requests_returned` and `truncated`). Under `mcp.dataDetail = metadataOnly`, a login or host name is shown as `login#` or `host#` plus 8 hex characters from a keyed hash, so the same name reads the same in every answer, brief and webhook from one store, across restarts. Darling's starter agent file says to use a small model for the first step of an investigation and a larger one only when the full investigation is needed. The start-up log and `--validate-config` warn about investigations switched on with MCP off, with no usable token, or with writes also on (writes win).

- **Alert Details window: resizable, selectable values, Copy all details, and a link to the full chain** ([#5854]) - In Lite and the Darling Viewer, the Alert Details window now resizes and remembers its size. Its values can be selected and copied, and a Copy all details button copies the whole alert as plain text. Blocking and deadlock alerts get a link that opens the server's Blocked Process Reports or Deadlocks grid around the alert's time.

- **MCP long-poll: an agent waits for an investigation request to open for its routes** ([#5856]) - New MCP tool `wait_for_investigation_requests` waits up to 25 seconds (20 by default) for an investigation request to open on the agent routes it names, then answers each new request's id, route, server, family and open time with a cursor for the next call. The claim stays `claim_investigation_request`, A call that passes the cursor from its last answer also gets every request opened in between (up to 100, oldest first); a call with no cursor starts from now.

- **Alert resolutions go to the channels that got the fire, opt-in per channel** ([#5855]) - When an alert clears, Darling can now send that to Slack, Teams, the generic webhook and email. Each channel has a "Send resolutions" setting that is off by default, and a notification route can override it for its own destinations; the clear goes only to the destinations its delivered fire reached, a mute rule stops it, and its history row records the channels and the outcome. With PagerDuty auto-resolve on, an alert's clear now closes the incident its fire opened (Server Unreachable and AG Replica Disconnected close through their own recovery alert).

- **Generic webhook: {{investigation_json}} carries the alert's investigation request** ([#5853]) - A generic webhook body template can now include `{{investigation_json}}`, the investigation request the alert opened or joined (its id, state, lease and expiry times, the brief masked at `mcp.dataDetail`, and the MCP tool names to claim and report it), so a POST endpoint can start an agent from the alert. It is empty when the alert opened no request, and the request is now opened before the alert's channels post.

- **Lite: Level 1 agent investigations** ([#5902]) - Lite can open investigation requests from alerts, and your own agent can list, claim and report on them over MCP (four tools, served only with mcp_allow_investigations on and mcp_allow_writes off, no token), with routes, settings, data-detail masking, an instructions paragraph, a guide per tool, a docs section and a starter agent file, matching Darling.

- **Practice requests with a score per agent** ([#5937]) - Pick a case you already gave feedback on, in the Viewer's new Practice tab, and Darling replays it for an agent without the original report, verdict or comment. The agent's report is scored against your feedback (a corrected verdict, or right and partly right) and the score shows per agent in the Viewer and on the web Admin page. A practice request never joins a live alert, never counts against a route's limit, and is left out of the Report Feedback list and the per-family counts; its report is not shown to other briefs. While a practice is live, the replayed case's report is also left out of the other briefs' earlier reports and prior links, and out of get_investigation_reports for an agent on the investigations arm. The score is advisory.

- **Agents at Level 2 can change mute rules and custom alert rules, journaled** ([#5934]) - An alert route set to Act (Level 2) now lets an agent with a live claim mute one metric on the request's server and create, change, disable or delete a custom alert rule scoped to that server. Every change needs a reason and evidence, is stamped with the agent, and is journaled with the before and after rule; most of the service's own alerts cannot be muted (the availability group alerts, Agent Not Running and the report digests still can) and writes stop once the report is submitted. The Viewer route editor offers the Act level.

- **Per-server alert threshold overrides** ([#5933]) - Darling can hold a threshold for one server, or one database on it, that differs from the global value, so an alert that is noisy on one server can be tuned without changing every other server. It covers the integer alert thresholds and the PostgreSQL deadlock and blocking counts; set one with `set_alert_threshold_override`, and see the effective value and its source with `get_alert_settings` and `server_name`. The desktop Viewer (Settings, Alert rules) and the web Admin page (Threshold Overrides tab) show a grid of the overrides with the global value beside each; both refuse a bad key or bound, and the web accepts a change only under an admin store login (a managed or compose store connects the web dashboard read-only, so there it is a list). A Level 2 agent may change an override only for its own request's server and can never set a threshold to the value that turns its alert off (the top of the key's range, or zero for Low Disk; to silence an alert, mute it), and a bring-your-own store needs `provision-roles.sql` re-run once to grant the table.

- **Agent changes list with one-click undo and an off switch** ([#5936], [#6271]) - The Viewer's Investigations window and the web Admin page have an Agent changes tab: every change an agent made, what it was refused, and calls with no known result shown as "result unknown". Undo puts a mute rule, custom alert rule or threshold override back the way it was before the agent's change, but only if nobody has changed it since (otherwise it says "changed since" and leaves it); a deleted rule comes back with its own Custom id. A switch turns every agent change off at once. The web decides only under the admin store login; on managed and compose stores it lists only.

- **CI lints the workflow files with actionlint** ([#5947]) - a pull request that changes a file under `.github/workflows/`, and every push to main or dev, now runs actionlint in the Guard tests job, so a broken expression, a `needs:` name that matches no job, or a bad action input fails at once and not when the workflow runs.

- **Tests wait on conditions, not fixed sleeps, and CI failures are counted apart from the skip marker** ([#5943]) - the test projects get two wait helpers in place of fixed sleeps, a fixed sleep is now a build error in them, and a new script counts the deliberate "CI not run" marker apart from real failures.

- **CI can set aside a test that dev's own latest push broke, for up to 72 hours, on pull requests that do not reach it** ([#5942]) - a broken test on dev failed every unrelated pull request until a fix merged. A new `.github/ci-quarantine.txt` lists such a test with its dev run, time and issue; the Guard job and the shard runners leave it out only while the latest dev push run failed it and the pull request does not touch it. The file ships empty.

- **Run all collectors now, or one collector now, for a server** ([#5941]) - On a server's Collection Health tab, an editor seat now has "Run all collectors now" (every enabled collector, once) and a "Run now" button on each collector (that one, even if disabled, without changing its schedule); the MCP tool `run_collectors_now` does the same. A second request is refused while one is running, and a request within 60 seconds of the last one is refused with the time the next is allowed.

- **Client Timeouts measurement scripts** ([#5736]) - Two read-only scripts, `Darling/tools/attention-rate-measure.sql` for the PostgreSQL store and `Lite/tools/attention-rate-measure.sql` for the DuckDB store, report each server's per-minute client attention rate over the minutes the collector actually ran (minutes in span, minutes with a run, longest collection gap, attentions, p50, p99, p99.9, max and the three busiest minutes) and the fleet spread of the per-server p99.9, so the Client Timeouts alert's default bars can be set from measured data.

- **Client Timeouts bars are now relative to each server's own normal rate** ([#5736]) - the Warning and Critical bars are the higher of the old fixed floors (10 and 60 a minute) and 3 and 10 times the server's own 7-day baseline, so a busy server no longer sits over the bar all day and a quiet one still fires over the floor. A server with under a day of capture uses the floors. The alert stays off by default.



- **Alert recurrence in investigation briefs** ([#6000]) - An investigation brief now says, for each metric linked to the request, how many times it fired and how many times it was muted within 30 minutes either side of the first alert's time of day over the previous 7 days (not counting the 30 minutes before the alert, which are the same incident), with the dates fired and the dates muted. A metric with no history says zero.


- **Query tag rule MCP tools** ([#5982]) - Darling serves `create_query_tag_rule`, `update_query_tag_rule` and `delete_query_tag_rule` (with `mcp.allowWrites` and a token) and `list_query_tag_rules` and `test_query_tag_rule`. - **Custom Views count each Default Trace event once** ([#5742]) - A Custom Views measure over the Default Trace events (`deftrace_duration_us`) counted every stored row, so an event stored twice (rows written before the upgrade, or written again after the collector's state was reset) was counted twice, while the MCP `get_default_trace_events` reader, the viewer and Lite showed it once. The measure now keeps one row per event, using the same key as the readers (the event's columns plus its sequence number), and keeps the earliest stored copy so a time-series panel shows the event in the hour it was first collected.

- **Lite's size-triggered database reset no longer pauses collection while it compacts the month's archive** ([#5771]) - collection used to wait for the whole reset including the monthly parquet merge, minutes by month end; it now waits only for the export and file swap, and the log records how long.

- **Lite saves webhook URLs of any length Windows allows, and says so when a save fails** ([#5772]) - Lite stored webhook URLs, the generic webhook headers and the PagerDuty routing key through a library that refused any value over 512 characters, and the Settings window gave no sign when a save was refused. Lite now writes these values to Windows Credential Manager directly, so a value of up to 1,280 characters (the Windows limit) saves and reads back, and entries saved by earlier versions still load. A save that fails now shows one message after the settings are written, naming which webhook or SMTP password was not saved (or not removed, when a box was cleared) and why, and the log records the key name and length but never the value.

- **Archive export lock** ([#5790]) - After Lite had been closed for a while, the first archive pass could keep the local database busy long enough that collection and other background writes gave up waiting for it; the archive now reads a large table in short slices, so those writes get in between.

- **MCP tool count** ([#5791], [#5722]) - The tool count in the Darling and Lite MCP server instructions now matches the tools the server actually lists, and says which setting is off when the write tools are not served. The instructions no longer name write tools the server does not serve. Before, it gave the full catalog count even when the write tools were off.

- **System.Security.Cryptography.Pkcs is pinned to the patched 10.0.13** ([#5803]) - Microsoft.Data.SqlClient 7.1.1 pulls in Pkcs 9.0.18, which two new advisories cover (9.0.0 to 9.0.20 and 10.0.0 to 10.0.12), so a vulnerability scan of the Darling service flagged it and every restore printed NU1902 and NU1903. The Darling service, its analysis libraries and the deprecated Installer now reference the patched 10.0.13 package directly. Lite and the Darling Viewer never use that package: their self-contained builds ship the .NET runtime's own copy, and this release builds them with SDK 10.0.402, which carries the patched runtime 10.0.13. The framework-dependent Viewer build uses the .NET 10 Windows Desktop runtime installed on the machine, which needs to be 10.0.13 or later.

- **A release no longer publishes the Linux tarball and container image before the Windows signature checks pass** ([#5805]) - the Linux release assets and the ghcr :latest image were published in parallel with the Windows build, so a release whose signature check failed was left half published. They now publish only after the Windows build, signature checks included, has succeeded.

- **Query Store history for one query no longer reads its whole database** ([#5816]) - `get_query_store_query_history` read every interval row of the query's database in the window and filtered on query_id, because no index on the interval table led with query_id; a read took up to 28 s on a large store. The service now builds an index on (server, database, query_id, first execution time) in the background after start, one partition at a time without blocking collection, and the read seeks only that query's rows ([#5807]).

- **Rollup coverage floors no longer cost a cold sort on reads** ([#5818]) - the coverage probe behind the trend, top-query and health reads re-measured every rollup view's floor inline with a `min(bucket)` sort of its compressed oldest chunk (about 10 s on a large store) whenever its cached floor was two hours old, and read the three raw tables on every probe. Floors now come from the oldest chunk's catalog range start when a bucket sits there; other views are measured one at a time in the background and logged with the reason, and raw-table floors are cached and checked on every read, so a deleted or backdated row is seen at once. A view keeps its last floor while it is re-measured, and a view with no floor yet is measured on the read that needs it; until a floor is measured the answer is not cached, so the next read picks up the measured floor. A raw-table floor is read again as soon as raw retention drops its oldest chunk ([#5808]).

- **get_query_store_top and the viewer's Query Store grid read the window once per call** ([#5827]) - when WAITFOR statements crowded the top of the ranking, a Query Store top read ran its statement up to three times, each time re-reading the server's whole window from the interval table; it now runs once, returns the same rows, and looks up query text only until the page is full.

- **Query Store regressions read the per-interval table instead of re-sorting eight days of raw rows** ([#5826]) - get_query_store_regressions and the viewer's Regressions grid deduped raw Query Store snapshots on every call, which took 17 s on average and up to 37 s for a 24-hour window on a large store. Both now read query_store_interval_wide for windows up to about 46 hours, with every execution outcome counted as before, and fall back to raw otherwise. The wide interval table now keeps 10 days instead of 9, and the regressions payload names the tier that answered in history_source.

- **Collection log records each scheduled analysis pass, and skipped-slot rows can name it as the cause** ([#5828]) - The analysis pass runs inside the fleet collection slot, but nothing recorded its length, so slots it held showed up as "no single cause" or as a fleet-slot wait. Each pass now writes an `analysis_pass` row (status `ANALYZED`, `ABANDONED`, `ERROR` or `SKIPPED`) with its duration, findings count and PLAN_REGRESSION read time. Collection health and run counts leave the row out. Skipped-slot rows now name the previous analysis pass as a cause, say how many fleet slots analysis passes held, and say "every collector that lost a slot" when the slot counts tie. The module name map refresh no longer rewrites rows that did not change, so a refresh over unchanged rows writes almost no WAL instead of a new copy of every row it re-read.

- **Slow-read rows record the window a read ran with, its default included** ([#5830]) - a call that left `hours_back` out, and `get_collection_health` with its fixed 7 days, recorded no window in `get_slow_reads`, though both reads were bounded. Windowed reads now record the window they read, `get_finops view=storage_growth` records the 30 to 90 days it reads, `get_finops` views that read the newest snapshot no longer record a 24-hour window they never read.


- **Custom Views panels grouped by object name no longer sort a whole day of procedure statistics when the module map is current, and raw panels too large for the time limit are refused up front** ([#5832]) - a raw-route panel with an object_name dimension ranked every procedure_stats row of its window before reading the facts, which took 5 s or more on large fleets and could reach the timeout; it now reads module names from the module map plus the procedure statistics since the map's last refresh (a stale map keeps the old query), and a query_stats panel read raw past 15 million rows, or a procedure_stats panel past 40 million rows, is refused with a message naming the estimate, the limit and a window that fits.

- **Plan regression reads no longer re-read three open days of Query Store intervals, and on-demand calls reuse the candidates for one analysis cadence** ([#5817]) - The PLAN_REGRESSION read took closed days from stored daily totals but read every interval row of the last three days again for every server on every pass. The hourly builder now also builds the open days as partial days, up to a watermark three hours before the current hour. For every built day the read takes the stored totals and reads only the interval rows after that day's watermark. An analyze_server or get_analysis_facts call with no as_of reuses the scheduled pass's plan regression candidates for up to one analysis cadence (30 minutes by default), and an analyze_server call saves the findings it builds from them. The scheduled pass always reads fresh. Every plan regression read, including the full-window read a server uses before its days are built, raises its work memory to 64MB for its own transaction, so neither read sorts to disk. Migration V185 adds the partial-build columns and moves the late-row trigger's bound to two hours before the current hour.

- **A slow Query Store database no longer holds up collection** ([#5831]) - a database whose Query Store was slow to answer could hold the query_store collector for minutes, in its runtime-stats read or in fetching its plans afterwards. Each database's runtime-stats read now has a 30-second budget: a database that runs out of time keeps its watermark and is read again on the next run, with nothing lost or written twice, and the other databases are collected as usual. The timed-out database is named in collection health as "<database> (timed out)", also on a server with only one database, where the run is recorded as an error. Each database's plan fetch now also has a 30-second budget per run: a database that is slow to return plans asks for fewer at a time, measured from its previous run, and any plans it did not get are fetched on later runs.


- **Retention Held now fires for held retention policies on continuous aggregates** ([#5859]) - The retention-hold read counted chunks under the aggregate's view name, but the chunks belong to its materialization hypertable. So every aggregate policy showed 0 chunks and no ratio in `get_store_metrics`, and the Retention Held alert never fired for one. The read now counts the materialization hypertable's chunks.

- **get_collection_health reads its week of collection history from an hourly rollup** ([#5829]) - The per-server read took 8 to 10 s in the field because it aggregated every run of the 7-day window, and its exact p95 forced a per-collector sort. Darling now keeps an hourly rollup of the collection log in a new store table, kept for about 7 days and filled a day per hour after the upgrade. The read takes closed hours from the rollup and the rest of the window from the raw log. On a planted 1-million-row server the read went from 1.8 s to 0.28 s once the rollup caught up. p95_duration_ms is now the upper bound of a log-spaced duration bucket, never above the max and up to 47% above the exact value. The sweep's peak-cycle figures charge the bucket's lower bound, so bucketing alone never raises a BODY_OVERRUN, and peak_cycle_note says the p95 is bucketed.






- **The Query Store compose rollup stops retrying a failing hour every tick** ([#5871]) - A build that fails is now retried next tick (under a 240 s timeout after a statement timeout), then once a day after 3 failures in a row. get_store_metrics lists such hours, and a Compose Rollup Hours Stuck self-alert fires while any hour waits a day between attempts.




- **PR test selection no longer falls back to the full suite when the nightly failed on an unrelated job** ([#5954]) - The pin step now takes the newest complete test map whatever the nightly's result, and a second, map-only build runs mid-day so the map is rebuilt twice a day (06:00 and 14:00 UTC).


- **The plan regression drill-down no longer reads two weeks of Query Store rows per server** ([#5957]) - Each analysis pass's PLAN_REGRESSION drill-down read every Query Store interval row a server had in the last 14 days to find five queries, which kept the store's disk busy and brought some drill-downs close to their 30 second timeout. A new index on the latest Query Store interval table, built in the background after the service starts, lets it read only those five queries' rows.

- **The 24-hour Query Store top queries read touches fewer blocks on servers with short intervals** ([#5815], [#5882]) - On a busy store the default 24-hour `get_query_store_top` read pulled yesterday's whole partition of Query Store rows and threw most of them away, up to 38 s on the largest store. The read now sizes its lower time bound to the longest interval the server has reported (3 hours at the default 60 minutes, instead of 26) and keeps the 26 hours whenever that length is unknown; the Queries grid in the Viewer reads the same way.


- **Ring-buffer collectors no longer fail forever on a deadlock involving a table or index with `&` in its name** ([#5948]) - A deadlock on a table or index whose name held `&` made the deadlock, blocked-process, client-timeout, long-query and system-health collectors fail on every run with "Cannot insert the value NULL into column 'ring_buffer'" until the session was restarted. Both products now escape the stray `&` before reading the buffer, and if a buffer still cannot be read the collector reports its size and SQL Server's own parse error instead.


- **Darling no longer checks PostgreSQL targets for missing SQL Server capture sessions** ([#6042]) - those sessions never exist on PostgreSQL, so every pass scanned the whole collection log to find nothing; large PostgreSQL fleets lost hours of store time a day

- **Module map repair runs once a day, not after every purge pass** ([#6044]) - a purge pass stopped by its time budget brings the next pass forward (#5592), and each pass re-ran the 30-hour module map repair, 13 to 17 GB of reads each time on a large store. The repair now runs at most once per 24 hours, and a failed one is retried on the next pass.

- **PostgreSQL statement-text due check reads one server's rows through a new index** ([#6043]) - The check that decides whether statement text is due walked back through every other server's newer rows, up to 6.8 s a call on a 50-server store. A `(server_id, last_seen)` index, built in the background after the service starts, lets it read only its own server's newest row.




- **The docs give the right MCP tool counts, and say what a support subscription gets you** ([#6060]) - the edition comparison said Darling serves 202 MCP tools and the MCP page said 204. - **`--backfill-rollups` runs on Linux** ([#6071]) - The verb, and `--collapse-legacy-slices` and `--recompress-plan-dim`, refused on every non-Windows host, although only a managed store's DPAPI credential needs Windows. - **The day-grain Query Store daily rollup fills again** ([#6070]) - `query_store_stats_daygrain_daily` refreshed one day per run, and its job could run before its parent's, so it read a day the parent had not written yet and never came back to it. It stayed empty and retention on `query_store_stats_interval_daily` was held forever. Its window is now one day wider, existing stores converge at startup, and startup refreshes the days it missed.

- **Darling fills a small rollup floor gap by itself** ([#6081]) - When a few raw rows arrive too late for the hourly refresh, the rollup above them starts after them, and the coverage gate holds the raw purge until someone runs `--backfill-rollups`. - **The viewer's "darling.json not found" hint now points to the right file** ([#6103]) - The hint told every machine to copy darling.sample.json, which holds service settings and not the store connection, so a viewer on another machine was sent to the wrong file. It now says where the viewer looked, to create the file from the sample on the service machine, and to run `--export-viewer-config` on the service host and copy its folder beside the viewer when the viewer is on another machine.

- **Job History sorts Duration by length and shows the full Message** ([#6105]) - The Duration column sorted by its text ("9s" above "5h 45m") and the Message column cut long text with no way to read it. Duration, Step and Retries now sort by their numbers, and hovering a Message shows all of it. - **A screen reader or UI test tool can open a server from the sidebar or an Overview card, and the alert badge and Settings inputs have names** ([#6138]) - Viewer and Lite sidebar rows and Overview cards now accept the Invoke action and open the server tab the way a double-click does; the alert badge reads "1 unread alert" or "N unread alerts"; every Settings input has an automation name. In the Viewer, Overview Needs Attention rows also accept Invoke, open on Enter, and are named for the server and why it needs attention.

- **An offline PostgreSQL target no longer reads as healthy** ([#6169]) - its empty panels and reads say it is offline, the fleet sweep keeps a target that was offline before a restart as offline, and Run all collectors now is off for it.

- **Five MCP reads no longer answer past the 32 KB response target without saying so** ([#6195]) - `get_perfmon_stats`, `get_blocked_process_xml` and `compare_analysis` were over the target at default arguments on a busy server (545 counters, 82 KB; 3 blocked-process reports, 54 KB), and `get_collection_health` with `full_detail` and `get_collection_log` with a large `limit` were over it when asked for more. Each read, on both Darling and Lite, now keeps the whole rows that fit and reports `truncated`, how many it returned of the total, and a `size_note` naming how to get the rest (a filter, a smaller `limit`, a shorter window, or one report by its `event_time`). Blocked-process report XML is never cut mid-document.

- **A collector the server keeps refusing is now tried less often** ([#6202]) - a permission-refused collector (for example `tempdb_stats` for a contained user on Azure SQL Database) wrote a PERMISSIONS row every interval in Darling and was skipped for the whole session in Lite. Both now back off while the same refusal repeats (up to hourly), return to the normal interval on the first success or a changed answer, and pick up a granted permission without a restart.

- **The PostgreSQL "Test an index" check now runs under its own login, with only the grants planning needs** ([#6191]) - the check ran EXPLAIN on stored statement text over the monitoring connection, and planning can run an IMMUTABLE function with constant arguments under the roles of the login that plans. It now signs in as a login set up like the remediation login (hypotheticalIndexUsername and hypotheticalIndexEncryptedPassword, an env: or file: reference) that needs CONNECT, USAGE and SELECT only. With no login set, the check is refused and the message says what to set up; it never falls back to the monitoring login. It tests SELECT statements only. Adds store migration V203 (two nullable columns on the server registry).

- **MCP reads name an Azure SQL Database server by its display name** ([#6188]) - an entry with a database set showed its `<host>:<database>` connection key in the `server` field and in message text of most MCP reads in Darling and Lite, in `get_pg_database_stats`/`get_pg_session_states` not_collected text, and on the Blocking, Query Store and FinOps Locking panels. They now show the display name; when two entries share a display name the key is shown so it can be passed back as `server_name`.

- **A row with an empty cell no longer costs every server its first delta after a restart** ([#6212]) - after a restart Darling reloads each server's last readings from the store so its first change figure is right; one stored row with an empty cell made it give up for every server. Empty cells now read as empty or 0, and a row with no key ids is skipped.

- **PostgreSQL collectors now work on older PostgreSQL targets** ([#6206]) - On PostgreSQL 10 to 13 targets, six collectors failed on every run and wrote an ERROR line to the target's log each time. Each collector now sends a query that fits the target's version: `pg_stat_statements` before 1.8 is stored from its old column names, newer-only columns are NULL, and `MATERIALIZED` is left out before PostgreSQL 12. `pg_write_stats` now also runs below PostgreSQL 14 with NULL WAL columns, and `get_pg_io_stats` says `not_collected` with the version on targets older than 16.

- **PostgreSQL target connections run no type-loading query of their own first** ([#6143]) - Npgsql read pg_type on the first connection of each PostgreSQL target, before the service checked search_path. Target connections now load no types, so the first statement on one is the service's own and a server's own search_path setting can't change how it reads.


- **Scheduled reports no longer log as alerts, and a failing channel no longer logs a warning every hour** ([#6219]) - the daily collector-cost digest, fleet-sweep rollup and analysis singles digest were logged as `ALERT TRIGGERED [Warning]`, and a notification channel that failed them (for example a Teams endpoint that timed out) logged the same warning again on every hourly retry. The three reports now log at Information as `SCHEDULED REPORT`; a failing delivery warns on the first failure and when the error changes, repeats at Information with a running count, reminds once a day, and logs one line on recovery. The collector-cost regression and digest also no longer treat the first hours of a new install as a baseline (a pair now needs 3 days between its first and last observation). Retries are unchanged.

- **The diagnostics bundle now finds a managed store that is starting or listening on another port, and says why when it cannot reach it** ([#6217]) - On a managed install the bundle tried the configured port once and reported `connect_failed` even with the service running. It now reads the store's own `postmaster.pid`: it connects to a live store on another port (with a warning), waits up to 20 seconds for one that is still starting, and otherwise reports `store_not_running`, `store_starting` or `data_directory_missing` instead of a bare `connect_failed`.

- **The web deadlock graph's process pane wraps its SQL handle note and property lines** ([#6228]) - The SQL handle note and the other lines in a process's detail pane ran in one line past the pane's right edge and were cut off, because the pane inherited the table cell's no-wrap setting. They now wrap inside the pane, and a long hex handle breaks anywhere, at desktop and phone widths. The desktop viewer already wrapped this text.

- **A quiet server's top-queries reads say "nothing ran" instead of "unavailable"** ([#6232]) - `get_top_queries_by_cpu`, `get_query_store_top` and `get_pg_top_queries` answered `unavailable` (check collection health) for a window in which the collector ran successfully and stored no rows because nothing executed. They now answer `empty` with `successful_runs_in_window`, and keep `unavailable` for a window with no successful run. Darling and Lite match; the Darling reads apply it only where the raw tier holds the whole window.

- **The PostgreSQL Activity grids show their values when a statement or log message has many lines, and the OS CPU grid shows rounded numbers** ([#6229]) - In the Darling Viewer, a statement stored with hundreds of line breaks made its Query Shapes row thousands of pixels tall, which pushed the row's numbers out of view and left the grid looking blank. Text cells in the Activity tab's grids are now capped at a few lines. The OS CPU grid showed raw doubles such as 130.67499999999 and bare disk byte counts; CPU, User and System are rounded to one place and Disk Read and Write show sizes. The captured-plans durations, the lock statistics Max Wait and the buffer usage percentages are rounded the same way.


- **Custom Views: a created, edited or deleted view reaches the sidebar and the list at once** ([#6243]) - after Create or Delete the sidebar kept the old list until a reload (the shell only re-read it on its 60 s poll). Every view write now refreshes the sidebar list straight away, and the Custom Views list no longer waits on the fleet read before it draws.

- **Darling Viewer: the Fleet Overview heading is no longer covered by its filter controls, and Help > About names the build** ([#6249]) - In a narrow window the "Needs attention only" checkbox was drawn over the "Fleet Health" heading; the controls now wrap to the next line instead. Help > About showed only "Version 3.10.0"; it now shows the commit the Viewer was built from when the build has one, for example "Version 3.10.0 (commit 0993a1441)", and just the version when it does not.

- **A command nobody picks up within 15 minutes now expires instead of running later** ([#6251]) - a pause, purge, undo or other command queued while the service was stopped used to run whenever the service next started, however late. The service now fails a pending command older than 15 minutes (on the store's clock) with an "expired" message instead of running it, and the Viewer cancels its own command when it stops waiting, unless the service has already started it, in which case it says the command is running.

- **The hourly store-size row no longer walks every database file** ([#6250]) - the store self-metrics sweep sized the whole database with `pg_database_size` every hour, which averaged 7.2 s and reached 77 s on a store with many chunks. The hourly row is now estimated from catalog page counts and marked `size_estimated` (in `get_store_metrics`, `get_store_host`, the web Store size cell and the Viewer status bar); one sweep a day still writes the exact size. The Store Disk Pressure alert text marks the store size it quotes as "~X (estimate)" when it came from the hourly estimate.


- **Plan correction and Query Store health skip a readable secondary replica** ([#6252]) - the two collectors only skipped availability group secondaries, so a cloud read replica was read on every pass and wrote the primary's rows again (69,358 plan correction rows in a day on one store). They now skip a database whose Query Store reports `readonly_reason` bit 8, as the Query Store collector does.


- **A failed webhook's stored error now shows the HTTP status only** ([#6241]) - the alert log's send error and the channel health text for a failed webhook post read `HTTP <status> <reason>`; the endpoint's reply body is written to the service log (Darling) or the app log (Lite). The Test buttons still show the body. A webhook or heartbeat URL written with a trailing dot, or as a NAT64 or IPv4-compatible link-local address, is now refused at save, and a heartbeat URL on a blocked address reports a fixed reason.


- **Diagnostics bundle no longer rewrites known names inside ordinary words** ([#6258]) - the final name check replaced a known name as a plain substring, so a name such as `data` also changed `database`. A name of 4 to 6 letters inside a plain run of ASCII letters is now left alone (`wholesales`, `administrator`). A name of 7 or more letters, a name with a digit or punctuation, and a name at an escape, case-change or digit-then-letter edge are still replaced, so `SALESDWFULL.BAK`, `SQLPROD_Full.bak`, `mainalpha-sql-01` and `SalesReport` are replaced.

- **A fleet Query Store panel reads the interval table for the servers that can use it, and raw only for the rest** ([#6115]) - one server that failed the interval-table gate (a newly enrolled server, or one with no Query Store collection) used to send every fleet panel to raw `query_store_stats`, which timed out on a large store; now only that server reads raw.


- **A fresh install no longer logs a console error on Alert History, FinOps and Job History** ([#6280]) - With no servers registered, `list_servers` answered with plain text, which the web API turned into a 400. It now answers the `empty` status like other reads, on Darling and Lite, so the pages show their empty text and MCP clients get a status they can read.

- **A change to a server's remediation login in darling.json now reaches a server that already exists** ([#6262]) - the two remediation keys were read only when a server was first registered, so editing them and restarting did nothing and said nothing. On every start, when both keys are in the file, they now set or replace the registered server's remediation login (and its "Test an index" login), with one log line per change. Removing the keys leaves the saved login in place; a one-key entry changes nothing and is logged that names the server and the secret's shape and never the login or secret. A server that is not in darling.json is not touched. `--validate-config` and the service log at start now also warn when the remediation secret is a DPAPI blob: operator remediation still opens it, but agent server actions (plan force, eviction, kill) accept only an `env:` or `file:` reference. The README and sample file now say so.







- **The Overview Blocking & Deadlocking lane now shows a lone deadlock or blocking event as a visible bar, and hovering it reads 1** ([#6287]) - over a long window (for example Yesterday) one event was drawn as a bar under a pixel wide and the hover read 0 unless the pointer was within a minute of it, so a deadlock the Blocking/Deadlocks page listed looked missing. The bar and the hover reach now scale with the window in the Darling Viewer and Lite. Short windows draw as before.


- **"Sign in again" after a web dashboard session expiry now takes you to the sign-in** ([#6278]) - the link pointed at the page's own address, so a click did nothing until the page was reloaded by hand. It now always reloads the current page, which shows the sign-in form (or starts the SSO redirect) at the same address, so the page you were on opens again after you sign in. The address named in the server's answer is not used.

- **A triage link clicked in Teams, mail or another site now opens signed in** ([#6286]) - the session cookie is `SameSite=Strict`, so a link followed from another site arrived without it and showed the sign-in page even with a live session. A page request marked cross-site and started by a click, with no session cookie, is now answered with a small page that reloads the same address from the dashboard's own site, which carries the cookie; the path, query and `#/` route are kept. Script redirects and meta refreshes still get the sign-in page, and with no session the click still ends at the sign-in page. A Mute Rules link now fills in only the scope fields (never the reason, source, start or expiry) and shows a notice to check the form. HTML pages carry `Cross-Origin-Opener-Policy: same-origin`. The cookie setting is unchanged.
- **CPU scheduler collector counts offline CPUs and NUMA nodes correctly** ([#5657]) - The offline CPU count now comes from the schedulers SQL Server reports as offline, and the offline node count no longer depends on the node being named ONLINE. The dedicated admin connection node is left out by its state instead of a fixed node number.
- **Azure error 40615 names the firewall and your client IP** ([#5658], [#5674]) - When Azure SQL refuses a connection with error 40615, the message now leads with the server firewall and the client IP address Azure reported. It then adds that if a database-level rule in a user database already allows that IP, you should set the database for the server to that database.
- **A plain message when Windows is too old to start Darling and Lite** ([#5664]) - On a Windows without the updates .NET 10 needs for CET, the Darling service and viewer and Lite stop at start with a cryptic runtime error. The Darling install script now recognises that message in its pre-flight check and stops with a plain message to install the Windows updates. The Darling and Lite READMEs now explain the problem and a short-term workaround.
- **A web page you leave mid-read no longer logs a failure** ([#5679]) - When you leave a Darling web dashboard page while it is still reading, the service used to log a store timeout as an Error and answer 500 for a request nobody was waiting on. It now treats that as a cancellation and writes only a debug line.
- **Blocking snapshots no longer merge two separate waits of one pair** ([#5766]) - Two separate short waits of the same blocker and blocked session, started less than 2 seconds apart, were counted as one wait when read from blocking snapshots. They now count as two.

- **Default trace events no longer time out on small servers** ([#6311]) - The default trace collector sorted its result on the server, and that sort asked for a 57-75 MB memory grant to return a few dozen rows. A server with less query workspace memory than that left the collector waiting for the grant until its 60 second command timeout, so the cycle failed with "Execution Timeout Expired" and collected nothing. The query no longer sorts (the collector orders the rows itself, newest first, as before) and runs single-threaded, so it requests about 1.5 MB.

- **Azure SQL Database: a connection outage is no longer logged as a missing XE session, and master is no longer a failed database** ([#6312]) - with every user database refusing connections during a firewall outage, the `attention` row was logged as a missing XE session with master's "session is not running" text; the connection failure now wins. The `attention` and `blocked_process_report` collectors skip master, so it no longer counts as a failed database. The blocking snapshot tests for a user process with `is_user_process`, so system sessions above 50 stay out of it.

- **MCP answers no longer misstate sub-millisecond CPU, the monitor's own xmin, the tag window minimum or a two-session move** ([#6305]) - `analyze_server` advice shows per-execution figures under 1 ms in microseconds instead of "0 ms"; `get_pg_xmin_horizon` no longer reports a holder at xmin age 0 (the monitor's own session); `get_resource_use_by_tag` says its query_store section needs hours_back 24 or more; `compare_analysis` bands a near-flat baseline against a noise floor (5% of the mean, 2 sessions for session counts), so a two-session move is no longer "worse" at 25 sigma.

- **The Admin Agent changes list names the server, Admin tabs wrap, and the server page header stays current** ([#6310]) - the Agent changes list showed "Server <id>" instead of the server's name, and its Kind column showed the raw `session_kill` where it now reads "kill session". The Admin tab bar wraps so every tab is readable at 1280 px, and the server page header tiles no longer lag the charts after a tab click. The Server actions switches lock with a "Saving" line while a change is in flight; before, a click during the change was silently dropped.

- **The web dashboard's sidebar no longer takes 260 px of a phone-width window** ([#6315]) - at 768 px and narrower the sidebar becomes an overlay menu opened from a new top bar, and the page content takes the full width with a 16 px side gutter. The fleet and Availability Group tiles wrap when their column is narrow, long selects shrink to their card, and the footer wraps.

- **The plan regression finding now also catches queries whose runs time out or fail** ([#6309]) - The finding counted only runs that completed, so a query that started timing out or erroring while its successful runs stayed cheap was never reported. It now flags a query whose timeouts or errors in the last 24 hours rise to at least twice the earlier rate (or appear where there were none, with at least 3 runs), in Darling and Lite, says so in its advice, and lists those queries with their recent and baseline timeout and error counts in the finding's drill-down next to the cost offenders.

- **The Query Store collector no longer joins Query Store views in one statement** ([#6257]) - the payload read and the text fetch now read each Query Store view once into its own temp table and join the temps, so a primary no longer merges each view's in-memory data in the middle of a join. The collected rows are unchanged.

- **A server's host can no longer send Windows credentials over a named pipe** ([#6352]) - adding or changing a SQL Server's host to `np:`, `lpc:`, `admin:` or another protocol prefix (other than `tcp:`), or to a path starting with `\` or `/`, is now refused in the web dashboard, the MCP tools, the command line, the Darling Viewer and Lite, including bulk add and settings import. Separately, every connection to a monitored SQL Server (the Darling service, its remediation login, Lite, and both Test Connection paths) now uses TCP only: a host with no protocol and no port used to fall back to a named pipe over SMB after TCP failed, sending the process's Windows credentials to a host with 1433 closed. A host on this machine (`localhost`, `.`, `(local)`, `(localdb)`, `127.0.0.1`, `::1` or the machine's own name) and a host with an explicit protocol in an existing row are left as they are. Stored hosts are not rewritten.

- **The service and Lite no longer follow a mirroring partner a monitored server names** ([#6365]) - A server in a database mirroring session could name its partner, and SqlClient would connect to that name when the principal stopped answering, falling back to a named pipe over SMB with the process's Windows credentials. The service and Lite now ignore a server-provided failover partner, so a mirrored database is no longer followed to its partner; the partner is monitored as its own server.

- **The default trace collector no longer logs a spurious "unexpected end of trace file" error on SQL Server on Linux** ([#6381]) - it now waits out the few seconds the server needs to grow its trace file and retries the read, while a missing or corrupt trace file still fails as before.

- **File I/O no longer invents reads and writes on Azure SQL Database Hyperscale** ([#6438]) - Hyperscale reports extra storage-layer file rows (database_id 0, shown as duplicate data_0, duplicate log and "Unknown" rows) that shared a delta key with the real files, so every minute the grid showed reads and writes that never happened and the latency chart drew an "Unknown" line. The collector now keeps only the connected database's own files, one series per file with deltas of 0 when nothing moved. Lite and Darling both change; General Purpose and SQL Server are unchanged.

- **Lite's Top Queries by CPU no longer ranks the whole procedure archive** ([#6096]) - the read looked up each statement's procedure with a window over every archived procedure row, so it slowed as the archive grew instead of following the time window; it now looks up only the procedures of the ranked statements, with the same rows. Darling's read is unchanged.

- **The web Job History Category list shows only the selected server's categories** ([#6443]) - the list kept every category seen on any server, so one server's page could offer another server's categories. It now lists only the chosen server's, and picking another server resets Category to All Categories.

- **Editing or adding a server in the web dashboard right after another edit is no longer refused as busy** ([#6450]) - the guard that allows one server edit or add at a time could, on a busy machine, still be held for a moment after the previous edit had been answered, so the next edit or add was refused with "busy" (429). The guard is now always free before the answer is sent.
