## [3.10.0] - 2026-10-08

### Important

- **Upgrading from 3.9 runs the Darling store migrations V158 through V170 on the service's first start** - they are almost all new tables that start empty or one-row setting columns: the install id's record of the store's cluster and database (V158, V159), a collector run time table (V160), per-day summaries for Query Store and plan regressions (V161, V168), the store's own slow-read and statement history (V162, V163), an hourly row-count ledger for query stats (V164), the password key and saved-password tables (V165, V167), a PagerDuty auto-resolve setting (V166), AWS role columns for monitored servers (V169) and an hourly PostgreSQL I/O rollup (V170). None of them rewrites a large table or needs an offline window. The two that read existing rows work on the registry of monitored servers and the notification settings, one row per server or one row in all: V167 records one row per saved old-format password, and V169 adds columns and a check constraint to `config.config_monitored_servers`. V166 adds a column with a constant default, which PostgreSQL 11 and later does without rewriting the table, and V168 adds a trigger to `collect.query_store_interval_latest`, which takes a short lock and rewrites nothing. No maintenance window is needed.

A tab load slower than 3 seconds logs its phase split, times the baseline-comparison read as a store read, and names every tab.
- **Two services starting against one PostgreSQL store no longer fail each other's role provisioning** ([#5566]) - the role and privilege batch that runs at start, and the reload's statement_timeout re-assert, failed with "tuple concurrently updated" when a second service ran the same statements at once. That left the viewer and MCP roles stale until the next start. Both now take an advisory lock first, so the second waits for the first. The wait is bounded at 12 seconds at start and 5 seconds on a reload. If something else holds the lock for longer, one warning names the session that holds it and the write runs without the lock. A write that fails because the other session wrote the same row first is run again up to twice. The self-managed store's password-rules step takes the same lock.
- **The Query Store interval purge finishes on a large store** ([#5572]) - On a large store, the purge of the wide and latest Query Store interval tables never removed anything. It deleted a whole day in one statement, and that statement timed out on every pass. The purge now deletes in batches of up to 50,000 rows and commits each batch. A batch that times out is retried at half the size. Each batch starts where the last one ended, so a backlog drains over a few passes. The purge of the plan content table now also starts each batch where the last one ended.
- **Running Jobs in Lite and the Viewer, and the get_running_jobs tool, list only jobs the collector's latest successful run found** ([#5554]) - A snapshot older than the long-running-job alert's bound is not listed. That bound is three missed cycles at the server's running_jobs cadence, at least 10 minutes. When that hides the jobs, the tab and the tool say collection is not current and give the time of the last good collection. A failed read shows "The running jobs could not be read". It no longer shows "No SQL Agent jobs are running." The empty grid says so in words. The column headers are wide enough to read.
- **Each File I/O chart draws its own ten files, so Read Latency no longer goes blank when logs are busiest** ([#5554]) - The read chart takes the ten busiest files by reads and the write chart the ten busiest by writes. Each chart draws its files exactly as the read ranked them. The read says which ten each file is in. The ranking puts NULLs last and breaks ties by file name the same way in the DuckDB and PostgreSQL stores. The Overview I/O Latency lane weights read latency by reads.
- **Lite's own queries no longer top Top Queries by Duration or Query Store by Duration** ([#5554]) - That covers its Query Store probe, its plan and text fetches, its connect-time detection query and its failed-jobs and job-step reads.
- **The Live Snapshot button and the Get Actual Plan buttons in Lite judge statement text and plans with the screens' statement filter** ([#5554]) - The Live Snapshot button and the six Get Actual Plan sites use the same statement filter as the screens. The filter runs off the UI thread. A plan the filter withholds is refused on save. The test that lists every place Lite opens its own server connection now covers all of Lite, with a reason for each file.
- **Select All in the Databases filter, or ticking every collected database, now means All** ([#5554]) - Databases collected later are then included. A filter for databases that are not collected yet stays a filter when the read of collected names fails.
- **Empty server-tab grids in Lite and the Viewer say why they are empty, and screen readers get names for toolbar combos and plan operators** ([#5554]) - Empty Trace Flags, Running Jobs and Query Store Regressions grids say why. Configuration and Index Analysis headers and notes read in plain words. The toolbar combos and plan operators have names for screen readers. The disabled Compare box says where it works. An empty comparison period says so. The Repro script's Generated line is in UTC.
- **The web dashboard's footer time, Job History messages, saved views, offline fleet cards and service log read correctly** ([#5554]) - The footer Updated time follows the page's own latest load and keeps its last good value when a poll fails. A read narrowed to its limit and then answered is not a failure. Job History messages are readable and open in full. A saved view opens on its server and says whose pick the scope is. It says all servers when its own setting is All. The Databases popover closes on a tab change. A server dark past the fleet read's 48 hours shows the real time of its last collection on its card. Availability Group counts and several empty-state sentences read correctly. A failed web request leaves exactly one service-log line, and it names the server and the cause. A failure before sign-in from one address is logged once per ten minutes. An unknown server is reported as not found. A registry lookup that fails no longer reads as "not registered". The offline-age read is cached and holds one pooled connection at a time.
- **The module map refresh no longer holds back the collectors at service start** ([#5580]) - On a large store, the start-up module map refresh read procedure_stats for about 55 seconds before any collector started, on every restart. The start path now only creates the table. The refresh runs after the collectors start, from the hourly tick and the daily purge.
- **The module map's daily refresh no longer sorts every raw procedure_stats row** ([#5584]) - On a large store the refresh read 10.6 M rows to find 21,636 handles. It took 35.5 s, most of it a sort that spilled 2.19 GB to disk. It now groups the rows by handle and names first. On a copy of that store the same window ran in 8.3 s with no spill. The map and its watermark come out the same.
- **The first Query Store read after a big retention drain is no longer slow** ([#5585]) - After the retention purge removed the oldest Query Store interval rows, each server's first floor read walked every dead index entry. On a large store that took 19.6 s for one server. The purge now runs that read once per server in the background when it finishes, one server at a time. It runs only when the purge deleted rows or failed. A pass that only drops whole day partitions skips it, because a dropped partition takes its index entries with it. It skips a server whose table is locked.
- **Web charts draw at the panel's real width** ([#5590]) - Line and scatter charts were stretched sideways to fit the panel. At 2,000 px their axis text was drawn at about twice its normal size, and the bar chart's labels grew with the panel too. All three now draw at the panel's width, and a resize redraws them with their zoom kept. Time labels follow the width, so none overlap on a phone or repeat on a short zoomed window. Across a clock change, each time label shows its time zone. The bar chart sizes its columns to the text, and printing scales each chart to the page width.
- **Autovacuum on the Query Store interval tables can finish again** ([#5593]) - The BRIN index on their collection time asked for each new range to be summarized. After a large retention purge, those requests cancelled the running autovacuum about every 2 minutes, so dead rows piled up. The index no longer does that. The service now summarizes new ranges once an hour, and it gives up rather than cancel a vacuum.
- **The Darling whole-tree guards CI job no longer fails after every test passes** ([#5598]) - WPF left a process-exit handler for each test thread that used a bound control. Each one waited out a 300 millisecond timeout, so the test process outlived the runner's 11-second exit window. The runner then forced exit code 1 with no failed test. Both test projects now set the WPF switch that skips the wait. This is a CI-only fix: no product code changed.
- **"Collection Falling Behind" no longer fires in the first hour after every start** ([#5599]) - It fired minutes after a start. The alert now leaves out what was counted in the first 15 minutes after the service starts. A store that stays behind fires about 30 minutes after the start. A stall, a clock step, a pause ending or the launch guard's release does not give those minutes again. The alert text names the minutes it judged, and in the first hour the log line says "last N minutes, since the service started". Slots due while a server's connect run was still seeding its schedule are no longer counted as skipped.
- **A hung test shard names its test and keeps its logs** ([#5591]) - A shard that ran into the job timeout lost its log and its timing. The Darling and Lite test steps now have their own timeout under the job's, so the upload steps still run. The runner reports any test that has run for 5 minutes, and its output is uploaded. The nightly runs get the same report. One test waited up to an hour while holding a lock. It now gives up after 60 seconds.
- **One-day Custom Views panels on Query Store data read an hourly rollup, or are refused up front** ([#5588], [#5610]) - On a large store, a one-day panel read 8.46 M rows and took 55.2 s against the 60 s limit. Darling now keeps an hourly rollup of the Query Store wide table and reads closed hours from it. The answer is exactly what the wide table returns. A panel over the row limit is refused up front with the reason. A ranked panel reads its rows once only when that cannot fill the temp file limit. A rollup build waits only for an open write to the wide table that began before its hour was safe to build. A long wait is logged as a warning that names the session. A schema upgrade that cannot get its table lock in time logs every session that holds a lock on the store's tables.
- **Darling's hourly maintenance step over stored analysis findings no longer times out on a large store** ([#5626]) - The step that re-masks stored analysis findings paged the table with a sort over a full scan. On a store with 600,000 findings each page read about 1 GB and timed out. It now reads a fixed 16 MiB slice of the table per page, so a page costs the same however large the table is or however many findings match. On a test store a page read 2,048 buffers instead of 35,698 and took 22 to 43 ms instead of 202 ms. The two stages over stored alerts now read one server at a time through the alert log's existing index, and their pages are bounded too. No store migration.
- **Upgrade refusals no longer list the service's own files** ([#5627], [#5629]) - The pre-lock check listed about 1,740 files the service had extracted. It now trusts the service's account only in the folders and files the service writes. A refused existing install gets numbered steps to move to a new folder, with the service, darling.json and store kept. upgrade-darling.ps1 now runs on Windows PowerShell 5.1 from its staging folder. A new CI check runs both scripts over real 3.7.1 and 3.9.0 installs. The compose quickstart pulls the latest image.
