### Added

- **Column selectivity in schema tracking** ([#8798], [#8894]) - A new opt-in Darling collector, `column_stats` (off by default), keeps how selective each column and each leading combination of columns is, so `get_object_definition` can answer "how selective is this column?" without signing in to the server. Each column gets a `selectivity` (`selectivity`, `distinct_estimate`, `rows_per_value`, a `unique` or `low selectivity` label, the statistic it came from, when that was updated and the sampled percent), the table gets `column_combinations` (the leading two or more columns of each multi-column statistic, with the clustering key columns SQL Server appends to a nonclustered index marked `includes_clustering_key`), and `selectivity_status` says whether the numbers are `current`, `not_collected`, `not_read_yet`, `not_read`, a `precondition` with the statements that create the login's user and grant `SELECT`, `current_only` for a past `as_of`, or `unavailable` when the store cannot be read. The numbers come from the density vectors of the statistics, read with `DBCC SHOW_STATISTICS`: no table data, no histogram, no column value, and filtered statistics are never read because their filter text can hold literals. It runs hourly beside the 15-minute schema pass, reads only where `schema_objects` is on and in the databases both scopes cover, and re-reads only the statistics that are new, whose `STATS_DATE` differs or that were renamed, so a quiet database costs one catalog read. The first read of a database continues across runs if it passes its time budget, and a restore starts it again. Memory-optimized tables, XML, spatial and columnstore index statistics and statistics never updated are left out and counted. It needs `SELECT` in each database it reads, which lets the monitoring login read every row there, so the grant is never in the base script: `--grant-script` takes `--column-stats-databases <db>`, once per database, and prints the block only for the databases you name (with `--azure`, the database-level `GRANT SELECT` to run in each of them), and the service's `test_connect` checks it only when the collector is on with an explicit list. Under trace flag 9485 `SELECT` is not enough and the notes say so. The current rows of an availability group's database are the group's, so after a failover the new primary's reads replace the old primary's. Update times are shown in UTC (exact on SQL Server 2022 and later and on Azure. On earlier versions an hour off across a daylight saving change). Where the collector is off, `get_object_definition` adds only `selectivity_status`. The current rows are kept outside the age purge while any server stamped the database within the collector's retention, and a run removes a database it no longer has. The run records are kept 30 days like any collector. Darling only, SQL Server and Azure SQL Database. [Collector settings](docs/darling/collector-settings.md#turn-on-column-selectivity-column_stats) and [permissions](docs/permissions.md#column-selectivity-per-database-select-optional) have the setup.

- **`get_object_usage`: which tables, indexed views, procedures and functions in a database were used over a long window** ([#8784], [#8855], [#8875]) - A new MCP tool in Darling and Lite for deciding what is safe to decommission. Table and indexed view reads and writes are summed from the daily `index_object_stats` snapshots, not read from the latest one. Every counter reset inside the window is detected and use after it is counted: a restart, and a database that went offline and online, was restored or was attached. Use between the last snapshot before a reset and the reset itself cannot be recovered, so the reply reports that time as `blind_hours` and leaves it out of the covered days. Counters are tracked per answering instance, so nodes that take turns behind a listener each keep their own running difference, and one index that is dropped and created again is counted on its own without resetting the rest of the database. The newest last-seen time is carried forward across resets. Procedure and function executions come from Query Store. Rows are ordered with the candidates first (`Not used in window`, `Not executed in window`, then `Write-only`), and the reply says, per registration, how many days the evidence actually covers, how many resets it crossed and which instances answered. Objects whose use this evidence cannot show are `Not tracked` and are never candidates, with the reason in `caveat`: memory-optimized tables (which `sys.dm_db_index_usage_stats` does not record), inline table-valued functions, CLR modules and natively compiled modules (which Query Store attributes no executions to), and every module that did not run in a database Query Store holds no data for. A module that did not run is also `Not tracked` where the database's Query Store capture mode in the window was not `ALL` (`AUTO`, the default from SQL Server 2019, `CUSTOM` or `NONE`), because Query Store then leaves out statements it judges infrequent or cheap, and the caveat names the mode. It is `Not tracked` too where no stored health snapshot says what the mode was (the `query_store_health` collection off, failing or scoped to other databases), since the mode may be the default `AUTO`. Only a stored `ALL` makes it a candidate. A module that did not run where Query Store covers only part of the window says so in its `caveat`, counting the days that actually hold data so a gap in the middle of the window counts, and one created inside the window says how many of the days asked for it existed, and a procedure that did not run carries a caveat that one whose body only calls other modules shows no executions however often it runs. Object names are matched exactly, so a case-sensitive database's `Orders` and `ORDERS` stay separate. To support this, `index_object_stats` now records the `@@SERVERNAME` of the instance that answered each collection and whether the table is memory-optimized. Darling only: a new daily `object_inventory` collector keeps the list of procedures, functions and views per database, so a procedure that never ran is listed. A per-day module execution summary is copied from the daily Query Store summary and kept as long as `index_object_stats` (set that collector's retention to 400 days to cover a year), a copy that only ever adds, so a later rebuild of the source cannot take evidence away, and a retention that is lowered only removes module evidence after it has stood for 7 days, so a setting lowered briefly loses nothing. `object_inventory` runs under `index_object_stats`'s database scope, so the object list and the usage counters cover the same databases. Execution coverage is per database, so a database with Query Store off shows no covered days where its neighbours on the same server do. The server's ReadOnlyIntent registration (`:RO`) is read beside it, with table reads and writes summed because they are per instance, and module executions taken as the larger of the two reads because a database has one Query Store. Lite reaches back as far as its three months of retention and lists only the modules that ran. Views that are not indexed are not covered yet.

- **The web dashboard can limit token sign-in to loopback, or turn it off** ([#8735], [#8868]) - A new `web.network.oidc.tokenSignIn` setting takes `on` (the default, which changes nothing), `loopback` or `off`. It covers every token the dashboard's sign-in form accepts: the shared token, the `web.network.tokens` entries and the Viewer's web access group tokens. MCP tokens and OIDC sign-in are not affected. Under `loopback` a token signs in only from a loopback connection, a browser on the host or `kubectl port-forward` to the pod (the break-glass path when the identity provider is down), and network clients see only the identity-provider sign-in. Under `off` no token signs in anywhere, and the shared token is not required. The rule also applies to existing token sessions on every request. A change applies at the restart, and the restart also ends every earlier token session. A refused sign-in answers 403 before the form is read and is not counted by the sign-in throttle. A reverse proxy on the same host, or a service-mesh sidecar such as Envoy or Linkerd, can make every client look like loopback. Listing the proxy in `web.network.trustedProxies` helps only when it sends `X-Forwarded-For` with the client's address on every request. A sidecar usually does not, so behind one use `off`. Each start under `loopback` on an exposed dashboard logs a warning that says so. `off` needs OIDC that works on an exposed dashboard. When OIDC is not configured or is refused at start, or the dashboard is not exposed, the web dashboard does not start and one Critical line says why. An unknown value does not start either. A `curl` POST of the token to `/auth/login` works only where the mode allows. A store behind a front door must keep `on`, because the front door signs in to the store with its shared token over the network. Under `loopback` or `off` the front door reports that the store has `tokenSignIn` set to `loopback` or `off`. `--validate-config` reports the mode when it is not `on`, fails on an unknown value or on `off` without OIDC configured or an exposed dashboard, and notes `loopback` with an exposed dashboard. With `web.enabled` false it prints one INFO line and checks nothing.

- **Index Analysis flags large, busy heaps** ([#8880], [#8896]) - Darling's FinOps Index Analysis tab, on the web and in the Viewer, and `get_finops` view `index_analysis` now list a heap (a table with no clustered index) that has at least 1,000,000 rows or 1 GB reserved and at least 1,000 reads (scans and RID lookups) since the server started. Each one is a REVIEW row with rule `Heap`, index `HEAP` and no script, because choosing a clustering key needs a person. Its note gives the size, rows, reads and writes since the server started, explains what forwarded records and empty pages cost on a busy heap, and says how many nonclustered indexes reach it by row locator. The roll-up gains a Heaps column (`heaps` in `get_finops`), and a database whose only finding is a heap still gets its roll-up row. Heaps are counted there only, so the table, index, size, row, reclaim and workload figures are unchanged. Heaps nobody reads, such as staging tables, are left alone. The data was already collected, so nothing changes in the store or the collectors, and Lite is unchanged.

- **`get_object_usage` covers views that are not indexed** ([#8784], [#9181], [#9331]) - Reading a view that is not indexed moves only its base tables' counters, so until now such views were left out. Their use is now read from Query Store statement text. Each statement is parsed with ScriptDom, so a name in a comment or a string does not count, and neither does a CTE, a table alias, a temp table or a table variable that shares the name. A view a statement names is `Referenced`, with `referencing_executions` and `last_referenced_utc`. A name written without a schema matches the view under any schema, and names are matched ignoring case. A view read from another database by a three-part name counts for its own database. A scalar function a statement calls counts as a reference to that function, since an inlined scalar function gets no executions in Query Store, so the walk below reaches a view used only inside one. Query Store keeps the condition of an `IF` or `WHILE` as a statement of its own, and that parses too. On Darling, a statement that still does not parse is searched as text for the database's views, whole words only, and the row's caveat says so.
  - **Darling** keeps a per-day summary of the referenced names for as long as `index_object_stats` is kept, the same retention as the module summary, because statement text itself is only kept about a month. A new daily collector, `object_dependencies`, keeps each database's `sys.sql_expression_dependencies` under `index_object_stats`'s database scope, for 3 days, since only the newest capture is read. A database's newest list is never aged out, so a database whose capture fails for a few days (a lost grant, or the collector failing there) still counts its references, and another database's view it names does not read `Not used in window`. A dropped database's list goes once it is past the 3 days and the server's newest `database_states` capture no longer names that database. A server with no `database_states` rows keeps its lists. The tool walks it from everything in use, so a view used only through another view, an inline function or a scalar function is `Referenced` too, and `used_via` names the object it was reached from. The collector also keeps each synonym as a row of its own, its base object split into parts, so use of a synonym reaches the view behind it. A view that another database's view or module on the same server names by a three-part name is `Referenced`, with `used_via` naming that object and its database, so a reporting database built over another database's views does not make those views look unused. The summary keys each referenced name by one case fold, so two spellings of one name are one row a day, and keeps the spelling first seen beside it, so a view listed from the summary keeps its own spelling. A view another database names is found by reading only the rows of each database's newest dependency list that name another database, through a partial index. The summary read for one database seeks its own rows and the other databases' rows that name it, each on its own index, rather than reading every database's rows for the server. A statement that does not parse is split into words once, and kept that way in the scan cache, so searching it for the database's views is one lookup per view. The walk also reaches a procedure that only other procedures call, which Query Store shows no executions for. A view nothing reaches is `Not used in window` only when the database has statement text in the window, a stored capture mode of `ALL` and a dependency list. Otherwise it is `Not tracked`. The collector needs `SELECT` on `sys.sql_expression_dependencies`, the grant FinOps Index Analysis already asks for. Without it the database stores no rows rather than failing, and its views stay `Not tracked`.
  - **Lite** parses its stored statement text at read time. It keeps no object list, so it lists only the names statements read as tables that are not a known table, as views with a caveat that they could also be synonyms. The old system tables written without a schema (`sysobjects` and the rest) are left out by name, so a view such as `SysUserSettings` is still listed. A view no statement named is not listed.
  - An inline table-valued function a statement names, which Query Store attributes no executions to, is now `Referenced` rather than `Not tracked`. Each coverage entry has a `views` block that says how many statements were looked at, how many had no stored text and how many did not parse.

- **The TempDB Log Space alert and the tempdb Growth Fit alert** ([#8886], [#8887], [#8888]) - Every tempdb collection now also reads the tempdb log: total and used space, the reuse wait and the truncation holdup reason. At 50 percent used or more it also records the oldest active tempdb transaction and its session. The TempDB Log Space alert fires on `tempdb_log_space.threshold_percent` (default 80) and supports mutes and per-server overrides. The tempdb Growth Fit alert warns when a tempdb file's next autogrowth is bigger than the free space on its volume. Both work in Lite and Darling. - **`--set-login-password` saves one login's password again for every server that uses it** ([#9748]) - A new Darling verb, `--set-login-password --username <login> [--dry-run] [--config <path>]`, reads one password from stdin and saves it, sealed with the service's password key, for every server that uses that login, disabled servers included. It is for a store moved to a new host. The private half of the password key does not move with the dump, so no saved password opens there, and the move guide had the operator enter every password again, one server at a time, in the Viewer. The verb runs on Windows and Linux as the store owner, with the configuration lookup and the exit codes of `--reset-password-key` (0 done, 1 usage or configuration, 2 a store that cannot be reached or refuses the write). The password comes from stdin only, as one piped line or at a hidden prompt, and is never an argument or an environment variable. No output, error or log line carries it. Stdin must be one non-empty line of strict UTF-8. A second non-empty line, a byte order mark, a NUL byte, a stray carriage return, bytes that are not UTF-8 and a stream over the longest password are refused with a sentence that repeats no line. An argument the verb does not know is refused by its position only, and its text is never printed, because the likeliest stray argument is a password typed on the command line by mistake. Before it reads the password, the verb prints the store the configuration reaches and the password key the password will be sealed to, and a dry run prints the same two facts. It then prints one line for each saved password it covers, with the server, the login and `set` (`would set` in a dry run), `unchanged` or `skip`, each with its reason, and ends with the number of saved passwords it changed. A server's remediation login is covered when its name equals `--username`. A running service takes the new passwords at its next configuration reload, with no restart. The CLI, Linux and store backup pages describe it.

The upgrade never writes in `/etc/darling`. The health check watches the unit for 30 seconds, and `--health-seconds` changes that. Each upgrade leaves `upgrade-run.json` in `/opt/darling`, the record the Windows upgrade script writes, and the service stores it. The unit runs the service sandboxed, and the sample config has a `file:` store connection string and a `file:` SQL password. The files ship only in the linux-x64 tarball, so the container image and the Windows zip are unchanged. The steps are in "Install and upgrade with the scripts" in `docs/darling/linux.md`.
- **Darling `--edit-server` changes a registered server, and the start-up warning gives the command** ([#9765]) - The Darling service has a new verb, `--edit-server <server name> --set <field>=<value> [--set ...] [--config <path>]`, on Windows and Linux. It changes a registered server's settings in the store. A headless host with no Viewer, no web dashboard and no MCP write surface can now change a server. The verb runs the same parse, connection test and store edit as the MCP `edit_server` tool. It works while the service runs, and the service reloads the registry on its next config poll. The settable fields are `name`, `host`, `port`, `database`, `auth`, `username`, `encryptMode`, `trustServerCertificate`, `readOnlyIntent`, `multiSubnetFailover`, `queryStoreReplica`, `monthlyCostUsd` and `enabled`. The exit code is 0 for an updated or unchanged server and 1 for any answer that wrote nothing. The start-up warning for darling.json values that disagree with the registry is now one line per server, for up to 10 servers, and one more line names the rest. Each line names every differing field with the file's value and the store's value. It also gives the `--edit-server` command that applies the file's values, written for PowerShell on Windows and for bash or zsh on Linux. A value that cannot be pasted into a command gets no command, and its line says to run `--edit-server` by hand. Lite's `edit_server` MCP tool now refuses a name that more than one server answers to, as Darling's does. It names each candidate's server id, and a retry passes it as `id:<server id>`. The verb is documented in `docs/darling/cli.md`.

### Changed

- **The exporter retries a store connect timeout once** ([#9578]) - A new connection to the local store sometimes stalled for the 30 s connect timeout and failed the run, and the next run was fine. The open is now retried once on that error only, with one warning line on stderr.

- **The exporter can send `pg_log_events` and `pg_buffer_usage`** ([#9519]) - `pg_log_events` was gated on a schema version no store could reach, so no export ever read it. The gate is now schema 239, the rung of the newest change to how the collector parses a log line, and the keep-only column list is unchanged. `pg_buffer_usage` joins the optional registry as a candidate event table. It holds buffer counts and catalog names only. Neither table is read unless a run names it.

- **A failed export prints the whole exception** ([#9351]) - The exporter printed only the exception message, and a bare "The operation has timed out" can come from a connection open, a read or an upload. The whole exception now goes to stdout, and the one stderr line gains the exception types.

- **The threshold override store parses the global threshold row with `JsonElement.Parse`** ([#9076]) - The old form built a `JsonDocument` and never disposed it, and analyzer rule CA2026 failed a downstream Linux build of the exporter tests on that line. Behaviour does not change.

- **The exporter now exports store columns its hand-written reads used to drop, and a test fails when a new store column is left out** ([#9069]) - `query_stats_hourly` and `procedure_stats_hourly` carry each plan's DMV attributes as of the hour's last sample (the per-execution `min_`/`max_` pairs, creation or cached time, handles, statement offsets, lifetime totals, plan size. These are lifetime values since the plan was cached, not the per-sample `worker_time_max` deltas), `pg_statement_stats_hourly` has `database_name`, `query_store_stats` has `interval_end_time_utc`, `pg_statement_text` has `own_entries`, and five other hourly tables gained the columns their rollups left out. Row counts are unchanged.

- **The exporter's `query_stats_hourly` now has a `host_object_name` column** ([#9066]) - it holds the stored procedure or other module a plan-cache statement ran under, so an exported `query_hash` maps to its module without matching plan hashes. It is NULL for ad-hoc statements, and rows with different host objects stay separate even when the query and plan hash match.

- **The exporter may now export `attention_events` and `column_stats_runs`** ([#9057]) - the optional-table registry adds both as Candidates, and they stay off until a store's `optional-tables.txt` names them. `attention_events` exports every column, including `statement_text` and `client_hostname`, in clear, as ruled for the deadlock and blocked-process reports. `column_stats` is registered as Blocked, because its `text[]` column has no Parquet type mapping yet.

- **The exporter may now export `pg_lock_stats`** ([#9010]) - the table holds only numbers and lock states, and it is small, so the optional-table registry moves it from Blocked to Candidate. It stays off by default: a store exports it only when its `optional-tables.txt` names it. `pg_session_states` stays Blocked, because it carries usernames and client addresses.

- **The Darling store runtime moves to TimescaleDB 2.32.0, and the container and Helm store images are pinned to the exact tag** ([#8858], [#8863]) - TimescaleDB 2.32.0 carries a larger set of security fixes than usual, so the bundled Windows store runtime takes it. TimescaleDB 2.32.0 supports PostgreSQL only up to 18.6, and policy jobs fail on PostgreSQL 18.7 with this release (timescale/timescaledb#11038), so the runtime moves to 18.7 together with TimescaleDB 2.32.1. - **A Linux `--rollback` is recorded as its own row in the upgrade history, and its closing message says the rollback copy is used up** ([#9832]) - `upgrade-darling.sh --rollback` now records its own run as one more row in `collect.upgrade_runs`, which the build it puts back stores, so the newest row names the build that runs. The row ends `succeeded`, or `failed` when the restored build fails its health check. The closing message says that `/opt/darling.previous` is gone. Going forward again is a new upgrade. The message for a restored build that fails its health check says the copy is used up too. A record that cannot be written is a warning and never changes the rollback's result. Known limit: the row of the upgrade that the rollback undid can stay `in_progress`, when the rollback comes before that build's first 5 minute pass. The rollback's own row still names the build that runs.
- **Darling logs each large index the start builds, and a timed-out bounded Query Store index build is now recorded** ([#9833]) - After an upgrade, the first start now logs one Information line before each missing large index it builds, naming the index and its table and the most seconds collection can wait while it builds, and one line after it with the seconds the build took. An index that already exists, a table with no rows and the hourly pass log nothing new. The bounded Query Store index build can time out after a short earlier build in the same start. That timeout is now recorded, so the next start skips the build instead of trying it again and pausing collection for up to another limit. The timeout Warning of a build now names the limit the build ran under.
- **`install-darling.sh` and `upgrade-darling.sh` no longer refuse for a process in a container that runs from the container's own `/opt/darling`** ([#9836]) - `install-darling.sh` and `upgrade-darling.sh` no longer stop with "A process still runs from /opt/darling" because of a process in a container that runs from the container's own `/opt/darling`. The check after the stop no longer leaves the service stopped for such a process either. A process now counts only when it runs from the host's folder. The service under its systemd sandbox still counts.
- **On Linux the Darling service no longer watches the whole file system, so a first start under systemd says it is ready at once** ([#9839]) - Every host the Darling service builds now uses the folder that holds the binaries as its content root, not the working folder. Before, a systemd unit with no `WorkingDirectory` ran in `/`, and the service watched every folder on the machine for a changed `appsettings.json` before it told systemd it was ready. On a machine with many folders the first start could pass systemd's 90 second start limit and fail, and every Linux install held that whole-tree watch while it ran. `--contentRoot` and `DOTNET_CONTENTROOT` no longer move the content root of these hosts. `appsettings.json` is read from beside the binaries, so a console run started from another folder no longer reads one from its working folder.
- **The Linux page's scripted install and upgrade check the tarball's hash in a step of their own, before anything is extracted or run** ([#9843]) - The **Install** and **Upgrade** steps in `docs/darling/linux.md`, "Install and upgrade with the scripts", now open with a block of their own that checks the tarball against the hash on the release page (`echo "<hash>  <tarball>" | sha256sum -c -`) and says to go on only if it prints `<tarball>: OK`. The block that extracts the tarball and runs its script as root comes after it. A pasted block runs every line, so the check now sits apart from the root script it guards, and a failed check never reaches the extract. The bullet that explains why the check comes first points at the new block, says why the check is a block of its own, and says that a mismatch prints `FAILED` and you stop there. Docs only.
- **Darling on Linux logs an upgrade run as recorded once for each run and state, not every five minutes** ([#9845]) - After a scripted Linux upgrade, Darling no longer logs "Upgrade run ... recorded in the store" every five minutes for up to a week. `upgrade-darling.sh` never marks a run verified, so a succeeded run keeps its file until it is verified, failed or a week old, and each five-minute pass recorded the same run in the same state again. The line is now logged once for each run and state. A new state (`in_progress`, `succeeded` or `verified`) or a new run id, such as the run a `--rollback` records, is still said again, once. The file handling and the row write are unchanged, so the file stays until the run is finished and the history still holds one row for each run.
- **`--grant-script --host` prints the SQL login script by default on Linux and in the Compose container, and the Compose docs gain three fixes** ([#9846]) - `--grant-script --host <host>` with no `--auth` now prints the SQL login script (`CREATE LOGIN [<login>] WITH PASSWORD`) off Windows, on Linux and in the Compose container, where it printed the Windows account script before. With no `--username` it names the placeholder login `YourLogin` and says so. Windows is unchanged and still defaults to the Windows account script. An explicit `--auth` still wins on every platform, and `--service-account` given with no `--auth` keeps the Windows account script on every platform, because it names the Windows account to grant. The `--grant-script` usage text and help lines say the default for each case. The Compose docs changed in three places. The quick start, `admin.md` "Add a server" and `cli.md` give the Compose line as `--grant-script --host <host> --auth sql --username <login>`. `admin.md` "Compose upgrade" says a `ports:` list in `docker-compose.override.yml` is added to the release's list and shows `ports: !override` (Compose 2.24 or later) to replace it, with both of the release's ports named. The quick start says the `FATAL` and `ERROR` lines and the `timestamp` best-practice warnings in the first second of a fresh store's log are expected.
- **The docs say the init server's locale WARNING and the Compose health port Warning are expected, and name the Lite `.previous` copies** ([#9849]) - Three docs gaps from the 3.14.0 upgrade checks. The quick start says that on a fresh Compose store `docker compose logs store` also shows `WARNING:  no usable system locales were found` from the image's init server. It is expected. The network endpoints page, in "The health port", says the non-loopback bind Warning is logged at every start on Docker Compose with `listen` empty, and is expected. The release's compose file publishes no health port. Only the stack's own containers reach it, and a `ports:` entry you add decides who else can. The Lite guide's "Upgrade a headless Lite" section says the `<folder>.previous` and `<data>.previous` copies stay until the next upgrade deletes them in steps 3 and 4. The data copy is as big as the data folder was at the upgrade. The section gives the `Remove-Item` line that deletes both once a rollback is no longer needed.
- **The Linux and Compose docs say the first-start login failure is expected and the grant script's password placeholder needs replacing, and the Linux page says what `--check` skips and what `--rollback` needs** ([#9860]) - Four docs gaps from the 3.14.0 checks. The quick start's "Run on Linux" says the service logs `Connect failed, retrying in 59s: Login failed for user '<login>'` as a warning until the monitoring login exists. That is expected on a first start. Collection begins at the first retry after the login exists. The quick start also says the printed `CREATE LOGIN` has a `<strong password>` placeholder. Replace it with the password in `secrets/sql_password.txt` before you run the script. `admin.md` "Add a server" and `cli.md` `--grant-script` say the same. The Linux page's "Install and upgrade with the scripts" says `--check` stops after the pre-flight. Only the real run checks that no process is left after the stop. Only it runs the health check. Only it ends with the line that the config, the secret files and the keys in `/etc/darling` are as they were. The page also says that once `/opt/darling-new` is removed, `--rollback` needs the tarball extracted to `/opt/darling-new` again. It still needs `/opt/darling.previous`.
