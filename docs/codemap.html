Overview

This repository holds two products you can build and run. Darling is a headless collector service that keeps its data in PostgreSQL with TimescaleDB, and it comes with a WPF viewer and a web dashboard. Lite is a portable WPF app that keeps its data in DuckDB.

Both products collect data from SQL Server and answer questions through an MCP server for AI tools. They share code for collectors, alerting, notifications, analysis and plan analysis.

The Full Dashboard and the CLI installer are frozen in a zip file. Nothing in the repository builds them.

In numbers:

  • 23 projects (4 app, 10 library, 5 test, 4 tool).
  • 320 Darling MCP tools and 130 Lite MCP tools.
  • 318 store migrations. The newest is version 319.
  • 4998 test classes in 5 test projects.
  • 20 CI workflows.

To build, run these from the repository root:

dotnet build Lite/PerformanceMonitorLite.csproj
dotnet build Darling/PerformanceMonitor.Darling.Service/PerformanceMonitor.Darling.Service.csproj
dotnet build Darling/PerformanceMonitor.Darling.Viewer/PerformanceMonitor.Darling.Viewer.csproj

Darling service (collectors, scheduler)

The Darling service is the headless process that collects data. At start it reads darling.json, bootstraps the store, and then runs each collector on its schedule. Collectors that are shared with Lite live in a separate project, and the service runs them through its collector runner. The same process hosts the MCP endpoint and the web dashboard.

Folders: Darling/PerformanceMonitor.Darling.Service, PerformanceMonitor.Collectors

Start here:

  • Darling/PerformanceMonitor.Darling.Service/Program.cs: The host. Builds the service and starts it.
  • Darling/PerformanceMonitor.Darling.Service/DarlingWorker.cs: The main loop, split across the DarlingWorker.*.cs files.
  • Darling/PerformanceMonitor.Darling.Service/DarlingWorker.Collection.cs: How a collection pass is scheduled.
  • Darling/PerformanceMonitor.Darling.Service/DarlingCollectorRunner.cs: Runs one collector against one monitored server.
  • Darling/PerformanceMonitor.Darling.Service/DarlingConfig.cs: The settings that darling.json holds.
  • Darling/PerformanceMonitor.Darling.Service/DarlingCliCommands.cs: The command line verbs of the service exe.

Darling storage (PostgreSQL store, migrations, rollups)

This project owns the PostgreSQL store. It holds the numbered migrations and the schema generator. It also holds the store classes that read and write each table, and the rollups and retention tiers that keep the store small. A change to a table starts with a new migration in the list. The Darling export tool also lives here, because it reads the store and writes Parquet files.

Folders: Darling/PerformanceMonitor.Darling.Storage, Exporter/PerformanceMonitor.Exporter

Start here:

  • Darling/PerformanceMonitor.Darling.Storage/PgMigrations.cs: The numbered migration list. The newest rung is at the end of Scripts.
  • Darling/PerformanceMonitor.Darling.Storage/PgSchemaGenerator.cs: Builds the collector tables for migration 1 and later table changes.
  • Darling/PerformanceMonitor.Darling.Storage/RetentionTierRouter.cs: Decides which retention tier a read or a prune uses.
  • Darling/PerformanceMonitor.Darling.Storage/QueryTagRollupSql.cs: An example of a rollup and its SQL.
  • Darling/PerformanceMonitor.Darling.Storage/IntervalRollupCountGuard.cs: A guard that checks interval rollup counts.
  • Exporter/README.md: The darling-export tool, which writes Parquet files from the store.

Darling MCP

Darling answers MCP clients from the service process. Each tool is a public static method that carries the McpServerTool attribute. The web endpoints call the same methods, so the two surfaces return the same data. A write policy decides which tools can change anything, and each change is off until an operator turns it on.

Folders: Darling/PerformanceMonitor.Darling.Service/Mcp, PerformanceMonitor.Common/Mcp

Start here:

  • Darling/PerformanceMonitor.Darling.Service/Mcp/DarlingMcpHostService.cs: Starts the MCP endpoint and registers the tool classes.
  • Darling/PerformanceMonitor.Darling.Service/Mcp/DarlingCoreToolProfile.cs: The small set of core tools.
  • Darling/PerformanceMonitor.Darling.Service/Mcp/DarlingMcpTools.cs: A first tool class to read.
  • Darling/PerformanceMonitor.Darling.Service/Mcp/DarlingMcpWritePolicy.cs: The rules for tools that change things.
  • PerformanceMonitor.Common/Mcp/McpSchemaCompat.cs: Builds tool schemas that more MCP clients accept. Both products use it.

Lite (WPF, DuckDB, archive and compaction)

Lite is one WPF app that collects, stores and shows the data. A background service runs the collectors on a timer and writes to DuckDB. Older data moves to Parquet files, which a compaction step merges. A retention service deletes archive files that are past their age limit.

Folders: Lite

Start here:

  • Lite/Program.cs: The entry point, including the headless mode.
  • Lite/App.xaml.cs: App start.
  • Lite/MainWindow.xaml.cs: The main window.
  • Lite/Services/CollectionBackgroundService.cs: The timer that runs collection, archive and retention.
  • Lite/Services/ArchiveService.cs: Moves old rows from DuckDB to Parquet.
  • Lite/Services/ParquetCompaction.cs: Merges small Parquet files.
