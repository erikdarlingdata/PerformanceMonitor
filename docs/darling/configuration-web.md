# Web dashboard configuration

Audience: operators.

This page covers the `web` block of `darling.json`. It moved here from the Darling operator guide. To turn the dashboard on and look at it, see [The web dashboard](web-dashboard.md).

## web

The embedded **web dashboard** — a browser view of the monitoring store, served over HTTP on its OWN port (default **5153**), separate from the MCP server. It is a distinct surface from [`### mcp`](configuration-mcp.md#mcp): its own enable flag, port, token, and exposure block, because the two gate different blast radii (the MCP token guards `analyze_server`'s **live outbound** connections to your monitored SQL Servers; the web dashboard reads the collected store and, for a sign-in that can make changes, queues commands and edits settings in that store, as below, but never runs SQL an operator wrote against a monitored server). It connects to the store as its own least-privilege `web` role on a managed store and on the compose distribution's own store; on any other bring-your-own store it connects as `postgres.webConnectionString`, or as the owner when that is unset (see [What a web token can reach](network-endpoints.md#web-endpoint-browser-over-the-lan)). Loopback-only by default; see [Opt-in Network Endpoints (LAN)](network-endpoints.md) to reach it from the LAN.

**Quiet window (#6231).** `set_quiet_window` (server or the whole fleet, an end, an optional start, a reason) and `clear_quiet_window` give planned work a time-boxed mute. A quiet window is a mute rule with only a server scope (or none) and an end; the new optional start (`starts_at_utc`, store rung V208) lets it be set ahead of the work, and until the start passes `get_mute_rules` lists it with `state: upcoming` and it mutes nothing. Both tools are write tools (served only with `mcp.allowWrites` and a token) and are never offered to an investigating agent. `create_mute_rule` and `update_mute_rule` take the same start, the Mute Rules page and the Viewer's mute dialog show and set it, and an end that is not after the start is refused. A window lasts at most 7 days and starts at most 7 days from now. A server, or the fleet, can have one quiet window upcoming or active at a time: a second `set_quiet_window` for the same scope answers `refused` and names the first, which `clear_quiet_window` removes. Each answer gives the rule id and the call that undoes it.
**Recurring mute rules (#7040).** A mute rule can repeat on a schedule (store rung V231). The fields are `recur_days` (day names such as `Mon` or `Monday`, any case, or omitted for every day), `recur_start` and `recur_end` (`HH:mm`), and `recur_time_zone`. A window that ends before it starts crosses midnight and belongs to the day it starts. The zone is an IANA id such as `America/New_York`. A Windows id is converted, and the service host's zone is used when times are given with none. The rule mutes only inside a window, and only between its `starts_at_utc` and `expires_at_utc`. The Mute Rules page, `POST /api/mute-rules` and `PATCH /api/mute-rules/{id}` take the same four fields. A PATCH sends `recur_start` and `recur_end` together. Sending all four as `null` clears the schedule. The service refuses one time without the other, equal times, days or a zone without times, a days list with no valid day, and a zone it does not know. The page shows the message under the field it names. The Mute Rules page fills the zone with the browser's. Each rule in `get_mute_rules` and on the page carries `recur_days`, `recur_start_time`, `recur_end_time`, `recur_time_zone`, a one-line `schedule`, `in_window_now` and `next_window_start_utc`. An older service does not know the schedule. See the V231 note in [Running Darling day to day](admin.md#rolling-back-to-an-older-build).

**Database state expectations (#6397).** `get_database_state_expectations` lists a server's databases with the state each is in now, the state the Database State alert expects (`expected_state`, `is_user_override`) and a status (`as_expected`, `deviating`, `ignored` or `pending`). `set_database_state_expected` sets one database's expected state, `IGNORE` (never alert for it) or `CLEAR` (remove the row; the service learns a baseline again from the next observation). The SQL is one copy, `DatabaseStateExpectedStore`, that the Viewer's override editor runs too. The write is served only with `mcp.allowWrites` and a token, is never offered to an investigating agent (an agent working an alert could otherwise silence it), refuses a database that is not in the latest collected snapshot and a state outside the allowed list, and answers with `previous` and the `undo` call. The `mcp` role gets INSERT/UPDATE/DELETE on `config.database_state_expected`; its read already ran on the SELECT it holds on all of `config`. On a bring-your-own store, re-run `tools/provision-roles.sql` to add the grant.

**Investigation admin over MCP (#6400).** With `mcp.allowWrites` and a bearer token, `write_investigation_note` (`note_text`, optional `server_name`, `metric_name`, `days`; approved as written), `approve_investigation_note` and `reject_investigation_note` (`note_id` of a pending agent note) and `close_investigation_request` (`request_id`, `reason`) do what the web's Write a note, Approve, Reject and Close do, through the same store code, with the same checks and refusals. `start_practice_request` (`request_id` of a judged case), `save_environment_profile` (`profile_text`, optional `server_name` or `tag_id`, optional `expected_modified_at`; a blank text removes the profile) and `record_investigation_feedback` (`request_id`, `verdict`, optional `corrected_verdict`, `missed_step`, `comment`; recorded under the token's name) do what the web's Start practice, profile Save and feedback form do the same way. Each answer shows the row before and after. The change is recorded as `person:mcp` and the token's name (`named token NAME`), or `legacy token` for the endpoint's one legacy token, and the service log line carries the client's own name. The first four have no undo, because the web has no way to reopen a request, return a decided note to pending or delete a note; a practice request is closed with `close_investigation_request`, a replaced feedback record is restored by recording its 'before' again, and a profile edit is restored by saving the answer's 'before' profile text again. An investigation agent is never offered these tools: it proposes a note through `submit_investigation_report`, and a person decides it.

**Run collectors now (#5941).** On a server's **Collection Health** tab, a seat that can edit sees a **Run all collectors now** button and a **Run now** button on each collector row. Run all runs every enabled collector for that server once, now, and leaves disabled collectors out. Run now runs just that collector once, even if it is disabled; its schedule and enabled state do not change. A collector that does not apply to the server's engine is skipped and the result says so. Use it to check collection right after installing an extension or changing a setting. Guards: a second request for the same server is refused while one is queued or running, a request within 60 seconds of the last one for that server is refused (the message says when the next is allowed), and the run takes a slot from the same limit as scheduled collection, so clicks on several servers cannot run more at once than the schedule does. A read-only seat sees no buttons and gets 403. The same action is the MCP tool `run_collectors_now` (served with `mcp.allowWrites`). Run all puts extra load on the monitored server, so prefer one collector when one is enough.

**Generate now and Ask AI on the web (#6389).** On a server's **Recommendations** tab, a seat that can edit sees a **Generate now** button. It queues the same `analyze_now` command the Viewer's Generate now queues (no arguments, one server), through `config.request_analyze_now`, because the web's `web` login holds no INSERT on the command queue. The page shows progress, then re-reads the findings when the service finishes. Guards: a second request for the same server is refused while one is queued or running, and one within 15 seconds of the last is refused, and a web click and an MCP `analyze_now` for the same server share one guard. A read-only seat sees no button and gets 403. A store you brought yourself needs `Darling/tools/provision-roles.sql` run again to add the function; until then the tab says so and points to the Viewer. Every finding card also has **Ask AI**, which copies the same investigation prompt the Viewer's Ask AI copies, built by one shared builder with the finding's window on the server's own clock. It only builds text for your own MCP client: the web holds no model key and makes no model call.

**Incident actions over MCP (#6230).** With `mcp.allowWrites` and a bearer token, `test_connection` (one registered server, by name), `analyze_now` (one server) and `purge_now` (whole store, optional `retention_days` 1 to 3650; the first call queues nothing and shows each collector's retention and the oldest time kept with a `confirm_value` the first call issues, and only a second call that passes it back queues the purge; the value works once and expires after 5 minutes) queue the same command the Viewer and the CLI queue, through `config.request_mcp_command`, the only way the `mcp` login writes a command row (it names `analyze_now`, `purge_now`, `test_connect` and `reload`, builds a connection test from the stored server row, and refuses any other type). Each answer gives a `command_id`; `get_command_result` shows the result once the service has run it on its next poll. A purge cannot be undone. `get_agent_changes` lists agent changes with their `called_id` and `can_undo`, and `undo_plan_change` undoes a plan force or unforce: it shows the statement first and writes only on `confirm: true` with that statement, and it needs that server's `force_plan` switch and remediation login, the same gate as the force tools. The three queued tools are never offered to an agent sent to investigate an alert. `set_agent_actions_enabled` (argument `enabled`) turns the service-wide agent switch off (`enabled: true` is refused: a person turns it on in the Viewer or the web dashboard), and `undo_agent_change` (argument `called_id`) undoes a mute rule, custom alert rule, threshold override or deadlock signature merge change, both by the code behind the Viewer and the web routes (`PUT /api/agent-changes/switch` and `PUT /api/agent-changes/{id}/undo`), so the refusals are the same (`already_undone`, `not_found`, `expired`, `not_undoable`, `changed_since`) and a plan change is pointed to `undo_plan_change`. Each answer gives the state before and after, and the journal names the caller as `mcp:` plus the token and client. Neither is ever offered to an agent sent to investigate an alert.

**Collection state over MCP (#6230).** With `mcp.allowWrites` on, an MCP client can `pause_collection` and `resume_collection` (all collection), `disable_server` and `enable_server` (one server), `set_server_excluded_databases` (one server's excluded databases, the same write the Viewer's Excluded Databases editor makes) and `reload_config`. `get_collection_state` reads whether collection is paused and each server's enabled flag, excluded databases and monthly cost, and `get_server_settings` (#6402) reads the fields `edit_server` changes for one server (never a password or external ID). Pause and resume queue the same `pause` and `resume` commands the Viewer queues, through `config.request_mcp_command`: the answer gives the command id and the read that shows the result (`get_command_result`, then `get_collection_state`), and the row is stamped `mcp`. The other writes run the command plane's own plan, so the SQL and the checks exist once; each answer gives the previous value and the exact call that undoes it, and each server write logs at Warning with the tool, the server and the caller. A server is found the way `edit_server` and `remove_server` find one (the storage name `list_servers` shows works); a name that matches several servers is answered with the candidates. None of the six is offered to an investigation agent. The `mcp` role holds no write on `config.config_service.paused`: a store that an earlier build granted it loses the grant on the next start, and a self-managed store re-runs `tools/provision-roles.sql`. `edit_server` still refuses `is_enabled` and `excluded_databases`, and its refusal names these tools.

**Known patterns over MCP (#6398).** With `mcp.allowWrites` on (and a token), `create_known_pattern`, `update_known_pattern` and `delete_known_pattern` add, replace and remove the entries `get_known_patterns` lists, the same writes the web editor makes (`note` is required and at most 500 characters; `server_id`, `metric_name`, `time_of_day`, `time_zone`, `window_minutes` and `expires_at_utc` are optional, and a field left out means any / UTC / the default window / never). They call the same store functions as the web routes and refuse the same things (a missing or over-long note, an unknown time zone, a `server_id` that is not registered, a bad time or expiry), and write nothing when they refuse. `update_known_pattern` replaces the whole entry, as the web editor's save does. Each answer carries the entry before and after and an `undo` call (a delete's undo re-creates the entry under a new id). The `mcp` role holds EXECUTE on the three functions and nothing on the table. These tools are never offered to an agent that Darling sends to investigate an alert; it may read with `get_known_patterns`.

| Key | Default | Notes |
|---|---|---|
| `enabled` | `false` | **Off by default** — a headless service does not open a local port unless you ask |
| `port` | `5153` | Chosen so all four local surfaces coexist on one machine (Dashboard 5150, Lite 5151, Darling MCP 5152) |
| `allowTokenlessLoopback` | `false` | On, a loopback-only dashboard with no token serves local browsers without one, for reads only, and every start logs a line saying so. A change (adding a server, editing a view, muting an alert) is refused with 403 and a message that names the token setting. Off, an enabled dashboard with no token does not start. A configured token gates every request either way. |
| `allowAdminWrites` | `false` when the key is missing | Managed store only. A new install writes `true` here (the installer's `darling.json` and `darling.sample.json`); a `darling.json` without the key, such as one from 3.11, keeps it off until you set it. On, a person signed in to the dashboard as an admin (the shared token, or an OIDC admin) can make its Admin writes (routes and environment profiles, threshold overrides, report feedback, server actions, note decisions, undoing an agent change and the agent switch, closing a request, writing a note, practice requests, and case export) through a second small connection pool. That pool signs in as the managed `admin` login, the one the Viewer uses. Every other request stays on the `web` login. Off keeps the dashboard list-only on the managed store. Every start logs which of the two it is. With OIDC on and no role mapping, every signed-in user has the edit seat. With this setting on, every one of them can make these writes. Every start with OIDC on and no role mapping logs a warning that names `web.network.oidc.roleClaim`, on any kind of store; map roles before you turn this on. On a store you bring yourself, including the compose store, this setting does nothing. There, what an edit seat can change depends on the grants of the web's own store login. File-only; restart to change |
| `allowWindowsAuthOverUnverifiedTls` | `false` | Adding or editing a server in the dashboard defaults to Windows authentication, where the service presents its own computer account to the host the form names. Off, the dashboard refuses a Windows-authentication server that also sets `trust_server_certificate` or an `encrypt_mode` other than `Mandatory` or `Strict`, because the service could not confirm which server it reached. To save such a server, use a verified certificate (`trust_server_certificate` false and `encrypt_mode` `Mandatory` or `Strict`), use SQL authentication, or turn this on. An edit is judged only when it changes the machine the entry names or its sign-in and certificate settings (the host, the port, the auth type, `trust_server_certificate`, `encrypt_mode` or the Query Store replica), on the server as it would be saved, so changing a display name, a threshold or a tag is never refused. `read_only_intent` and `multi_subnet_failover` do not change the host the entry names, so they are not judged. On, the dashboard accepts the combination. SQL authentication and the Entra modes are not affected. It is the dashboard twin of `mcp.allowWindowsAuthOverUnverifiedTls`. The setting is not written by the installer. File-only; restart to change. |

**What the dashboard can change.** Besides reading the store, a sign-in that can edit adds, edits and removes monitored servers. It also edits alert routes, mute rules and custom alert rules, and runs the commands and changes the settings described above.

**Daily Health Report settings ([#7041](https://github.com/erikdarlingdata/PerformanceMonitor/issues/7041)).** On the Admin page, the Settings tab lists the alert settings read only, with one exception: a signed-in admin also gets a form under the Daily Health Report rows. It holds the checkbox "Send a daily health report", the "Send at" time (`HH:mm`), the "Time zone" (an IANA id, starting at the browser's zone for a report that is off and has no zone yet, blank for the service host's zone) and an optional "Title". Save writes through `PUT /api/alert-settings/daily-report`, which runs the same validation as `update_alert_settings`, so a refused value shows the service's own sentence. **Preview** builds the report with `get_daily_health_report` and shows it on the page without sending anything. A dashboard on the managed store needs `web.allowAdminWrites` for the save, like the other Admin writes. The other alert settings stay in the Viewer and over MCP. See [Daily Health Report](alerts-and-notifications.md#daily-health-report).

**A token is required on loopback too.** Once `web.enabled` is on, the dashboard starts only with a token. Set `web.network.encryptedToken` (from `--encrypt-password`) or `web.network.token` (the token itself, `env:NAME` or `file:PATH`), and leave `web.network.listen` out to stay loopback-only. On Windows, use `encryptedToken`. `env:NAME` and `file:PATH` references are for the compose and Linux setups, where there is no DPAPI. To make a token, use [the PowerShell one-liner under MCP endpoint](network-endpoints.md#mcp-endpoint-assistant-over-the-lan). The browser then shows a sign-in page: paste the token there once, and it is exchanged for a session cookie. With no token the dashboard does not start, and the service log names these settings. `--print-web-token`, run elevated on the service host, prints the configured token. To serve local browsers with no token, set `web.allowTokenlessLoopback` to `true`. The dashboard then serves reads only, and every start logs a line saying so. A token shorter than the floor below (16 characters, 6 of them different) still signs a browser in, but the dashboard serves reads only until a longer one is set.

Once enabled, open `http://localhost:5153/` in a browser on the service host. Like the MCP server, `enabled`/`port` here are the file SEED; after first start they live in the control plane and the Viewer's Settings toggles them LIVE (the service starts/stops/rebinds the dashboard within seconds — no restart). If the port is already in use at startup, the web host logs an error and retries on a calm cadence; collection is unaffected.

**What you see.** The dashboard opens on a **Fleet Overview**: a card per enabled server with a status dot, six per-metric health bands (CPU, threads, memory, blocking, deadlocks, collectors), and its last collection time — all banded server-side, so the browser only renders (a server the service has just registered and not yet collected from shows an amber "Awaiting first collection", never a red offline; one that stopped reporting reads Offline however long ago it stopped). Above the cards a worst-first "Needs attention" list surfaces the servers to look at, or an all-healthy line when there is nothing to chase. Click a card to **drill into one server**: an overview, wait stats with a trend for the heaviest wait, active queries, a CPU chart, memory and file-I/O trends, and collection health — the same collected data the viewer shows, over inline charts. A fleet-wide **Alert History** page (with a server filter box) rounds out phase 1, a **Custom Views** page hosts the composer for the saved dashboards/notebooks in `config.custom_views`, and an **Alert Rules** page edits the user-authored custom alert rules (evaluated on a managed or compose store; on any other bring-your-own store they can be authored but do not fire, since its `web` role comes from `tools/provision-roles.sql`, which does not create the resolve function the evaluator needs, [#3970](https://github.com/erikdarlingdata/PerformanceMonitor/issues/3970)). A **Fleet Sweeps** page ([#3466](https://github.com/erikdarlingdata/PerformanceMonitor/issues/3466)) renders the scheduled whole-fleet sweep reports as a timeline at a configurable viewing span (default the last hour): each sweep's document diffs against the previous sweep (band transitions with reasons, arrivals and departures), carries the watch-item worklist with its hysteresis position, states the alert master switch on every sweep and renders the would-have-paged ledger whenever one was taken under mute — and a sweep that could not prove its instruments were alive renders LOUDLY (a red banner and a marked timeline row), because quiet is not clean. The sweep cadence shown there is read from `get_alert_settings`' `fleet_sweep` group; the Settings window and `update_alert_settings` own the knob. Channel delivery of sweep content is bounded at a **daily rollup**, a ceiling rather than a default, per the issue's delivery ruling: at most one INFO post per day through the existing alert channels, summarizing the trailing day's band transitions, watch-item openings and closings, instrument-liveness incidents, and — whenever any covered sweep ran under the alert master switch — the would-have-paged ledger those sweeps carried, so the operator sees what the silence cost. A day with nothing to say posts nothing (the collector-cost digest's own discipline — the web feed is where the affirmative, instrument-proved all-clear lives at full cadence), and the rollup's delivery is itself master-gated: with `alerts_enabled: false` the sweeps keep publishing here and to `get_sweep_reports`, nothing reaches the channel, and the first rollup after re-enable states how many of its covered sweeps ran muted — older muted days stay readable on this page permanently rather than arriving as a re-enable flood. The HTTP API also carries the mute-rule write endpoints (`/api/mute-rules`, [#3450](https://github.com/erikdarlingdata/PerformanceMonitor/issues/3450)) — their page UI is deferred; the endpoints are the deliverable — all writes gated on the editing seat. Otherwise it is a read-only view — no settings, no live-server queries — and it refreshes every 60 seconds (pausing while the tab is hidden). The frontend ships fully self-contained (no CDN, no fonts, no remote anything), so it works on an air-gapped host with no internet access.

**A web dashboard that fronts other stores.** A service with `frontDoor.enabled` serves this same dashboard, with a store picker, and sends each page call to one of its stores. The `web` settings above (token, `allowFrom`, OpenID Connect) decide who can sign in to the front door. The `webUrl` and `webToken` of each store are in the `frontDoor` block. See [The front door](front-door.md#the-web-dashboard).
