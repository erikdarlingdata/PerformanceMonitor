# Configuration Reference

Audience: operators.

This page covers the keys of `darling.json` that set up the store and the servers, plus `peers`, `heartbeat` and `reads`. It moved here from the Darling operator guide. The other blocks have their own pages: [Alert and notification settings](alerts-and-notifications.md), [Agents and alert sources](agents-and-alert-sources.md), [MCP configuration](configuration-mcp.md), [Web dashboard configuration](configuration-web.md) and [Collector schedules and switches](collector-settings.md).

All sections except `postgres` and `servers` are optional — omit a section (or any key) to get the defaults listed here. Defaults deliberately mirror a fresh Lite install.

## Where each setting lives: first-run seed or file only

`darling.json` does two jobs. Some keys are read from the file at every start. Others are only a **first-run seed**. The first time the service starts against a store with no settings, it copies them into the store. After that the store holds the only copy that counts, and the service replaces the file's value with the store's on every load. If you change a seeded key in the file and restart, nothing changes. Each seeded section is copied once, only while its own store table is empty.

| Keys | Where they live | Where to change them after the first start |
|---|---|---|
| `alerts` (every key), `analysis` (`enabled`, `intervalMinutes`, `notificationsEnabled`, `notifySeverity`) | First-run seed | The Viewer's Settings window, or the MCP tool `update_alert_settings` |
| `smtp` (including `emailSendResolutions`), and `webhooks` (the Teams, Slack, generic and PagerDuty keys, including `slackSendResolutions`, `teamsSendResolutions` and `genericSendResolutions`) | First-run seed | The Viewer's Settings > Notifications, or the MCP tool `update_notification_channels`. The send-resolutions switches are also set by `update_alert_settings` |
| `capturePlans`, `queryStoreBackfillEnabled`, `queryStoreTextBudgetMb` (default `64`), `queryStoreFetchTopN` (default `100`), `maxConcurrentSweeps` (default `4`) | First-run seed | The Viewer's Settings window, or the MCP tool `update_service_flags` |
| `planContentRetentionDays` (default `21`), `composeStatementTimeoutSeconds` (default `60`), `planXmlCompression` (default `"gzip"`) | First-run seed | Neither the Viewer nor MCP edits them. Change the column in `config.config_service` (`plan_content_retention_days`, `compose_statement_timeout_seconds`, `plan_xml_compression`). The statement timeout reaches the `viewer` and `mcp` roles on the next service start |
| `mcp.enabled`, `mcp.port`, `web.enabled`, `web.port` | First-run seed | The Viewer's Settings window, live and with no restart. On a box with no Viewer, `--enable-mcp` and `--enable-web` |
| `servers` | First-run seed, copied once while the server registry is empty. A server added to the file later is ignored | The Viewer, the web dashboard's Admin page, or the MCP tools `add_servers` and `edit_server`. The one exception is the `remediation*` and `hypotheticalIndex*` login keys, which the service syncs from the file at every start |
| `analysis.uncorroboratedRoute` | Both. The store's value wins when it is set. Otherwise the file's value is used | The store value, from the same places as the rest of `analysis`. Clear it to hand the choice back to the file |
| `postgres`, `collectSchemaChangeEvents`, `rawChunkIntervalReconcileEnabled` (default `true`), `procedureStatsPlanCycleInterval`, `queryStatsDeferredPlanFetch`, `procedureStatsDeferredPlanFetch`, `allowedAwsRoles`, `peers`, `frontDoor`, `heartbeat`, `reads`, `forcePlanBot`, `analyzer`, and every other key in `mcp` and `web` (including `mcp.network` and `web.network`) | File only | Edit `darling.json` and restart the service |

There is deliberately **no plaintext variant** of this one — a wrong monitoring password fails a read, a wrong remediation password fails a write against a production server. Unlike the other per-server keys, **both remediation keys are re-read from darling.json on every start**: an entry with both keys sets or replaces that registered server's remediation login. Anything else leaves the login alone. An entry with neither key never clears a login that was set in the store, and **removing the keys does not disarm a server**. To stop agent actions on a server, turn off its action switches, or turn off agent changes service-wide; the switches cover agent actions only, not operator remediation from the Viewer. To remove a server's remediation login entirely, so neither agents nor operators can use it, first take both keys out of darling.json (an entry with both keys would set the login again on the next start), then run this as the store owner: `UPDATE config_monitored_servers SET remediation_username = NULL, remediation_encrypted_password = NULL, modified_at = now() AT TIME ZONE 'UTC' WHERE name = 'alpha-sql-01';`. An entry with only one key is logged and changes nothing. A server that is not in darling.json is never touched. The login is written only to the registered server that pairs with the entry by id (else by name, among rows no other entry claimed by id), and only when that server's host, port, engine and other connection settings are the entry's: otherwise it is skipped and the log names the server. A password that is none of an `env:`/`file:` reference, a sealed value or a DPAPI blob is not written (the log gives its shape, never the value). Services that share one store should declare the same logins, because each one copies its own darling.json when it starts. The log says when a login is set or changed |
| `hypotheticalIndexUsername` | *(none)* | **PostgreSQL targets only. The login that the "Test an index" check runs under (#6170).** The check never runs under the monitoring login. With no login set, the check is refused and the message says what to set up. See [Testing an index on PostgreSQL](#testing-an-index-on-postgresql) |
| `hypotheticalIndexEncryptedPassword` | *(none)* | The password of that login, as an `env:NAME` or `file:/path` reference. Darling reads it on its own host when the check runs. A stored password is refused, and so is a reference to one of Darling's own configuration files or secrets (unless this same reference is in darling.json for this server). The login needs a SCRAM-SHA-256 password: the check signs in with SCRAM-SHA-256 only, as the remediation login does |

**Least privilege for the remediation credential.** Grant `ALTER` on each database you intend to force a plan in — that is what `sp_query_store_force_plan` / `sp_query_store_unforce_plan` need. `ALTER SERVER STATE` is needed *only* to evict a plan (`evict_cached_plan`, #5632), because that is what a targeted `DBCC FREEPROCCACHE(plan_handle)` requires, and it is the expensive grant. It is genuinely optional: without it an eviction is refused as `evict_permission_denied`, a named reason and never silent, and nothing is run. The service does not guess per platform: before it evicts (and on a dry run) it asks the server with a read-only `HAS_PERMS_BY_NAME` check, which answers for the credential's effective permissions however the grant arrived. Azure SQL Database has no plan handle eviction at all, which no grant changes, and that is refused as its own reason, `evict_unsupported_on_platform`, rather than as a permission problem. An eviction has no undo, and it also needs that server's `evict_plan` switch; no server has it on after an upgrade.

**`ALTER ANY CONNECTION` is a strong grant, and it is needed only to kill (`kill_session`, #5632).** It lets the remediation login kill ANY session on that server, not only the one an agent names, so grant it only on a server where you want an agent to be able to kill. Darling checks that the session id and its sign-in time still match what the agent read from `get_blocking` before it runs `KILL`, and that the session's last request ended at the same time as when it was read (if the session ran something new since, the answer is `session_changed` and nothing is killed), and refuses with `kill_permission_denied` (a named reason, nothing run) when the login lacks the grant. A kill also needs that server's `kill_session` switch, which is off after an upgrade. A person turns it on the way they turn on `evict_plan`: the store owner sets `enabled` to true for that server and the action `kill_session` in `config.config_server_actions`. There is no switch screen for it today. [Agent dispatch](../darling-agent-dispatch.md) gives the statement. **Azure SQL Database (General Purpose and Hyperscale).** A session there is reached only from inside its own database, so `kill_session` takes `database_name` (the `database_name` of the `get_blocking` row) and connects to that database, never to `master`, read-write. The database must be the server entry's database or one Darling collected a blocking row from in the last day, and not one the entry excludes; anything else is refused before a connection opens (`database_required`, `database_excluded`, `database_not_monitored`). The remediation login needs a user in each database it may kill in, either a contained user or a user for its login, with exactly these grants: `CREATE USER [remediation] WITH PASSWORD = '...'; GRANT VIEW DATABASE STATE TO [remediation]; GRANT KILL DATABASE CONNECTION TO [remediation];`. A missing grant answers `view_state_permission_denied` or `kill_permission_denied` and names the grant. One batch checks the engine, that the connection is in the named database (`wrong_database`), that the database is read-write there (`not_primary`), the session id and its `login_time` (`session_reused`), that the session's `database_id` is this database (`session_in_other_database`), and refuses system sessions and any session of the monitoring or remediation login (`tool_login_session`). On Hyperscale the kill reaches only the primary: a session on a named replica or a read-only secondary answers `session_gone` (not found on the primary) and nothing elsewhere is touched. A serverless database that is paused or resuming is retried on the open twice and then answers `database_unavailable` with nothing sent; an Azure transient error after the batch was sent answers `outcome_unknown`, and the batch is never sent again.

## Testing an index on PostgreSQL

The server tab can test an index on a PostgreSQL server. It plans one stored statement twice, with and without an index that does not exist. The index is a hypothetical one from the `hypopg` extension. Nothing is built.

Planning a statement can run a function. PostgreSQL runs a function while it plans when the function is marked `IMMUTABLE` and its arguments are constants, and also when it is marked `STABLE` and its arguments are constants, because the planner calls it to estimate how many rows a condition matches. The function runs under the login that plans. So the check does not use the monitoring login, which usually holds `pg_monitor` or `pg_read_all_stats`. It uses its own login.

Set up the login the way you set up the remediation login:

1. Create a login on the server. Give it no `pg_monitor`, `pg_read_all_stats`, `pg_read_all_data` or superuser role.
2. Give it `CONNECT` on the database.
3. Give it `USAGE` on each schema that holds a table you want to test, and on the schema `hypopg` is installed in.
4. Give it `SELECT` on each table that the statements read. PostgreSQL checks table privileges when it starts an `EXPLAIN`, so a table the login cannot read stops the check with `permission denied`.
5. Give it a SCRAM-SHA-256 password (`password_encryption = 'scram-sha-256'` when you set it), and a `scram-sha-256` line in `pg_hba.conf`. The check signs in with SCRAM-SHA-256 only. A server that asks for a password in clear text, MD5, or no password at all is refused before the password is sent. Unless the server entry verifies the server's certificate in full (encryption not `Optional` and `Trust server certificate` off), the check also needs SCRAM channel binding, so TLS must be on at the server (`ssl = on`).
6. Set `hypotheticalIndexUsername` to the login name and `hypotheticalIndexEncryptedPassword` to an `env:NAME` or `file:/path` reference to its password.

**For a server that is already in the store**, there are two ways. If you set BOTH keys in darling.json for that server, Darling applies them on every start (it sets the login, or replaces it when the file's differ), and the log says which server and the shape of the secret, never the login or the reference. Only an `env:` or `file:` reference is written, and only to the server whose connection settings match the entry. Leaving the keys out of darling.json never clears a login the server already has, and neither does a single key. Services that share one store should declare the same logins, because each one copies its own darling.json when it starts. The other way is to set them on the store row, as the store's owner role (the web dashboard, the MCP `edit_server` tool and the desktop viewer cannot set either pair, by design). For example, in `psql` as the owner:

```sql
UPDATE config.config_monitored_servers
SET hypothetical_index_username = 'pm_index_check',
    hypothetical_index_encrypted_password = 'env:PM_INDEX_CHECK_PASSWORD',
    modified_at = (now() AT TIME ZONE 'UTC')
WHERE name = 'my-pg-server';
```

The service picks the change up when it next reloads its server list. Once the password column is set, the web dashboard, the MCP `edit_server` tool and the desktop viewer refuse to change how that server is reached (host, port, database, authentication, username, encryption), as they do for a remediation login: change it on the service host, with the same `UPDATE` as the owner. Removing the two columns (`SET ... = NULL`) lifts that, unless darling.json still has both keys for the server: the next start puts them back.

A bring-your-own store needs one step after the service upgrades the store to V203. Run `tools/provision-roles.sql` again, so `config.edit_monitored_server` and the password-rules trigger know the new password column. The service replaces both on each start when its login owns them, and warns once, naming the script, when it does not. The compose store and managed provisioning do this on their own.

A bring-your-own store needs one step after the service upgrades the store to V213 (the Query Store replica setting). Run `tools/provision-roles.sql` again. The service replaces the three `config.edit_monitored_server` functions on each start when its login owns them, but the new 18-argument one is a new function that only the script grants to the `web` and `mcp` roles, and only the script grants them the new `query_store_replica` column; until then a web or MCP edit of a server fails with `permission denied`. The compose store and managed provisioning do this on their own.

A bring-your-own store needs one step after the service upgrades the store to V214 (known patterns). Run `tools/provision-roles.sql` again. It creates the three functions that add, change and delete a known pattern and grants them to the `admin` and `web` roles. Until you run it, adding, changing or deleting a known pattern fails. Reading them keeps working. The compose store and managed provisioning do this on their own.

**What a role that can create functions can read through this check.** The check runs `EXPLAIN` on a stored statement. If a role can create a function in that database, and a statement that calls it with constant arguments is among the statements the check plans, that function runs while the statement is planned, as this login. So a role that can create functions in that database can read, through the check, whatever this login can `SELECT`. Grant the login `SELECT` only on the tables you want to test, and treat the right to create functions in that database accordingly. The transaction is read-only, so the function cannot write.

The login needs no write grants. The check tests `SELECT` statements and `WITH` statements only. An `INSERT`, `UPDATE` or `DELETE` is refused with a plain message, because planning one needs a write grant on its table.

With no login set, the check is refused. The message names the login, the grants and the two keys. Darling never falls back to the monitoring login.

## Ending a PostgreSQL session

On a PostgreSQL server the remediation login ends one session with `pg_terminate_backend` (`kill_session`, #5632). The agent names the session by its `backend_id` and its pid. `get_pg_blocking` returns them as `root_backend_id` and `root_pid`, and `get_pg_session_states` as `backend_id` and `pid`. The `backend_id` holds the session's start time in whole seconds, then its pid in seven digits. The two must agree, or Darling refuses.

Darling checks the pid and the start second in the same statement that ends the session. The statement also ends the session only if its transaction start and last state change are still the ones Darling read earlier. If the session ran something new since, the answer is `session_changed` and nothing is ended. A pid given to a session that started in another second is never ended. This is not a full guarantee. On Linux a pid comes back only after many others have been handed out. On Windows a pid can come back within about a second, so a new session there can have the same pid and the same start second.

If the monitoring login lacks `pg_read_all_stats`, the collector cannot read another role's start time, and it stores the server's start time in `backend_id` instead. Such an id names no session, so Darling refuses it as `backend_id_has_no_session_start`. Grant `pg_read_all_stats` (or `pg_monitor`) to the monitoring login; the ids collected after that work.

The login needs two grants: `pg_signal_backend`, and `pg_read_all_stats` (or `pg_monitor`, which includes it). Without `pg_read_all_stats` the server hides another role's start time. Darling then cannot check the session and refuses. Darling reads what the login can do before it tries. It refuses with `not_permitted` and a message that names the missing grant, and it does not try the kill anyway.

Darling also refuses a session that belongs to a superuser. PostgreSQL lets only a superuser end one, and `pg_signal_backend` does not change that.

Darling ends client sessions only. A background process or a replication sender is refused as `not_user_session`, and Darling's own connection is refused as `own_session`. Ending a session rolls back its open transaction. A session that is waiting for a synchronous standby has already committed on the server, so its commit stays. There is no undo.

`pg_terminate_backend` only sends the signal. After a kill Darling reads the session once more and says in `still_there` whether it was still there. When that read fails, or the caller cancels during it, `still_there` is null and the kill still counts as done. On SQL Server the same holds for `rollback`. If the reply to the kill is lost, for example because the connection drops or the server ends the kill's own connection, the answer is `outcome_unknown`: the session may have ended. The agent changes list then shows the kill as "result unknown", not failed. The SQL Server kill answers the same way. A kill also needs that server's `kill_session` switch, which is off after an upgrade.

### How the remediation login signs in to PostgreSQL

The remediation connection always opens the `postgres` database. It does not use the database that the server entry names. `pg_stat_activity` and `pg_terminate_backend` cover the whole cluster, so that database is enough. If the login cannot connect to `postgres`, Darling refuses with `sign_in_failed` and names that database. A person can run `GRANT CONNECT ON DATABASE postgres TO <remediation login>`.

The connection sets `search_path` to `pg_catalog, pg_temp` when it signs in. A setting made with `ALTER DATABASE` or `ALTER ROLE` does not change it. If a connection pooler drops that setting, Darling reads `search_path` before it runs anything, refuses with `search_path_not_pinned`, and names the value it found. The server entry then needs to point at the PostgreSQL server directly. Each statement that Darling runs also names its views, functions and operators with the `pg_catalog` schema. Darling never uses a function or an operator of the same name in another schema.

The remediation login signs in with SCRAM-SHA-256 only. If the server asks for a password in clear text or as MD5, or asks for no password, Darling refuses with `sign_in_not_strong_enough`. It does not send the password. If the server entry does not verify the server's certificate in full, the sign-in also needs SCRAM channel binding. Channel binding ties the sign-in to the TLS session. The sign-in then fails when that TLS session does not end at the server that holds the login. The monitoring connection does not change.

Before a kill or a dry run can sign in, do these steps:

1. Set `password_encryption = 'scram-sha-256'` on the server. It is the default from PostgreSQL 14.
2. Set the password of the remediation login again, so that the server stores it as SCRAM.
3. Give the remediation login a `scram-sha-256` line in `pg_hba.conf`.
4. Turn TLS on at the server (`ssl = on`). Channel binding needs TLS, and a verified certificate needs TLS too.
5. If you do not want channel binding, verify the certificate. In the server entry, set an encryption mode other than Optional and turn off Trust server certificate.

## Managed PostgreSQL

None of the three providers' pages says whether its admin role holds `pg_signal_backend`. Check your own login: a dry run asks the server and ends nothing. These are the facts each page states.

- Amazon RDS and Aurora: `rds_superuser` can stop connections with `pg_terminate_backend`. The internal `rdsadmin` role does the work of a superuser ([AWS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Roles.rds_superuser.html)).
- Azure Database for PostgreSQL flexible server: the server admin belongs to `azure_pg_admin`, a pseudo-superuser role. It does not belong to `azuresu`, the role with superuser privileges ([Microsoft](https://learn.microsoft.com/en-us/azure/postgresql/security/security-access-control)).
- Google Cloud SQL: `cloudsqlsuperuser` holds limited superuser privileges. `cloudsqladmin` is a system user with superuser privileges ([Google](https://docs.cloud.google.com/sql/docs/postgres/users)).

On any of them, a login that is not a superuser cannot end a superuser's session. Darling refuses it as `not_permitted`.

> Phase 1 ships **no consumer of this credential**. It is accepted, stored and resolvable so the arming model can be reviewed and provisioned ahead of the write path; the service logs at connect that an armed server is inert in this build. Nothing in this release can write to a monitored server.

## allowedAwsRoles (array, optional)

| Key | Default | Notes |
|---|---|---|
| `allowedAwsRoles` | `[]` | The AWS roles the web, MCP, desktop viewer and `--add-server` may set on a server. Each entry is an IAM role ARN (matched exactly) or a 12-digit AWS account id (every role in that account in the `aws` partition; write `aws-cn:123456789012` or `aws-us-gov:123456789012` for an account in the China or GovCloud partition). The service runs a role only if it is listed here or a `servers[]` entry in this file names it in `awsRoleArn`. With no list, the web and MCP cannot set a role. Read at start: restart the service after you change it. Example: `[ "arn:aws:iam::123456789012:role/darling-monitor", "123456789012" ]` |

## capturePlans (boolean, optional)

| Key | Default | Notes |
|---|---|---|
| `capturePlans` | `true` | Capture execution plans into `query_stats.query_plan_xml` and `query_store_stats.query_plan_text`. PostgreSQL TOAST compresses the plan text transparently (LZ4 on the managed store) and TimescaleDB chunk compression squeezes it further, so plans are cheap to keep — unlike Lite, which stores to DuckDB/Parquet and deliberately never captures them. Set `false` to skip plan capture (e.g. to shave storage across a very large fleet). |

## collectSchemaChangeEvents (boolean, optional)

| Key | Default | Notes |
|---|---|---|
| `collectSchemaChangeEvents` | `true` | Record `Object:Created` / `Object:Altered` / `Object:Deleted` schema-change (DDL) events in the built-in default-trace collector. Set `false` on a noisy or benchmark box where a create/drop-happy workload floods the viewer's **System Events > Default Trace** tab — e.g. HammerDB's TPC-H Query 15 creates and drops a `revenue` view thousands of times, and the collector faithfully records every create/delete. Only the Object DDL slice is suppressed; file auto-grow/shrink, ErrorLog, and security-audit events are still collected. The shared collector's equivalent of the full Dashboard's `@include_object_events`. A file-only knob (not stored in the control plane): edit and restart. |

## procedureStatsPlanCycleInterval (integer, optional)

| Key | Default | Notes |
|---|---|---|
| `procedureStatsPlanCycleInterval` | `4` | How many collection cycles pass between execution-plan captures for `procedure_stats`. `1` captures on every cycle and is byte-identical to releases before this knob existed; `4` captures on one cycle in four. Clamped to `[1,60]`, and a nonsense value (`0` or negative) degrades to `1` rather than to the default, so a bad setting never silently starts skipping plans. **Why it exists:** `procedure_stats` is normally the most expensive collector against a monitored server, and nearly all of that cost is plan XML — a controlled decomposition put **73.8%** of its read loop in RENDERING the plans and **26.0%** in shipping them, against **0.2%** for the same query with no plan apply at all. The render happens inside `sys.dm_exec_text_query_plan`, a server-side TVF, so it is CPU on the **monitored** server rather than on the collector host; skipping a cycle omits the apply entirely rather than rendering and discarding. **What you trade:** plan freshness — a stored plan can be up to this many cycles old, and `4` keeps the worst case inside the collector's own ten-minute candidate window. Runtime statistics (execution counts, CPU, duration, reads) are collected every cycle regardless, and the collector stays on its 1-minute schedule. The capture cycle is offset per server, so a fleet spreads across the interval instead of every server rendering together. Only `procedure_stats` is gated; `query_stats`, `query_store`, `deadlocks` and `blocked_process_report` still capture plans every cycle. A file-only knob (not stored in the control plane): edit and restart. |

## queryStatsDeferredPlanFetch (boolean, optional)

| Key | Default | Notes |
|---|---|---|
| `queryStatsDeferredPlanFetch` | `true` | Whether `query_stats` fetches execution-plan XML only for the plans this collector host has not already stored. On (the default), the main query reads the statistics with no plan, and a second query on the same connection renders just the plans whose identity (plan handle, `creation_time`, `plan_generation_num`) the host has not committed; a row for a plan it has stored reuses the stored digest, so every reader sees the same rows and plans as before. Off restores the inline capture, which renders and ships every row's plan on every run. **Why it exists:** on one large store the inline capture rendered 54 GB of plan XML an hour on the monitored servers and shipped 29 GB of it, against 1.1 GB an hour of distinct plans, about 47 times the plans there are. The render is CPU on the **monitored** server (`sys.dm_exec_text_query_plan`), so this is load taken off the servers you watch. **Why you would turn it off:** to get the plan re-rendered on every run (for example to compare against the old behavior while testing), or if a server is so constrained that the second round trip is unwelcome. **What you trade by leaving it on:** a plan's text is fetched once per identity, so a plan the engine changes in place without a recompile is not re-read until it leaves the cache (entries unused for an hour are dropped; a restart empties it and each server renders its plans once more). A statement recompile between the two queries can pair the new plan with the old identity for that one run's row; the old identity leaves `sys.dm_exec_query_stats` at once, so it is not read again. **Azure SQL Database keeps the inline capture** regardless of this setting, because its per-database collection path has no second query to defer to. Only meaningful while `capturePlans` is on. The run records `plans_rendered`, `plans_rendered_bytes` and `plan_fetch_ms` in its `collection_log` note. A file-only knob (not stored in the control plane): edit and restart. |

## procedureStatsDeferredPlanFetch (string, optional)

| Key | Default | Notes |
|---|---|---|
| `procedureStatsDeferredPlanFetch` | `"on"` | Whether `procedure_stats` fetches execution-plan XML only for the module plans this collector host has not already stored. Three values; anything else is read as `off` and logs one warning. **`off`** keeps the inline capture and is the way to turn the deferred fetch off: every captured module plan is rendered and shipped, as before. **`shadow`** does exactly what `off` does, and every stored row is the same as `off` would store; in addition it recognizes each module plan by its identity (plan handle, `cached_time`, and a fingerprint of the module's statements read from `sys.dm_exec_query_stats`: how many, the latest `creation_time`, the sum of `plan_generation_num`) and checks that identity against the plans this host has already stored. It writes nothing different. What it measures lands in the run's `collection_log` note, beside `plans_rendered`: `deferred_would_hit` (identities it would have skipped rendering), `deferred_false_hit`, `deferred_same_shape` and `deferred_miss`. Of the would-hits that rendered different bytes, `deferred_false_hit` counts the plans whose shape changed, or whose shape could not be compared. This is the number that must stay 0. `deferred_same_shape` counts the plans whose bytes changed but whose shape held, for example a memory grant that SQL Server adjusted in place. `on` treats that as a correct hit. Each false hit logs one warning. It names the identity and says why. One reason is that the plan's shape changed. The other reasons mean the shapes were not compared: the cached entry has no shape yet, the rendered plan is over the size cap, or its XML did not parse. The note also splits `deferred_false_hit` by reason into `deferred_false_hit_shape`, `deferred_false_hit_no_shape`, `deferred_false_hit_over_cap` and `deferred_false_hit_unparsed`, which add up to it, so a real shape change reads apart from a plan that was not compared (an over-cap plan is still compared by its byte size, so a memory grant change can count there). **`on`** (the default since 3.10) skips the render for a recognized plan and sends its stored digest instead; the others are rendered in one second query on the same connection, at most 150 per run (the main query is already `TOP (150)`, so the limit is a guard, and `deferred_over_cap = 0` is expected). The run records `plans_rendered`, `plans_rendered_bytes`, `plan_fetch_ms`, `deferred_hit` and `deferred_miss`. `procedureStatsPlanCycleInterval` still decides which runs may render plans: a run between captures sends the digest for a recognized plan and renders nothing. An identity is trusted for four capture cycles, then rendered again. **Why a shadow mode:** a module plan changes in place when one statement recompiles, with the same plan handle and `cached_time`; shadow measures the identity against the plans it just rendered before `on` is allowed to trust it. Move from `shadow` to `on` only after `deferred_false_hit` has stayed 0 over a representative period. A rising `deferred_same_shape` is not a reason to wait. **Azure SQL Database stays `off`** regardless of this setting. Only meaningful while `capturePlans` is on. A file-only knob (not stored in the control plane): edit and restart. The plan cache starts empty under whichever mode the service starts in. |

## peers

**Declared peer stores** — optional, and only relevant when the fleet is split across **several Darling boxes**, one store each (SQL Server primaries on one box, their readable replicas on another, PostgreSQL on a third). Each box's MCP server answers over **its own** store only, so a server monitored by a sibling resolves as not-found — which an agent cannot tell apart from *"nobody monitors this server."* Declaring the siblings fixes that at the three places an agent forms its picture of the fleet.

**Disclosure only.** There is no address and no credential in this block, and nothing behind it: the service never contacts a peer, cannot read a peer's data, and cannot tell whether a peer is even running. A peer is a **name** plus a **sentence**, so an agent (or its human) can pick the right endpoint. Everything here is sent verbatim to every connected MCP client, so the service **refuses to start** if any peer text looks like a connection string or credential.

| Key | Default | Notes |
|---|---|---|
| `storeName` | `""` | **Opt-in.** A short label for THIS store itself; when set, every store self-alert fires under it instead of `Monitor Store` — see below, setting it re-keys the self-alert fingerprints |
| `thisStoreCovers` | `""` | One sentence naming what THIS store monitors — the anchor the peer list is relative to |
| `stores[].name` | — | **Required.** Whatever an operator would recognize (the box name, "the use1 store") |
| `stores[].covers` | `""` | A short sentence naming what that store monitors. Human prose — never parsed, only shown |
| `stores[].matches` | `[]` | Optional server-name **substrings** that store monitors, case-insensitive. The only machine-checked field |

```jsonc
"peers": {
  "storeName": "prod-sql-use1-monitor-01",
  "thisStoreCovers": "the 42 us-east-1 SQL Server primaries",
  "stores": [
    {
      "name": "prod-sql-use2-monitor-01",
      "covers": "the readable replicas of those same 42 primaries, in-region from us-east-2",
      "matches": ["use2"]
    },
    { "name": "prod-sql-pg-monitor-01", "covers": "the Aurora PostgreSQL clusters", "matches": ["-aurora-"] }
  ]
}
```

What it changes, with peers declared:

- **The MCP instructions** gain a Fleet Coverage section, high enough that an agent reads which store it is talking to before it reads the tool census.
- **`list_servers`** gains `this_store_covers`, a `peer_fleets` array, and a `peer_note`. Both are always present: an *empty* `peer_fleets` has two very different meanings (this really is the only store, or nobody declared the siblings) and the service cannot tell them apart, so `peer_note` says exactly that rather than letting an empty array read as "this is the whole fleet." An **empty registry** answers in prose rather than JSON, and carries the peer list too — a store with nothing registered is a fresh or just-restarted box, which is the worst place to drop the disclosure.
- **The server-resolution miss** appends the disclosure to the existing "Could not resolve server. Available servers:" listing, naming the peer whose declared coverage matches — so *not monitored here* stops looking like *not monitored anywhere*.

**`storeName` names the store on its own self-alerts.** Every fleet-level self-alert — `Store Disk Pressure`, `Retention Held`, the `Collector Cost Digest`, the `Fleet Sweep Rollup`, all twelve families and their resolution edges — fires under the constant `Monitor Store`, which is unambiguous with exactly one store and collides with exactly two: on a shared channel the alert cannot say which host it is about, and the delivery fingerprint downstream automation dedups on is identical on both stores, so the second store's incident lands on the first store's ticket as a recurrence rather than opening its own. Set `storeName` on each store and its self-alerts carry that label instead — into the cards, the alert history, the mute-rule matching and the fingerprint, the same way a monitored server's display name travels. **Setting it is accepting a re-key**: the label is part of the fingerprint, so open work items keyed on the old one are orphaned and fresh ones start beside them. That is why it is opt-in with the constant as the default (unset is byte-identical to every earlier release), and why there is deliberately no machine-hostname fallback — a fallback would perform that re-key on every existing install at upgrade, silently. Two couplings to plan for: **mute rules match the alert row's spelling**, so re-scope any self-alert mute from `Monitor Store` to the new label; and **do not reuse a monitored server's display name** — the two would be indistinguishable on every shared surface including the triage page, and nothing polices it, because the registry is store-authoritative after seeding and config validation cannot see it.

`matches` is deliberately plain substrings, no globbing and no regex: it exists to answer "which region/role prefix is this name?", and a pattern language would be a config surface with its own failure modes. Blank entries are dropped — an empty substring matches every name, which would make one peer claim the whole fleet. A peer with no `matches` is still disclosed everywhere; it just cannot be singled out on a miss, and the miss message says so instead of implying the server is unmonitored.

A **file-only** block (not seeded into the control plane): it describes the deployment topology of *this* box, which must not be editable from a peer's Viewer. An edit takes effect on the next service restart. There is deliberately **no cross-store connectivity** here — actual federated reads (auth between stores, latency, partial failures) are a much larger surface, and may never be worth building if disclosure alone makes the split legible.

**Declaring nothing changes nothing, with one exception worth knowing about on upgrade.** The instructions, the resolution-miss message, and `list_servers`' empty-registry sentence are byte-for-byte what they were. But `list_servers`' JSON envelope carries `this_store_covers`, `peer_fleets` and `peer_note` on *every* response, declared or not — so a script comparing that tool's exact shape sees three new keys even if you never write a `peers` block. That is deliberate: an empty `peer_fleets` means *either* "this is the only store" *or* "nobody declared the siblings", and a note that only appeared when peers were declared would say nothing in precisely the case that produces the wrong conclusion.

**A `peers` block that fails validation is refused whole, and nothing is disclosed** — not the valid subset. An unfinished block that asserts coverage which may be wrong is worse than no block, and the service logs each problem at Critical. The check runs inside the publish rather than only in config validation, because the MCP host loads its own config and deliberately never validates it (its fail-closed checks are host-local), so validation alone would leave the one path that actually broadcasts uncovered.

## frontDoor (optional)

Turns this service into a front door: one MCP address and one web address in front of several Darling stores. It is off unless `frontDoor.enabled` is `true`. The block is file-only, holds the access token of every store, and is never returned by a page or an MCP tool. It is not part of `peers`, because the `peers` text goes to every MCP client. In front-door mode the service has no database of its own, so `postgres` is not required, and no collector runs. Every field, the checks at start and the setup of each store are in [The front door](front-door.md).

## heartbeat

An optional outbound ping to a dead-man's-switch URL, off unless `url` is set. File-only: the web Admin and MCP cannot edit it, and no page returns it. See [Watching the service from outside](operations.md#watching-the-service-from-outside).

## reads (optional)

`reads.maxHeavyReads` (default 2) is how many long reads the MCP server and the web dashboard run at once. A read is long when the 90th percentile of its tool or page is above 2 seconds at that window size over the last 7 days (with no history yet, a 7-day or longer window counts as long). Up to 16 more long reads wait, oldest first, for up to 45 seconds; past that a read is refused: `busy` on MCP and HTTP 429 with `Retry-After` on the web. Short reads, the health reads (`get_read_latency`, `get_slow_reads`, `get_collection_health`, `get_collection_log`, `get_store_metrics`, `get_store_log`, `list_servers`) and MCP write tools never wait. `0` turns the limit off. The limit is per service process: the WPF viewer reads the store directly and is not counted. The value is read when each server starts.

An identical long read is answered from memory for a short time: 15 seconds for a read with no window or a window up to 1 hour, 30 seconds up to 24 hours, 60 seconds up to 7 days and 120 seconds beyond. One read is cached whatever its cost: `get_resource_use_by_tag` for the whole fleet (no server named) with a window of 24 hours or more, for 5 minutes, because it takes about a minute when nothing is stored and a page reload or a second user would pay that again. The plan cache, procedures and blocking sections of that answer come from 1-minute collectors, so a blocked process report or a deadlock that landed in the last 5 minutes can be missing from the fleet answer until the entry expires. The window is the length asked for, not its band, so a fleet read of 2 to 23 hours (the page's Past 4 hours) is not held for 5 minutes. A window under 24 hours, and a read of one server, keep the times above. The 5 minutes count from when the answer is stored, not from a fixed clock boundary. A Custom View or alert notebook read panel of `get_resource_use_by_tag` loads through the same read as the page, so with no server and a window of 24 hours or more it is held for 5 minutes too, with the same lag. Only a composed panel (one with a `source`) keeps the times above, and this read is not a compose source. A read answered from memory takes no slot. The cache is per service process too.

`get_read_latency` (and its grid on the web) counts these per route and window size. `count` and the percentiles cover only the reads that ran. `queued` is the reads that waited for a slot, `queue_wait_ms` their summed wait and `queue_wait_p95_ms` the 95th percentile of that wait. `rejected` is the reads answered `busy` or 429, `cache_hits` the reads answered from memory and `cancelled` the reads whose caller left. `wait_total_ms` stays the wait for a store connection only. The `admission` object is the live state of this process since it started: the limit, the long reads running and waiting now, and per route the reads admitted, queued, refused, answered from memory and missed by the cache. It is not stored, so it starts again at zero after a restart.
