# Security and agent changes

Audience: operators.

This page covers the store's schemas and roles, the list of agent changes with its undo and its switch, and what an agent can change at Level 2. It moved here from the Darling operator guide.

## Security & Least-Privilege Roles

The store is split into two schemas so that no consumer connects with more privilege than it needs:

- **`collect`** — the collector hypertables (one per collector) plus the service-written, user-read metadata (`servers`, `collection_log`, `analysis_findings`, the `v_*` views). Read-only to everyone but the service.
- **`config`** — exactly the tables a human operator changes through the Viewer or MCP: `config_mute_rules`, `config_alert_log` (alert dismissals), `config_edge_trigger_watermarks`, and `analysis_muted`.

Table names are unchanged — only their schema moved — and the shared SQL keeps using the bare, unqualified names, resolved through `search_path = collect, config, public` (set as the database default and carried on the managed connection strings). This is deliberate: Darling's SQL is byte-identical to Lite's DuckDB SQL, and re-qualifying it would fork that twin.

**The roles.** The service still owns the store as the `darling` superuser (it does the DDL — migrations, hypertable conversion, retention). On top of that, **managed mode provisions four least-privilege login roles**, and so does the service on the compose distribution's own store; any other bring-your-own store gets the same four from a shipped script (see below):

| Role | Privileges | Used by |
|---|---|---|
| `darling` | superuser / owner | the service (collection, migration, provisioning) |
| `admin` | SELECT on both schemas — **including** the secret columns, which the Settings window reads — plus INSERT/UPDATE/DELETE on `config` only. No statement timeout | the Viewer, by default (`connectAs: "admin"`) |
| `viewer` | SELECT on all of `collect`, and on `config` **minus the secret columns** of `config_monitored_servers` / `config_command` / `config_notification` (carved fail-closed, below). No writes. Runs under `statement_timeout = 15s` | a locked-down Viewer (`connectAs: "viewer"`) and remote Viewer seats |
| `web` | `viewer`'s exact read surface (the same secret-column carve) + the web dashboard's narrow single-table writes: INSERT/UPDATE/DELETE on `config.custom_views` (the composer's saved views), on `config.custom_alert_rules` (the user-authored alert rules), on `config.database_state_expected` (the per-database override editor) and on `config.config_mute_rules` (the dedicated mute-rule endpoints, [#3450](https://github.com/erikdarlingdata/PerformanceMonitor/issues/3450)) — plus UPDATE on exactly the two `config_service` reload-beacon columns the mute table's bump trigger writes as the caller. Runs under `statement_timeout = 15s` | the web dashboard (managed and compose stores: its own login; bring-your-own: when `postgres.webConnectionString` names it). Never a seat login, and it never gets a network line |
| `mcp` | `viewer`'s exact read surface + INSERT on `collect.analysis_findings` + INSERT/DELETE on `config.analysis_muted` (the mute and unmute tools) + INSERT/UPDATE/DELETE on `config.custom_views` (the custom-view tools) + INSERT/UPDATE/DELETE on `config.database_state_expected` (`set_database_state_expected`, #6397) + UPDATE of the three close columns on `config.investigation_requests` and INSERT of the five decided-note columns and UPDATE of the four decision columns on `config.investigation_notes` (the four investigation admin tools, #6400) + INSERT of the practice request's columns on `config.investigation_requests` and of the copied alert columns on `config.investigation_request_alerts`, INSERT/UPDATE of the feedback columns on `config.investigation_feedback` and INSERT/UPDATE of the profile columns plus DELETE on `config.agent_environment_profiles` (the three tools that start a practice request, record feedback and save a profile, #6400) + the alert-tuning writes (INSERT/UPDATE/DELETE on `config.config_mute_rules`, UPDATE on `config.config_alert_settings`, UPDATE on the single non-secret `email_cooldown_minutes` column of `config.config_notification`, and the `config_service` reload-beacon columns) + the server-onboarding writes (INSERT/UPDATE/DELETE on `config.config_monitored_servers` — the credential column stays SELECT-carved, so it can WRITE a password blob but never READ one back) | the store identity the MCP host connects as — loopback and network alike — on a managed store (`DarlingMcpHostService` builds its pool from the stored `mcp`-role credential, never from the owner's) and on the compose store; on any other bring-your-own store when `postgres.mcpConnectionString` names it |

`admin` cannot `DROP`, alter schema, touch `collect` data, or create objects — it can only do what the Viewer's mute-rule / alert-dismiss surfaces need. The `mcp` role is narrower still: it reads exactly what `viewer` reads (the secret config columns are carved out identically) and its writes are a small, enumerated set — the two analysis-table INSERTs (`analyze_server` + `mute_analysis_finding`), the single-table `config.custom_views` CRUD (the custom-view tools), the alert-tuning writes (`config.config_mute_rules` CRUD + a single-row `config.config_alert_settings` UPDATE + a single-COLUMN `config.config_notification` UPDATE for the delivery cooldown, plus the two `config_service` beacon columns so a settings write's self-bump trigger can fire), and the server-onboarding writes (`config.config_monitored_servers` CRUD for `add_servers` / `remove_server` — its `config_monitored_servers` write fires the SAME `config_service` beacon trigger, already covered by that column grant) — so a token-holder on the network MCP endpoint can never reach the `config`-table service-credential pivot, the secret columns, or a service flag like `paused`. Even on `config_monitored_servers`, which it may write, the `encrypted_password` column stays in the fail-closed secret carve, so `mcp` can WRITE a credential blob (onboarding) but can never READ one back. `config_notification` is the sharpest case of the same shape: it holds the SMTP password blob, the Teams/Slack/generic webhook URLs and the PagerDuty routing key, so the write there is COLUMN-level on the one non-secret cooldown column — `mcp` cannot write even a non-secret sibling like `smtp_host`, let alone a credential. `ALTER DEFAULT PRIVILEGES` means new collector tables auto-inherit SELECT for `admin`/`viewer`/`web`, so the model never drifts as collectors are added (every `mcp` write is an explicit single-table/single-column grant, deliberately not schema-wide).

**Managed mode** provisions all of this automatically on every start (idempotent and self-healing), generating a per-role DPAPI-LocalMachine credential — `pg-admin-credential.dpapi`, `pg-viewer-credential.dpapi`, `pg-web-credential.dpapi`, and `pg-mcp-credential.dpapi` beside the data directory, same posture as the owner's `pg-credential.dpapi`. The passwords never travel in a statement: provisioning sends each role's SCRAM-SHA-256 verifier, which PostgreSQL stores as-is (what psql's `\password` does), and only for a role whose stored verifier no longer matches its credential file, so a steady-state start sends none (#3910). Every start also switches off `SUPERUSER`, `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS` on the four roles and revokes any role membership someone granted one of them since ([#3914](https://github.com/erikdarlingdata/PerformanceMonitor/issues/3914)): the batch grants none, and either would outrank the grants above (a `pg_read_all_data` membership reads the carved secret columns). Nothing to configure beyond `connectAs`.

**The compose store** gets the same roles from the same batch ([#3914](https://github.com/erikdarlingdata/PerformanceMonitor/issues/3914)), because it is the service's own: the service recognizes it by logging in as the store's bootstrap superuser (the role `initdb` created, `POSTGRES_USER` in the compose file), inside a container. The passwords are generated the same way and kept as plain owner-only files (`pg-admin-credential`, `pg-viewer-credential`, `pg-web-credential`, `pg-mcp-credential`, the `file:` secret shape) in the `darling-credentials` volume at `/var/lib/darling/credentials` — the container boundary is the isolation there, as it is for `secrets/`. Three differences, each deliberate: the roles carry the comment `darling-compose` rather than `darling-managed`, so the service never takes over a role `provision-roles.sql` made (it re-keys the roles it owns from its credential files every start, and would otherwise reset an operator's password); the owner and database are whatever the store's login and database are called; and the database-level `REVOKE ALL … FROM PUBLIC` is left out, because people read the compose store directly with roles of their own and that statement would take their `CONNECT` away. When the store is not recognized (a login that is not the bootstrap superuser, or a cluster that also holds a database besides the store's own and `postgres`, which makes it an operator's own cluster), or a same-named role is not the service's, nothing is created. On such a start, and on one whose provisioning fails or never runs because the collector stopped first, the web dashboard and MCP keep connecting as `web` and `mcp` with the credentials an earlier start wrote, if the files pass the trust checks; a role login the store refuses keeps that surface down rather than falling back. Only a surface with no usable credential connects as the owner. Each surface's startup warning says which of these it is and why. The trust checks: every start sets the credentials directory back to owner-only (0700) before reading it, and a directory that is a symbolic link, still reachable by other users afterwards, or was writable by them before has none of its files read (every role gets a new password that start). Each file must be a regular file with no group or other permissions. The file's owner cannot be checked from managed code; the named volume the Dockerfile seeds as `root:root` 0700 is what keeps anyone else from creating one, so a bind mount another host user can write to is outside what the checks can see.

**Credential file protection.** DPAPI LocalMachine scope is deliberate (the service writes the credential, a *different* interactive user's Viewer reads it), which means the machine-bound blob is decryptable by anything that can *read* the file. So the credential files are locked down with an NTFS ACL that strips the inherited world-read `%ProgramData%` would give them:

| File(s) | Readable by |
|---|---|
| `pg-credential.dpapi` (superuser), `pg-web-credential.dpapi` (the web dashboard's role), `pg-mcp-credential.dpapi` (the network MCP role) + the transient init pwfile | SYSTEM, Administrators, the service account. **Not** the operator group |
| `pg-admin-credential.dpapi`, `pg-viewer-credential.dpapi` | the above **+ members of the local group `PerformanceMonitor Darling Operators`** (the Viewer and the CLI, run without elevation) |
| `log-hash-key.dpapi` (the store's log-hash key, [#4004](https://github.com/erikdarlingdata/PerformanceMonitor/issues/4004)) | SYSTEM, Administrators, the service account. **Not** the operator group |

`pg-web-credential.dpapi` and `pg-mcp-credential.dpapi` sit with the superuser (non-interactive) rather than with the Viewer's credentials because only the in-service web and MCP hosts read them — never an interactive Viewer.

**The log-hash key** ([#4004](https://github.com/erikdarlingdata/PerformanceMonitor/issues/4004)). `pg_log_events` stores two identities per event: `raw_line_hash`, which every read dedupes on, and `statement_fingerprint`, which groups one statement shape. Both are HMAC-SHA-256 under a 32-byte key the service generates and keeps **outside** the store, so a reader of the store cannot test guesses at the literals a log line hid (an unkeyed hash let #3996's review recover a four-digit PIN in 6 ms). Neither hash is returned by any tool or viewer. The key is loaded once at service start and lives beside each distribution's other secrets: `log-hash-key.dpapi` next to `pg-credential.dpapi` on a managed store (DPAPI, the ACL above); `log-hash-key` in the `darling-credentials` volume on compose (0600, under the same directory and file checks as the role passwords); and `darling-keys/log-hash-key` (`.dpapi` on Windows) beside `darling.json` on bring-your-own. It is generated when no file exists. The service does not replace an existing key, because a new one gives every stored log event a new identity: a key file it cannot trust or read makes it refuse to collect log events, with the file and the reason in the service log, until you fix the file's access or delete it (the way to rotate). The one exception is a key directory other users could write to, such as a bind-mounted credentials directory left at `0777`: any file in it could have been planted, so the moment the service finds it open (whichever start, and whichever part of the service looks first) it sets it owner-only, removes the key and the role passwords there, and logs an error; a new key and new passwords are generated, and the first `pg_log_events` run after that says so on its Collection Log row. A directory with something in it at one of those names is left alone (the service never deletes someone else's tree, and nothing reads a directory as a credential), but everything else is still removed and the directory stays owner-only; that start uses nothing in the directory, and its error names each path to remove before you restart. A directory that keeps being opened (a Kubernetes `fsGroup` re-applied on every mount) rotates the key on every start, so keep it owner-only. Run one service per credentials volume (on Kubernetes, one replica with `strategy: Recreate`, never a rolling update): the check is not locked across processes, so a second service starting beside the first could read the directory between the first one's chmod and its removal. Keep it with the store's backups of its other credentials. Rows stored before #4004 keep their unkeyed hashes until the 30-day retention drops them, so the first cycle after the upgrade stores each entry still in the tail's overlap window once more, and a statement shape's fingerprint changes once.

**The password key** ([#5366](https://github.com/erikdarlingdata/PerformanceMonitor/issues/5366)). A SQL login password saved in the store is sealed to a key pair the service owns. This works on every platform, so you can save a password on Linux and in a container as well as on Windows. The store publishes the public half, and every place that saves a password seals it to that half: the Viewer, the web dashboard, the MCP tools and `--add-server`. Only the service holds the private half, so only the service can open a saved password. A sealed password opens only for the connection it was saved with. If you change a server's host, port, database, login or encryption settings, enter its password again.

- **Where the key is kept.** In the compose deployment it is the `password-key` file in the `darling-credentials` volume, with the other service credentials. On a Linux or Windows install where you bring your own PostgreSQL it is in a `darling-keys` directory beside `darling.json`. With the managed PostgreSQL on Windows it is `password-key.dpapi`, beside the other credential files. It is never in the store or its volume.
- **First start and the fingerprint.** The first start makes the key. Each start logs a `Password key` line with the key's fingerprint, as four groups of four letters and digits. The first time a Viewer saves a password to a store it shows the same fingerprint. Check that the two match. If the key later changes, the Viewer stops saving passwords. It asks you to compare the new fingerprint with the service log, then choose Trust the new key.
- **Backups.** Back up the credentials volume (or the `darling-keys` directory) after the first start and again after every reset. Keep that backup apart from the store's backups. A store restored without its key cannot open its saved passwords, and the service reports the key as missing. On Windows the key is protected with DPAPI for the machine, so its backup restores only on the same machine.
- **Resetting the key.** [`--reset-password-key`](collector-settings.md#make-a-new-password-key---reset-password-key) retires the key at the next start and makes a new one. Every saved password must then be entered again. If the key may have been copied, reset it. Then change the SQL logins' passwords. Delete the retired key file (`password-key.retired`, or `password-key.dpapi.retired` on Windows) once you no longer need it.
- **Updating and rolling back.** Update every Viewer that saves passwords to the store. An older Viewer does not know the key and saves passwords in the old format, which the service does not use for a new row. Passwords saved on Windows before the upgrade keep working on the same machine. If you roll the service back to an older version, it cannot open the passwords saved since the upgrade. Enter them again.

**Who can read `darling.json` and the admin and viewer credentials.** SYSTEM, Administrators, the service account, and members of the local group `PerformanceMonitor Darling Operators`. No one else can, including a user who is logged on at the console. Other services, sandboxed or SSRF socket code and scheduled tasks are shut out too, and so is the group from the superuser and MCP credentials.

`install-darling.ps1` and `upgrade-darling.ps1` create the group, empty, when it is missing. Adding a member is your decision, and the answer to the installer's question is No unless you type `y`. At the end of the install, `install-darling.ps1` asks `Add <account> to 'PerformanceMonitor Darling Operators'? [y/N]`, naming the account signed in to the session. When that is not the account that ran the script (you elevated with another administrator account), the prompt says so. For a scripted install, `-AddOperator DOMAIN\user` adds that account without asking. `-NoOperatorPrompt` never asks. A host that cannot take an answer (input redirected, or PowerShell started with `-NonInteractive`) counts as No. On a domain controller no group is created and nothing is asked. `upgrade-darling.ps1` never adds a member.

After a Yes, the account also gets a direct grant of the same access the group has. The Viewer and the CLI then work in the session that is already open, with no sign-out. The grant is read on `darling.json`, read on the store's `pg-admin-credential.dpapi` and `pg-viewer-credential.dpapi`, and traverse on the store folder. The service rewrites those permissions at each start, which drops the direct grant. From then on the group covers the account only after the person has signed out and back in once. A reboot does that. A service restart or an upgrade does not, so a person still in the same session then has to sign out and back in.

`uninstall-darling.ps1` removes the grant from those four paths. A plain uninstall keeps the group and its members. `uninstall-darling.ps1 -PurgeData` removes the group too, but only when the install created it, which it judges by the group's description. A group an administrator made first is left in place. To remove it sooner, run `icacls <path> /remove *<the account's SID>` on each path. On a fresh install, the service writes the credential files at its first start. The installer waits up to three minutes for them, so the grant can include them.

For everyone else, and after a No, add each person who runs the Viewer or the CLI without elevation. Use Computer Management > Local Users and Groups, or `net localgroup "PerformanceMonitor Darling Operators" DOMAIN\user /add`. A person you add that way has to sign out and back in before the membership takes effect.

Members can read `darling.json` and the store's admin and viewer credentials, which decrypt every stored password. Add only people who are trusted with those passwords.

A hand install (`sc create`, no installer) has no group until you create it. Until then the service grants only SYSTEM, Administrators and itself, and it logs a warning that names the group. Create the group, add the people, and restart the service so it grants the group. Anyone who is not a member sees a message that names the group when the Viewer or a CLI verb cannot read the file.

The installer also creates the store folder before the service starts (`%ProgramData%\PerformanceMonitorDarling` unless `postgres.dataDirectory` says otherwise). Administrators own it, and it gets the same locked ACL the service applies on every start. An ordinary user can otherwise create and own that folder first.

The service also refuses to trust a credential file that isn't owned by SYSTEM/Administrators/itself, and regenerates an untrusted role credential.

**A read-only (`viewer`) Viewer degrades gracefully.** It probes its own privileges on connect (`has_table_privilege`), so the mute-rule Add/Edit/Toggle/Delete/Purge buttons and the alert Dismiss / Dismiss All buttons are hidden or disabled, and any write that still slips through returns a clear "read-only connection" message instead of an error.

**Bring-your-own PostgreSQL.** The schema split runs everywhere (it's a migration — the service applies it on startup and best-effort sets the database `search_path`; if your collection login can't `ALTER DATABASE`, run that one statement yourself as the owner). The service provisions roles only on a managed store and on the compose store, so for any other BYO store you create them yourself, once, with the shipped script:

```
psql -X -h <host> -U <owner> -d darling -f Darling/tools/provision-roles.sql
```

The release zip, the MSI and the Linux tarball carry the same script as `provision-roles.sql` beside the service exe, so a package install runs it from the install folder. The path above is for a source checkout.

Use **psql 10 or later**. The script saves and restores your `ON_ERROR_STOP` around its collision check, and only psql 10 and later read an unset one as off; in psql 9.6 the run stops at its first error, so an owner without superuser gets no grants at all. Edit the four password placeholders (and the database/owner names if yours differ) first. Each placeholder is in two places, a check and its `ALTER ROLE` line, so use a find-and-replace on the whole file. The script stops with an error, before it sets any password, while any of the four is unchanged. If you re-run it after an upgrade with a routine that replaces `CHANGE_ME_ADMIN_PASSWORD`, `CHANGE_ME_VIEWER_PASSWORD` and `CHANGE_ME_MCP_PASSWORD` only, add the fourth, `CHANGE_ME_WEB_PASSWORD`, to it. To set the passwords with `\password` instead, put a long random value in each placeholder for this run, which `\password` then replaces for each of the four roles. The `-X` skips your own `psqlrc`: an `\set AUTOCOMMIT off` in it would leave steps 3 to 5 (the write grants, the default privileges and the public hardening) uncommitted while psql still exits `0`. The roles, the passwords, the read grants, the secret-column carve and the password key table revoke commit at the script's own `COMMIT`. An `ON_ERROR_STOP` in your `psqlrc` would change where the run stops. **It creates the same four login roles, `admin`, `viewer`, `web` and `mcp`, with exactly the managed grants** (a test holds the script's grants, default privileges and role settings to the managed batch's). If a role with one of those names already exists without Darling's `darling-managed` marker (a comment on the role), the script stops at that check with an error, before it re-keys or grants anything on that role: rename or drop the other role, then run it again.

The guard also refuses a marked role that another login administers. The marker is a public string, so it does not show who made the role. From PostgreSQL 16, a role with `CREATEROLE` holds `ADMIN OPTION` on every role it creates. That option lets the holder reset the password of the role and grant the role to other roles. The script refuses a marked role when another login holds `ADMIN OPTION` on it. That login is any role that is not a superuser, not the database owner and not the role running the script. A plain membership, such as `GRANT viewer TO some_analyst`, does not count. To continue, run the script as that login, which the check leaves out. If more than one login holds the option, run the script as one of them after the others lose it. Or, as a superuser, revoke that option or drop the role. A login that created the role cannot revoke the option itself, because PostgreSQL records that grant as made by the bootstrap superuser. Then run the script again.

The guard creates the four roles without a password. The `ALTER ROLE` lines after the guard set the passwords. A run that stops at the guard therefore leaves no password in the server log. The server writes a failed statement to its log with the whole statement text. A run that succeeds also writes all four passwords to the log when `log_statement` is `ddl`, `mod` or `all`, or when `log_min_duration_statement` is `0` or more. Step 0 turns both settings off for the session of the script, and the two sampling settings `log_min_duration_sample` and `log_transaction_sample_rate` as well. It also sets `log_min_error_statement` to `panic`, so that a failed statement is not written to the log with its text, and it turns off `debug_print_parse`, `debug_print_rewritten` and `debug_print_plan`. It can do that for a superuser, and for a role that was granted `SET` on the setting (PostgreSQL 15 and later). The role and grant statements of the run are then not in the log either. When a role that may not change `log_statement` or `log_min_duration_statement` finds either one set so that the passwords are logged, the script prints a WARNING right after step 0 and goes on.

`pg_stat_monitor` is handled like `pg_stat_statements`: step 0 sets `pg_stat_monitor.pgsm_track_utility = off` for the session (any role may), and the guard stops the run if it is still on. `pgaudit` is different. Its `role` class writes `ALTER ROLE` statements to the log, with the statement text while `pgaudit.log_statement` is on, which is its default. Only a superuser can change a `pgaudit` setting, so step 0 sets `pgaudit.log_statement = off` for a superuser (or a role granted `SET` on it) and for any other role the `pgaudit` entries of the run keep their statement text. The same holds for its `function` class, which logs the `DO` blocks that check the placeholders, so the step 0 warning also names a `pgaudit.log` setting that covers `function`. Use a `SCRAM-SHA-256` verifier in place of each password literal there.

A store you bring yourself needs one more step, for large objects and session locks. On a managed or compose store the service takes two groups of built-in functions away from every role. It grants the session lock functions back to the logins that use them. The script cannot do this, because the functions belong to a superuser. So a superuser runs the statements below once, connected to the store database. Without the first statement, any login that can connect, a `viewer` seat included, can store data in the database through large objects. Without the second and third, a session or transaction lock on the migration key, held open, makes the next upgrade wait out its time limit and stop. Replace `<owner>` with the role your `postgres.connectionString` uses.

```sql
REVOKE EXECUTE ON FUNCTION pg_catalog.lo_create(oid), pg_catalog.lo_creat(integer), pg_catalog.lo_from_bytea(oid, bytea) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION pg_catalog.pg_advisory_lock(bigint), pg_catalog.pg_advisory_lock(integer, integer),
   pg_catalog.pg_try_advisory_lock(bigint), pg_catalog.pg_try_advisory_lock(integer, integer),
   pg_catalog.pg_advisory_lock_shared(bigint), pg_catalog.pg_advisory_lock_shared(integer, integer),
   pg_catalog.pg_try_advisory_lock_shared(bigint), pg_catalog.pg_try_advisory_lock_shared(integer, integer) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_advisory_lock(bigint), pg_catalog.pg_advisory_lock(integer, integer),
   pg_catalog.pg_try_advisory_lock(bigint), pg_catalog.pg_try_advisory_lock(integer, integer) TO <owner>, admin, mcp;
REVOKE EXECUTE ON FUNCTION pg_catalog.pg_advisory_xact_lock(bigint), pg_catalog.pg_advisory_xact_lock(integer, integer),
   pg_catalog.pg_try_advisory_xact_lock(bigint), pg_catalog.pg_try_advisory_xact_lock(integer, integer),
   pg_catalog.pg_advisory_xact_lock_shared(bigint), pg_catalog.pg_advisory_xact_lock_shared(integer, integer),
   pg_catalog.pg_try_advisory_xact_lock_shared(bigint), pg_catalog.pg_try_advisory_xact_lock_shared(integer, integer) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_advisory_xact_lock(bigint), pg_catalog.pg_advisory_xact_lock(integer, integer),
   pg_catalog.pg_try_advisory_xact_lock(bigint), pg_catalog.pg_try_advisory_xact_lock(integer, integer),
   pg_catalog.pg_advisory_xact_lock_shared(bigint), pg_catalog.pg_advisory_xact_lock_shared(integer, integer),
   pg_catalog.pg_try_advisory_xact_lock_shared(bigint), pg_catalog.pg_try_advisory_xact_lock_shared(integer, integer) TO <owner>, admin, web, mcp;
```

The service itself uses no large objects. The session lock grants stay on `<owner>`, `admin` and `mcp` because the migration lock and the agent-change undo take session locks. The transaction-level lock functions go to `<owner>`, `admin`, `web` and `mcp`, the logins whose own code takes one, so a `viewer` login cannot hold one open.

These statements change the store database only. Each database on the server has its own large object functions and its own `TEMP` grant. A login that can also connect to `postgres` or `template1` can still store data there, on the same disk. The managed store runs `REVOKE CONNECT ON DATABASE postgres, template1 FROM PUBLIC;` for that reason. If no other login needs to connect to those two databases, run it on your server too.

Every run also takes back what an adopted role picked up since. It switches off `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS`, and it revokes every membership in another role. Managed mode does the same. The attribute statements and the membership statements run as two blocks with `ON_ERROR_STOP` on: a privilege refusal prints a WARNING and the run goes on, and any other error stops the run, so a lock timeout or a concurrent role change cannot leave a role with an attribute or membership while psql exits `0`.

The table grants, the secret-column carve and the revoke on the password key tables (step 2d) run as one transaction. If a statement in that block fails, psql prints the error and none of the block commits. Fix the cause, then run the script again. Step 3g repeats the key table revoke after the write grants of step 3, so the key tables are closed to `viewer`, `web` and `mcp` when the transaction commits and stay closed.

Any other error is printed and the run carries on with the rest of the script. This is psql's default and is deliberate. Read psql's output for errors, and run the lines that failed as a superuser.

An owner that is not a superuser can run the script, with these limits:

- The owner needs `CREATEROLE`. From PostgreSQL 16 it also needs `ADMIN OPTION` on each of the four roles, to set a password or take back an attribute. An owner holds that option only for a role it created itself. For a role that a superuser made, a superuser must first run `GRANT <role> TO <owner> WITH ADMIN OPTION`. The guard checks this before it sends a password. If the owner cannot change one of the four roles, the run stops at the guard with exit code 3. The message names the roles and the `GRANT` statements to run. The same stop happens when one of the roles is a superuser. Before PostgreSQL 16, it also happens when one of the roles has `REPLICATION`. Only a superuser can change such a role. The guard also stops the run, before a password is sent, when one of the four roles is a member of a role that would outrank the grants (the owner, a superuser or `BYPASSRLS` role, `pg_read_all_data`, `pg_write_all_data`, `pg_read_server_files`, `pg_write_server_files` or `pg_execute_server_program`) and the owner cannot revoke that membership. From PostgreSQL 16 that needs `ADMIN OPTION` on the role the membership is in, and no role has that on itself. The message names each membership. A superuser is never stopped by these checks.
- The owner cannot set `temp_file_limit` or the two slow-statement logging settings, and those lines fail.
- The owner cannot take `pg_stat_statements` from PUBLIC when a superuser created the extension (step 1b), because only the owner of the extension or a superuser may. The script and the service then leave the grants as they are, and each prints a warning that names the owner of the extension and the statements to run. Run them as that owner, in the store's database (with your schema if the extension is not in `public`, and your store owner for `darling`; drop the last four lines when there is no `pg_stat_statements_info` view):

  ```sql
  REVOKE SELECT ON public.pg_stat_statements FROM PUBLIC;
  REVOKE EXECUTE ON FUNCTION public.pg_stat_statements(boolean) FROM PUBLIC;
  GRANT SELECT ON public.pg_stat_statements TO pg_read_all_stats, darling;
  GRANT EXECUTE ON FUNCTION public.pg_stat_statements(boolean) TO pg_read_all_stats, darling;
  REVOKE SELECT ON public.pg_stat_statements_info FROM PUBLIC;
  REVOKE EXECUTE ON FUNCTION public.pg_stat_statements_info() FROM PUBLIC;
  GRANT SELECT ON public.pg_stat_statements_info TO pg_read_all_stats, darling;
  GRANT EXECUTE ON FUNCTION public.pg_stat_statements_info() TO pg_read_all_stats, darling;
  ```

  A superuser who runs the script does this itself, and grants the view to the store owner too, so the service's statement statistics keep working for an owner that is not a superuser.
- The owner cannot switch off `SUPERUSER`. From PostgreSQL 16, it can switch off `REPLICATION`, `BYPASSRLS` and `CREATEDB` only if it holds that attribute itself. From 16, it can also revoke a role membership only with `ADMIN OPTION` on the role that the membership is in. Before PostgreSQL 16, only a superuser can switch off `REPLICATION` or `BYPASSRLS`. The script prints a WARNING for each attribute or membership that it leaves in place. From PostgreSQL 16, the owner also has to be able to act as the role that granted each membership of the four roles (the grantor in `pg_auth_members`), because a revoke removes only the membership recorded with the grantor it names. The script names that grantor in each revoke. The guard stops the run when the owner cannot act as the grantor of a membership that would outrank the grants, and a run that still finds such a membership after the revokes stops with an error before any grant.
- If `pg_stat_statements` is loaded with utility tracking on, the script's first statement, `SET pg_stat_statements.track_utility = off`, fails for this owner. The run then stops at the guard, before it touches a role or a password. The stop matters because utility tracking records the password statements verbatim, where every `pg_read_all_stats` member can read them. To continue, run `GRANT SET ON PARAMETER pg_stat_statements.track_utility TO <owner>` as a superuser (PostgreSQL 15 and later), or turn utility tracking off for the cluster. Then run the script again.
- Two settings put the passwords in the server log even when the run succeeds: `log_statement` at `ddl`, `mod` or `all`, and `log_min_duration_statement` at `0` or more. Step 0 turns those settings off for the session. It cannot do that for this owner unless a superuser ran `GRANT SET ON PARAMETER <setting> TO <owner>` (PostgreSQL 15 and later); where it could not, the script prints a WARNING after step 0. A failed `ALTER ROLE ... PASSWORD` line, for example one that a password-check module rejects, is also written to the log with its password, unless step 0 could set `log_min_error_statement` to `panic` for the session. To keep the passwords out of the log, put a SCRAM-SHA-256 verifier in each `ALTER ROLE` line in place of the literal. You can also set the passwords with psql's `\password`.
- Three more cases write the same lines: `log_transaction_sample_rate` above `0`, `log_min_duration_sample` at `0` or more together with `log_statement_sample_rate` above `0`, and `pgaudit.log` covering the `role` class (`role` or `all`, and not `-role`) while `pgaudit.log_statement` is `on`. The script prints the same WARNING after step 0 when it sees any of them.

Then point the web dashboard and the MCP server at them with the two settings in the [`postgres` block](configuration.md#postgres) — the service's own login stays the owner, for collection:

```json
"postgres": {
  "connectionString": "file:/etc/darling/store_owner",
  "webConnectionString": "file:/etc/darling/store_web",
  "mcpConnectionString": "file:/etc/darling/store_mcp"
}
```

(literal connection strings work too; the references keep the passwords out of `darling.json`). **Left unset, a surface connects as the owner** — the collection login — and none of the role-level protections applies to it: not the secret-column carve, not the narrow write grants, not the `statement_timeout` backstop. The service logs a warning at startup naming exactly that. A read-only Darling Viewer points its `connectionString` at the `viewer` role the same way. `viewer` is read-only and is the login for remote and locked-down seats. `web` is the web dashboard's login: point `postgres.webConnectionString` at it and never give it to a seat. To move a store that an earlier script set up, set the `web` password in the script, run it again, and point `postgres.webConnectionString` at `web` in the same step. Running the script takes the web dashboard's writes away from `viewer`, so a web dashboard still on `viewer` can read but its writes are refused until you point it at `web`. The service warns at startup while `postgres.webConnectionString` names `viewer`. **That script is the authoritative grant list for a BYO store** — it is what actually runs, the table above is its summary, and an `ALTER DEFAULT PRIVILEGES` in it means a store gaining collectors later needs no re-grant for reading them. Re-run it after a schema upgrade to cover new tables and the single-table writes a newer migration adds.

## The front door holds every store's token

A front door (see [The front door](front-door.md)) keeps the MCP token, the agent-role token and the web token of each store it fronts, in the `frontDoor` block of `darling.json`. Treat that file as you treat the `postgres` connection strings. Use `mcpEncryptedToken`, `mcpEncryptedAgentToken` and `webEncryptedToken` where DPAPI is available, or an `env:` or `file:` reference. The service never prints a token in a log line or an error, and no page or MCP tool returns the block.

The roles that count at a store are the roles of the tokens the front door holds, not the roles of the person at the front door. Every web call reaches a store through the front door's shared-token sign-in, and every MCP call from an operator reaches it with the operator token. A change a person makes through the front door is attributed at the store to that shared sign-in, and the front door logs who made it: one Information line per change with the signed-in name and role, the store, the method, the path without its query string, and the store's status code (never the body, a token, a cookie or the query string). So give a person who must not change things a read-only role at the front door. For that person the front door sends each call with a header that makes the store answer it as a read-only caller, for that one call: the store refuses the reads it refuses a viewer and reports a viewer's flags. The header can only lower what the session may do, and it names nobody. Every store must run a build that reads it: the front door refuses a read-only person's call to a store that does not confirm it. Give an agent the `agent` role, which the front door forwards with the store's agent-role token only. Give the front door only the tokens that its users need.

## Agent Changes: List, Undo and the Switch

When a notification route is set to Level 2, an investigating agent may change monitoring settings (a mute rule, a custom alert rule, a threshold override) through the gate. Every call is journaled, so every change can be seen and taken back.

**The list.** The Viewer's Investigations window has an **Agent changes** tab, and the web dashboard's Admin page has an **Agent changes** tab. Each row is one agent call: when, server, kind, tool, agent, why and the result. A call that was journaled with neither a "done" nor a "failed" result shows **result unknown**: the change may or may not have happened, so it has no Undo. Below the calls, the refusals list what an agent asked for and the code it was told (for example `actions_off`). A mute row shows how many alerts were muted since the change.

**Undo.** One click restores what the setting was before the agent's change, and only when nobody has changed it since. Undo compares the setting as it is now with what the agent left; it looks at the settings an agent can change and ignores the updated-at and updated-by stamps. If they match, the before image is restored and the undo is journaled as `action_undone` by `person:<login>`, in one transaction. If a person edited it since, Undo says **changed since** and leaves the setting alone. A rule the agent deleted comes back with its own `Custom:<id>`; if a rule with that name exists now, Undo refuses. A change the agent created is deleted; one it changed is put back. Undo works for 365 days from the change.

**The switch.** `config_service.agent_actions_enabled` is on by default: a route set to Level 2 is the opt-in. **Turn off agent changes** (Viewer or web) makes the gate refuse every agent change as `actions_off` at once; nothing already made is undone. An operator can also turn it off with `set_agent_actions_enabled` over MCP (`mcp.allowWrites` and a token); `enabled: true` is refused and writes nothing, because an MCP client must not give agents back the actions a person took away: a person turns them on in the Viewer (Agent changes) or on the web dashboard. That tool is never offered to an agent.

**Who can decide.** The Viewer signs in as the store admin and can undo and switch. The web decides only under the admin store login. On the managed store the web login is derived (the `web` role) and `postgres.webConnectionString` is refused. With `web.allowAdminWrites` on, a person signed in to the web as an admin, which includes the shared web token, undoes and switches through the managed `admin` login. A new install writes it on. A `darling.json` without the key keeps it off, so an upgrade from 3.11 changes nothing until you set it. With it off, the page lists only and the 403 names the switch. On a bring-your-own store the 403 also says to give the web an admin store login: set `postgres.webConnectionString` to an admin login to decide from the web.

**Server action switches (#6269).** Each monitored server has a switch for each agent server action (`force_plan`, `evict_plan`, `kill_session`, `recompile_module`, `create_plan_guide`, `drop_plan_guide`), all off until a person turns one on; an agent can act on a server only while its switch for that action is on. The Viewer's Investigations window has a **Server actions** tab, the web dashboard's Admin page has a **Server actions** tab, and the `set_server_action` MCP tool turns a switch on or off. Each change is journaled as `server_action_switched` with who made it, from which screen, and the state before and after. The web tab turns a switch only for an admin who is signed in to the dashboard: a dashboard with no sign-in configured, or a viewer account, lists the switches and answers 403 to a change (the same rule that applies to undoing a plan force or unforce from the web). The MCP tool is served only with `mcp.allowServerAdmin`, takes ONE server by its exact name (a disabled server too; a part of a name is refused and the near matches are listed), and is never offered to an agent that investigates an alert. A switch cannot be turned on for an action the server's engine cannot run: every action except `kill_session` is SQL Server only. A switch can always be turned off. An Azure SQL Database target cannot take `evict_plan`, `create_plan_guide` or `drop_plan_guide`, and an Azure SQL Managed Instance target cannot take `create_plan_guide` or `drop_plan_guide`. The edition is the one Darling collected for the server. Until Darling collects it, the switch can be turned on and the tool still refuses the call. Where none of these is at hand, the store owner can still set the row in `config.config_server_actions` by hand; the table's grants are unchanged.

**People, identities and grants (#7107).** An administrator can name people, map each one to the identities they sign in with, and give them grants. A `web` identity is a signed-in web seat's owner key, a hash of the identity provider's issuer and subject. It is never the user name, because some identity providers reuse user names. The shared web token has no owner key, so it maps to nobody. A `slack` identity is the Slack team id and user id. One identity belongs to one person at most. A grant names a capability and a scope: one server, one tag, or the fleet. The capabilities are `ask`, `request_level_2`, `request_level_3`, `approve`, `undo`, `decide_note` and `feedback`. A `request_level_3` or `approve` grant also lists the server action kinds it covers. The web dashboard's Admin page has a **People** tab. Only a signed-in admin, or the shared web token, sees the list with each person's sign-in keys and Slack ids. Any other session sees only its own sign-in key, to give to an administrator. MCP `get_people` shows the kind of each identity and never its key or ids. Only the store owner writes the three tables. The schema upgrade itself takes every write back from the four roles, on the tables and on their id sequences. So the tables are safe even before provisioning runs again after the upgrade. Removing a server or a tag removes its grants. See [People, sign-ins and grants](admin.md#people-sign-ins-and-grants).

Only the store owner writes the three tables, as for the server action switches. The `admin`, `viewer`, `web` and `mcp` logins read them and cannot change them. Each change writes a journal row that names the administrator. Only the store owner can write those rows: `person_added`, `person_renamed`, `person_enabled`, `person_disabled`, `person_identity_added`, `person_identity_removed`, `person_grant_added` and `person_grant_removed`. The `get_people` MCP tool reads the directory. No MCP tool, chat message or agent changes it. No gate checks a grant yet. So nothing a login, token or screen can do changes, and administrators keep every power they have.

**Action approval and proposals (#7109).** Each alert route has two approval settings. `action_approval` is `required` or `off`, and a new route starts at `required`. The upgrade to this version set `off` only on the routes that were at Level 3 then, so those routes keep acting as before. `approval_single_person` starts off. A proposed server action waits in `config.agent_action_proposals` for a person. Only the store owner writes that table. The `admin`, `viewer` and `web` logins read it, and the `mcp` login cannot read it, because a proposal holds the statement it would run. A proposal is `pending` until a person approves it, and it expires after 60 minutes. The service's sweep voids a pending proposal when a person closes its request, and voids a pending `kill_session` proposal when the alert of its request resolves. It marks an approved proposal `unknown` when no outcome arrives within 10 minutes. Each state change writes a journal row that only the store owner can write: `proposal_created`, `proposal_first_press`, `proposal_approved`, `proposal_run`, `proposal_failed`, `proposal_unknown`, `proposal_refused`, `proposal_expired`, `proposal_superseded` and `proposal_voided`.

**Approving a proposal (#7109).** A person approves in two presses, and the same person makes both. Each press runs the tool's dry run again against the proposal's server. If the facts differ from what the agent proposed, the proposal ends as `superseded` and nothing runs. The confirming press checks, in one transaction, the conditions the agent's own write checks (the service switch, the request not closed, a `kill_session` on an alert request whose alert has not resolved, Level 3 over the live routes, the server's switch and the remediation login), and the approver. The approver is an enabled person signed in with their own identity, with an `approve` grant for that kind on that server. When the route does not allow single-person approval, a person who asked in the request cannot approve, and neither can the shared web token or the Viewer. The write then runs in its own transaction, which checks the same conditions again. If they no longer hold, the proposal ends as `refused` with the reason. The journal records the agent as the actor of `action_called` and the approver in its detail. No agent tool approves a proposal. The agent's own kill is also refused once a person closes the request or the alert of an alert request resolves (`request_closed`, `alert_resolved`). Approving works for the PostgreSQL kill in this version. The other six action tools refuse the press until their dry run is connected to it.

## Level 2: agents change mute rules and custom alert rules

An alert route set to **Act (Level 2)** (Viewer route editor, Agent column) lets an agent that holds a live claim on a request change alert settings on **that request's server only**, with `mcp.allowInvestigations` on, `mcp.allowWrites` off and a token set. Level 2 is a per-route choice: a request opened by alerts from several routes takes the lowest level among them, and an operator can turn every agent change off with `config_service.agent_actions_enabled`.

**Change first, report last: writes refuse after submit.** The claim must be live (not lapsed, released, reported or taken by another agent id). Every change names the request, claim and agent, a reason of 1 to 2,000 characters and evidence shaped like a report's, in the `agent_action` argument:

```json
{"request_id":"...","claim_id":"...","agent_id":"agent-a","reason":"the chain is the nightly batch","evidence":[{"tool":"get_blocking","arguments":{},"key_numbers":"12 blocked"}]}
```

| Tool | What an agent may do | Refusal codes it adds |
|---|---|---|
| `create_mute_rule`, `update_mute_rule`, `set_mute_rule_enabled` (on) | Mute exactly one metric on the request's server. The scope is `server_id` = the request's server; the mute names a `metric_name`. The reason ends with `[agent:<id> request <uuid>]`. | `mute_needs_metric`, `self_monitor_metric`, `other_server` |
| `delete_mute_rule`, `set_mute_rule_enabled` (off) | Delete or switch off a mute whose stored rule is on the request's server. | `other_server` |
| `create_custom_alert_rule`, `update_custom_alert_rule`, `delete_custom_alert_rule` | Create, change, disable or delete a custom rule whose scope is exactly the request's server, before and after. `updated_by` is `agent:<id>`. | `rule_scope` |

A custom alert rule is not tied to one server by the tool call: `create_custom_alert_rule` and `update_custom_alert_rule` take no server argument, and a rule with no `scope` in its definition applies to every monitored server. To limit one, put `{"scope":{"mode":"servers","servers":["<server name>"]}}` (or `{"scope":{"mode":"tag","tagId":<fleet tag id>}}`) in the definition (#6455). An agent's Level 2 rule must carry a scope of exactly the request's server.

What an agent never does: it never mutes a whole server (a mute without `server_id` and `metric_name` is refused as `mute_needs_metric`), never mutes the service's own alerts (a metric in the self-monitor family or one of the service's own alert names, including Notification Channel Failing and Notification Channel Recovered, is refused as `self_monitor_metric`; the availability group alerts, Agent Not Running, Agent Alert Gaps and the report digests are still mutable), and never writes an enable flag, `alerts_enabled`, a `self_alerts.*` setting or an exclusion list: `update_alert_settings`, the notification route tools, Custom Views, server tags and the server tools are not offered to an agent at all. An agent turns an alert off only with a mute. A custom rule carries no SQL: it binds an existing view panel and a predicate and runs on the viewer-role pool. A rule's name and description travel with its alerts through notification channels. A request opened by an alert from a custom rule an agent last wrote is Level 1.

The gate's refusals (`agent_action_required`, `agent_action_invalid`, `actions_off`, `claim_not_live`, `practice`, `not_level_2`, `other_server`, `journal_capped`) answer `{status: refused, reason, message}`, change nothing and are journaled once per request, tool, code and hour. A change journals `action_called` (with the before image) and then `action_done` (with the after image) or `action_failed`. Under `mcp.allowWrites` the same tools work as before and ignore `agent_action`. `action_proposals` in a report stays refused. The change, the gate's re-check of the claim, the level and the server, and the `action_done` journal row are ONE transaction: a change is in force if and only if its `action_done` row exists, and a change that fails (a duplicate name, a stale version, a rule re-scoped since it was read) rolls back and is journaled `action_failed` with the answer the agent was handed. An update replaces, never stacks, the `[agent:<id> request <uuid>]` suffix on a mute reason. A custom rule definition that does not parse is refused as `agent_action_invalid`, naming the `definition` field.
